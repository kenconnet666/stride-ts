# 决定记录

## 2026-11-20 操纵器的吸附：工具条上的开关和步长，拖的时候按住 Ctrl 反过来

工具条上一个吸附开关、移动（米）、旋转（度）、缩放（倍数）三个步长，默认关、1 米、15 度、0.1 倍（Stride 编辑器的默认值）。拖操纵器时按住 Ctrl 反过来：开着时临时不吸，关着时临时吸（Godot 的做法；Unity 只有"按住 Ctrl 吸"，Stride 只有开关）。两种用法都顺手：大部分时候自由摆、偶尔对齐的按 Ctrl，搭关卡时一直开着、偶尔微调的也按 Ctrl。设置记在编辑器的会话里（`EditorSession.snap`），换场景、试玩回来、游戏页面重新加载以后都还在；不进工程文件（是个人习惯，不是工程的设置）。实现：`SnapSettings`、`applySnap`（`editor/TransformGizmo.ts`），视口每帧照设置和 Ctrl 设操纵器的步长，拖到一半按下、松开 Ctrl 也跟着变。

顺带修的：在用户主 Chrome 里用插件验证时，标签页在后台被节流到 4 fps，按下、拖动、松开落在同一帧里，视口拿"这一帧鼠标最后的位置"去点把手，点不到，整个拖动丢了。机器卡的时候人手也会遇到。改成按下用指针事件里记着的按下那一刻的位置，同一帧里松开的先拖到松开的位置再结束。
## 2026-11-20 物理一帧补多少：按时间上限（0.25 秒），不按步数（3 步）

CI 在 SwiftShader 上帧很慢（几帧每秒），冒烟脚本发现脚本按游戏时间算的东西和物理对不上：`Simulation.maxStepsPerFrame = 3`，一帧最多补 50 毫秒的仿真，而 `Game` 一帧最长给 0.25 秒；没补完的时间一直攒着，帧率低于 20 时物理越落越远，恢复后又连着每帧 3 步地追，插值系数也超过 1（往前外推）。

- **改法**：照 Stride 4.5.2（上游自己把 `MaxStepPerFrame` 换成了 `MaximumTimeSpanToProcess`，默认 0.25 秒）：`SimulationSettings.maximumTimeToProcess`（秒，按步长向下取整）和 `dropPostponedTicks`（补不完的丢整步，默认不丢）。默认值和 `Game` 的一帧上限相同，所以物理和游戏时间总是对得上。插值系数夹到 1：有整步没补完时画最新的一步。
- **导入**：4.4 工程的 `MaxStepPerFrame` 不导入（没有对应关系，Stride 的升级器也是删掉）；4.5.2 的两个属性照导。场景文件里这两项可以不写。以前导入的内容里多出来的 `maxStepsPerFrame` 没人读，不用重新导入。
- **代价**：仿真本身是瓶颈时（一步比 16 毫秒还长），一帧最多补 15 步，会比原来更慢；这种工程把上限调小。
- **别的做法**：把 `Game` 的一帧上限降到 50 毫秒（Unity 的 maximumDeltaTime 的思路，整个游戏一起放慢）——帧率一低于 20 游戏就成慢动作，不如让物理补上。

## 2026-11-20 场景里的错误不让整个场景加载不了：缺必填属性的脚本跳过，找不到的父实体换个地方挂

编辑器验收时发现：在编辑器里给实体加了一个有必填属性（没有默认值的 `prop.entity()` 这类）的脚本、还没填，试玩时整个游戏启动失败（脚本的属性在构造时校验，抛出来场景就加载不了）。

- **脚本**（`SceneScriptBinder.attach`）：属性校验不过（必填的没设、类型不对）时 `console.error` 一条带场景、实体名、`脚本.属性` 的错误，这个脚本不挂，别的照常。和 Stride 不同：Stride 照挂，脚本用到没设的引用时才抛 NullReferenceException，而且是在游戏跑起来以后；我们在加载时就知道，报得更早、更准，也不让一个脚本拖垮整个场景。
- **编辑器**：属性面板把没设的必填字段（没写、或者引用是 null）的名字标红、带星号；保存照样保存，工具条上列出哪几处没设（`EditorSession.missingRequiredProps`），试玩时这些脚本不挂。不拦着保存：做到一半的场景要能存。
- **父实体不在场景里**（`SceneBuilder` 的 `parentOf`）：原来报错、场景打不开；改成警告，挂到父实体 id 里还在的最近一层实例上（`<实例>/<成员>` 的成员被预制体删掉时），都没有就放最上层。父实体在文件里但排在后面仍然报错（那是文件写错了，不是内容变了）。编辑器里的场景树照样显示它，用户自己挪。

## 2026-11-20 往预制体实例的成员下面加实体

场景里给实例的某个成员挂东西（给敌人预制体的手加一把场景里才有的武器）：加、粘贴、拖进成员下面的实体是场景文件里的普通实体，父实体写成员的 id（`<实例>/<预制体里的 id>`，同场景里别的东西引用成员的写法），展开时挂到成员上。不记进实例的覆盖：覆盖只改预制体里有的东西，加的实体属于场景（和 Unity 的"added GameObject"一样是实例上的增量，但我们不用另一套格式存）。

- 场景文档（`SceneDocument`）认这种父实体：`owner(id)` 是代表它的文件里的实体（成员就是它的实例），能当父实体的都有；实体的顺序要求它排在实例后面，没有兄弟时紧跟实例；删、挪实例时带着它们；挪实例到它自己的成员下面报错。文件里没有预制体的内容，成员在不在预制体里由编辑器（展开的场景）保证。
- 预制体改了、把这个成员删了：这个实体的父实体就找不到了。加载时警告、挂到还在的最近一层实例上（都没有就放最上层），场景照常打开，见下一条。
- 成员自己仍然不能拖（它跟着预制体）。

## 2026-11-20 编辑器里多选一起改

场景树里 Ctrl+单击加进、去掉一个，Shift+单击选上次点的到这次点的一段（按树里看得见的顺序），单击只选它（vue-tsx-pro 的 Tree 自己的多选是点一下加、再点去掉，`SceneTree` 在捕获阶段记下按键再换算）；视口里 Ctrl+单击原来就能加减。属性面板（`Inspector`）对单选、多选是同一套代码，单选就是只有一个实体的多选：

- **显示什么**：每个实体都有的组件和脚本（脚本按"第 k 个类名是它的"对上，同一种挂了两个也能对）。值逐项并（`ui/values.ts` 的 `mergeValues`）：一样的照常显示，向量、对象逐项比，位置的 x 不同、y 相同时只有 x 显示"多个值"（窄的数字框里是"—"）；列表长短不同、有的写了有的没写的显示"多个值"。旋转只要四元数有一处不同，三个角都显示"多个值"（各个实体的欧拉角要从各自的四元数算，并起来的四元数算不出）。
- **改一处**：对每个实体各一个 set，放进一个 batch，撤销一步全部撤回；连着拖、打字时 mergeKey 并成一步，同单选。路径按实体算（脚本在各自列表里的下标不同）。值要按原来的算的（改欧拉角的一个分量、换颜色不动 alpha、换联合的种类留下共有的字段）字段编辑器给的是函数（`ValueUpdate`），每个实体用自己现在的值算：四面朝向不同的墙一起把俯仰改成 10°，各自的朝向不变。
- **加、去掉组件**：加的组件只加在还没有它的实体上（列表里是"不是每个都有"的）；去掉是每个都去掉。脚本一样。
- 预制体实例、成员混在多选里照常（batch 里的每一步经 `toDocumentEdit` 换成实例的覆盖）。"这是哪个预制体的实例"的说明只在单选时显示。
- 没做：多选时的名字改了就是都叫这个名字（不加序号）；数值的相对改（都加 1）、按比例拖还没有。

## 2026-11-20 编辑器里加脚本组件：type 写登记的名字

属性面板的"添加组件"下面列出游戏登记的脚本（`EditAgent.scriptTypes`，`Registry.gameScriptNames`），选了加在实体的脚本列表最后，单独一步撤销；属性先都不写（用脚本的默认值，面板上淡色显示），字段照 `scriptFields` 画。

- **type 写什么**：写登记的名字（`game/camera/ThirdPersonCamera#ThirdPersonCamera`，或脚本 `props('Gameplay.Boss', …)` 给的显式名字），不写 Stride 那种带命名空间的类型名（游戏里没有命名空间这回事）。找脚本的规则统一成 `Registry.scriptsForType`：整个 type 是登记的名字就是它，否则按最后一段的类名找（导入的 Stride 场景）。加载场景（`SceneScriptBinder`）和面板（`EditAgent.scriptFields`）都用它。原来只按类名找，显式名字带点的脚本（`Gameplay.Boss`）按最后一段 `Boss` 找不到，也一并修了。
- **列哪些**：只列游戏的模块里的（`registerModules` 登记的）；引擎自己 `register` 的脚本（UI、粒子、声音的发射器和听者、导航）是场景组件的实现，场景文件里是专门的组件，不列。实体上已经有的脚本（按类名比）不再列：同一种脚本挂两个在 Stride 里能做，但实例的覆盖按类型名指脚本，挂两个就分不清；要的时候再说。
- 预制体实例上加脚本记成实例的覆盖（整个脚本列表，`toDocumentEdit` 原有的规则）。

## 2026-11-20 富文本的写法和排版（运行时）

用户定的方向是"文件里存 Markdown，Markdown 没有的用它自己的扩展语法补，普通的阅读器看到的仍是可读的文字"（本文件"编辑器的界面用 Vue……"那条）。这次做运行时：`rendering/text/markdown.ts`（解析）、`richLayout.ts`（排版）、`SpriteBatch.drawRichText`（画）、`ui/controls/RichTextBlock.ts`（控件），SpriteFonts 加了第九屏。

- **子集**：照 CommonMark 的段落、软换行（单个换行是空格）、硬换行（行尾两个空格或 `\`）、`#` 标题、`-`/`1.` 列表（两个空格一层）、强调的配对规则（左右侧翼、下划线在单词中间不算、三的倍数规则）、行内代码、链接、转义；删除线照 GFM 的 `~~`。不做引用块、代码块、表格、图片、HTML、自动链接（UI 的文字用不上，要时再加）。
- **扩展的写法**：比较过 Unity TextMeshPro 的 `<color=#f00>`、Godot 的 BBCode `[color=red]…[/color]`、HTML 的 `<span style>`、Pandoc/Djot 的方括号属性 `[文字]{…}`、markdown-it-attrs 的 `{.class}`。选 Pandoc（Djot 也一样）的方括号属性：`[文字]{color=#ff8800 size=120% .underline}`，链接后面也能跟。理由：它本来就是 Markdown 方言里的写法（Pandoc 认，`.underline` 就是 Pandoc 的下划线），普通的 CommonMark 阅读器把它原样显示成"[文字]{color=…}"，仍然读得懂；标签式的写法在不认识它的阅读器里要么被当成 HTML 藏掉、要么满屏尖括号。color 是 `#rgb`、`#rrggbb`、`#rrggbbaa` 或 CSS 的基本颜色名（不预乘，画的时候乘），size 是虚拟像素或百分比；不认识的属性忽略，以后加 `font=` 这类不用改语法。
- **字体**：粗体、斜体、粗斜体、代码优先用控件给的同族字体（`boldFont` 这些，Stride 的字体资源本来就是一个字重一个文件）；没给时合成，做法同 FreeType：粗体轮廓往外扩 em/48（`FT_GlyphSlot_Embolden`，用描边同一套按距离的着色，前进宽度加两份），斜体往右斜切 0.2126（12°，`FT_GlyphSlot_Oblique`，只改字形的 y 轴）。
- **排版**：一行里不同字号基线对齐、行高取最高的；对齐在画的时候按框宽加到每行（框宽变了不重排）；块之间空半行，列表项之间不空，列表缩进 1.5 个字号、记号挂在左边。和 Stride 的 TextBlock 换行不同：中日韩的字之间也能断（Stride 只在空白处断，中文整句只能按字硬断）。下划线、删除线的位置和粗细取 em 的比例（字体文件里没存 post 表的值）。
- **链接**：只有链接点得到（`intersects` 只认链接的矩形），文字其余部分不挡游戏的输入；按下、松开在同一个链接上发 `LinkClicked`（冒泡）。影子 DOM 里富文本按行出 span、每行按链接分段，链接是 `role=link`、能 Tab 到、Enter 和读屏的点击都触发同一个事件；链接的节点不接鼠标（鼠标点在画布上，走上面那条路）。不能用鼠标拖着选中（`isSelectable` 不起作用）。
- **为什么解析不放进 wasm**（用户问到）：UI 的文字一般几十到几百个字，只在文字变了的时候解析一次（`RichTextBlock.document` 缓存着）；在这台单核慢的机器上，35 个字的一句解析约 8 微秒，2 KB（40 个列表项，每项有粗体、斜体、代码、链接、颜色）约 0.32 毫秒。字符串进出 wasm 要编码、拷贝，这段开销和解析本身是一个量级，换不来什么。要显示大段文档（游戏内的书、帮助）时再量。
- 还没做的：编辑器里的所见即所得编辑（下一步）；放在 3D 里的 UI 里的富文本照常能画，但没单独验过。

## 2026-11-20 点选认粒子和放在 3D 里的 UI；全屏的 UI 不参加点选

路线图遗留的小项"粒子、场景里的 UI 的点选"（`game.pick`、`stride pick`、编辑器的视口选物体都走 `ScenePicker`）。

- **怎么画**：粒子和 UI 都不是渲染特性，`ScenePicker` 在网格、精灵那一遍之后直接调 `game.particles.drawPicking`、`game.ui.drawPicking`，同一个编号缓冲、同一个只留被点像素的剪裁矩形，写实体的变换槽位加一。照"画出来是什么样点到的就是什么样"：粒子用同样的四边形和材质，预乘颜色的 rgb 和 a·alphaFactor 都不到 0.1 的地方丢掉（加法混合的粒子 a 是 0，靠 rgb）；UI 用同样的 `drawUI`，`SpriteBatch` 设了 `pickId` 时贴图按 alpha、文字按字形的覆盖率丢掉差不多全透明的地方。所以点到 UI 页面上透明的空处会点到后面的东西，不是整块矩形都算。
- **前后**：点选时粒子写深度（主画面里不写），UI 不写、在最后从远到近画，和网格、精灵、粒子靠深度测试比远近。
- **数据不互相盖**：点选和主画面在同一帧里录命令，`queue.writeBuffer` 都在提交之前生效，共用缓冲的话后写的会盖掉主画面的数据。所以粒子用另一个 `ParticleRenderer` 实例，UI 每个组件另有一个点选用的 `SpriteBatch`（都是第一次点选时才建）。考虑过在 CPU 上拿射线和 UI 平面求交：要再拿到那个像素的深度才能和场景比远近，也做不到"透明的地方点不到"，不做。
- **全屏的 UI 不参加点选**：`game.pick` 和编辑器点到全屏 UI 时，返回的是它后面场景里的东西。理由：全屏 UI 不在场景里，不随相机走，盖满整个画面；点它的元素是 UI 自己的输入处理（`UIPicking`、`elementUnderMouseCursor`，UI 占着的输入脚本看不到）。编辑器的视口里它要是能点中，透过 HUD 就选不到场景里的东西了；要选 UI 的实体在场景树里点，编辑 UI 的元素以后是 UI 页面编辑器的事（Stride 也是单独的 UI 编辑器）。
- **编辑器的选中框**：粒子系统用包围形状（Stride 的 BoundingShape），没有时用活着的粒子占的范围（`ParticleSystem.particleBounds`，框会跟着粒子变）；放在 3D 里的 UI 用上一帧画的那块板（`UISystem.worldBox`，大小是 Size，页面内容超出虚拟分辨率的部分不算）。调试线（选中框、操纵器）改在 UI 之后画，不被 3D UI 盖住；代价是和场景比深度的调试线在 3D UI 后面时也画在 UI 上面（UI 不写深度）。
- 实测（ui-element-link 的倾斜场景、particles-sample，无头 Chrome）：点 3D UI 的面板、按钮返回 UI 的实体，按钮前面的球、跟着的骑士、烟各自返回自己的实体，UI 页面中间透明的地方点空；全屏场景里点按钮返回它后面的球。

## 2026-11-20 编辑器里复制、粘贴实体：粘贴成兄弟，引用跟着拷贝走

场景树、视口里 Ctrl+C / Ctrl+V / Ctrl+D（工具条上也有），实现在引擎的 `editor/copyEntities.ts`，剪贴板在界面的会话里。

- **粘贴到哪**：Ctrl+V 粘贴成选中的（最后一个）实体的兄弟，紧跟在它后面；Ctrl+Shift+V 粘贴成它最后的子实体；没选中时放在最上层的最后。Ctrl+D 每个选中的实体各拷一份，放在原来的那个后面、同一个父实体下。粘贴出来的选中（场景树展开到它们），一次操作撤销一步。照 Unity 2022 起的做法（Paste 是兄弟、Paste As Child 另一个键）：用得最多的是"再来一个一样的放旁边"，粘贴成子实体容易把东西塞进不想要的层级。Stride 的 Game Studio 粘贴到选中的实体下面，不跟。
- **拷什么**：选中的实体连同后代、组件（祖孙都选中时只算最上面的）。新 id；名字、本地的变换不变（不像 Unity 加 "(1)"，和 Stride 一样；本地变换不变是因为换了父实体也照"放在父实体的那个位置"理解，和拖动换父实体一致）。
- **引用**：拷的实体之间的引用（父实体、约束的两个物体、实例化、两种 link、脚本属性的 `$entity`，实例成员的 `<实例>/…`，实例覆盖的值里的实体）换成新的；指向拷贝以外的照旧指原来的（Unity、Godot 都这样，拷一个跟着某个相机走的 UI 不会把相机也拷一份）。
- **预制体**：拷实例还是引用加覆盖（成员粘贴后由预制体展开出来），挂在成员下面的文档实体跟着拷；拷别的文档里的实例时，用到的预制体在粘贴前加载。选中的是实例的成员时拷展开以后的样子，成了普通实体，和预制体断开（成员不在文档里，没法"拷一个成员的引用"）。可以粘贴到成员下面（见下一条）。
- **剪贴板**放在编辑器的会话里，换着打开场景、预制体以后还能粘贴；不进系统剪贴板：另一个标签页里的编辑器拿不到，要的时候再加（JSON 的文本格式）。
- 顺带：场景文档把父实体是实例成员（`<实例>/<成员>`）的实体算作实例的后代：删、挪实例时带着它们，加在实例后面的兄弟排在它们后面，加这样的实体要排在实例后面。原来挪实例会把它们留在原地、实体的顺序乱掉。

## 2026-11-20 物理天空：Hillaire 2020 的查找表，太阳光按透射率变，天空当环境光

P4 画面功能的下一项（`rendering/Atmosphere.ts`、`AtmosphereRenderFeature.ts`，`SkyAtmosphere` 组件，场景文件的 `skyAtmosphere`，`stride call sky`）。Stride 没有。做法照 Hillaire 2020 "A Scalable and Production Ready Sky and Atmosphere Rendering Technique"，对照 Babylon.js 的 atmosphere 插件（MIT）。

- **模型**：星球中心在世界原点正下方（世界原点在北极的地面上，Y 向上，米换千米），瑞利、米氏散射和臭氧吸收按高度衰减，默认地球的参数。
- **太阳**：投阴影的方向光（没有时是第一盏）的颜色 · 强度是大气层顶的照度；地面上的直射光 = 它 · 相机处朝太阳的透射率，在 CPU 上积分（40 步），所以落日时直射光自己变红变暗，不用 GPU 读回。转太阳的实体就是日夜变化；太阳圆盘按光源的角直径（`shadowLightAngle`，和 PCSS 共用）。
- **查找表**（计算着色器，rgba16float）：透射率 256x64、多次散射 32x32（大气参数变了才算）；天空视图 192x108（太阳动了约 0.05°、相机高度变了 1 m 才算，约 0.5 ms）。天空按视线查天空视图表，打到地面的视线加上被太阳照亮的地面（Babylon 的天空在那里是黑的）。
- **环境光**：天空视图画进 64² 的立方体（每级 mip 直接按方向算，Stride 的立方体约定），镜面用天空盒的同一个预滤波，漫反射在 GPU 上投影成球谐（和资源管线的 `st_cubemap_sh_lambert` 一样的系数约定），异步读回、晚一两帧用上；当作天空盒光（`SkyboxLight.skybox` 可以是 `DynamicSky`），代替场景原来的天空盒光。太阳动了约 0.5°、亮度变了 2% 才重算（约 1 ms），日夜循环时不每帧都算。
- **空气透视**（远处的东西被大气染色、变淡）：每帧按主相机算 32³ 的体素表（屏幕 32x32 格，32 层距离按平方分布，最远 128 km），每列沿视线只走一遍、每层接着上一层积分（各层单独从相机积分时采样数不同，层和层之间的误差不连续，画面上是一圈圈的环）。不透明的画完以后按深度合成：颜色 = 散射 + 颜色 · 平均透射率（混合状态做，不要另一张贴图；各通道的透射率差别只在很远处明显，先不用双源混合）。没有表面的画法里透明的和不透明的在同一遍，透明物体按它后面的深度算，以后给透明的材质自己算。`aerialPerspectiveScale` 是距离倍数（同 UE 的 Aerial Perspective View Distance Scale），几十米的小场景要看出效果可以调大，0 关掉。
- **环境光的分辨率**：天空立方体和镜面贴图 128（64 时粗糙度 0.5 落在每面 8²、4² 的级别，双线性插值的折线在反射里明显）；每个纹素取 4x4 点平均，mip 是区域平均；预滤波按级给采样数（32、64、128、256），比统一 256 的总数还少。
- **顺带：阴影投射加按坡度的深度偏移**（`depthBiasSlopeScale` 1.5，上限 0.01）。和 Stride 不同：只有常量偏移加法线偏移时，太阳低（20° 左右）光掠过地面，受光面上是一圈圈的阴影痤疮；加了以后没了，脚下的影子也没脱开。默认的 TPP 平均亮 0.8（地面上原来轻微的自遮挡去掉了）。
- **还没做**：夜空（月亮、星星）、云、太阳在大气层外（太空）的视角、反射探针拍的面里的空气透视。场景里同时有 Background 时两个都画，天空在后（盖住背景）。
- TPP 上（`stride call sky`）：30° 时直射光 (5,5,5) → (4.4,3.7,2.9)；3° 时 (2.0,0.65,0.09)，地平线是橙色的晚霞、场景暗下来偏蓝；70° 时和原来的光照接近。

## 2026-11-20 反射探针：盒子探针，一帧拍一个面，视差校正

P4 画面功能的下一项（`rendering/ReflectionProbes.ts`、`ReflectionProbe` 组件、场景文件的 `reflectionProbe`、`stride call probe`）。Stride 没有（它只有天空盒和 LocalReflections），做法同 Unity、Godot 的盒子探针。

- **组件**：盒子以实体为中心、边长是 `size` 乘实体的缩放，不跟旋转；`blendDistance` 以内淡出；`boxProjection` 做视差校正（Lagarde 2012：反射光线打到盒子的内壁，用拍的位置到那一点的方向取）；`refresh` 是 `once`（加进来、挪了、改了盒子、`ReflectionProbes.refresh()` 时拍）或 `everyFrame`。
- **拍**：一帧最多拍一个面（不卡顿；一个探针六帧拍完），用前向渲染器的同一套通道画进 6 层的捕捉贴图；拍的视图不用方向光的阴影（级联按主画面算），以后要的话给拍的视图单独算一组级联。右手系的相机拍出来和 WebGPU 立方体贴图的面左右相反：六个面齐了以后翻正画进辐射度立方体、逐级缩小出 mip，再用天空盒的同一个预滤波（`CubemapPrefilter`，从 `SkyboxPrefilter.ts` 抽出来、管线共用）按粗糙度预滤波进立方体数组。探针每纹素 256 次 GGX 采样（源贴图带 mip，按立体角取 mip）。拍的画面里有别的探针的反射，几轮以后就是多次反射。
- **着色**：探针表按盒子体积从小到大排，小的先占：权重 = 到盒子的面的距离 / 过渡距离，乘还没被占的比例；盖不住的部分才用环境光和天空盒的镜面反射。屏幕空间反射照旧盖在最上面。只管镜面；漫反射的间接光是以后的光探针、DDGI 的事。
- **规模**：同时最多 16 个（`MAX_REFLECTION_PROBES`，按体积小的优先），每像素在着色器里循环。立方体数组按探针数取 2 的幂、不够了换大的全部重拍；128² 的面，16 个约 16 MB。开放世界要更多时改成按相机距离挑、分簇，到时再做。
- 画质档位：低档关。TPP 上（地面临时改成镜面看）墙、窗、楼梯、房子的倒影方向对；拍一个面两遍通道约 0.01 ms，着色几乎不变。

## 2026-11-20 接触硬化的软阴影（PCSS）：方向光按角大小算半影

P4 画面功能的下一项（`rendering/MeshRenderFeature.ts` 的 `pcssShadow`；Light 的 `shadowFilter: 'pcss'`、`shadowLightAngle`，场景文件的 `filter: 'pcss'`、`lightAngle`）。Stride 没有。

- **做法**（Fernando 2005）：在级联的阴影图里按遮挡物最远可能在的地方（级联的近平面）定搜的范围，16 个点找比这里离光近的深度取平均；半影的半径 = 平均深度差（换成世界单位）× tan(角半径)，换成图集的 UV；在这么大的圆盘里 16 次比较采样。和 Babylon 不同：方向光的半影直接按深度差和角大小算，不除深度、没有经验系数，角直径默认 0.53°（太阳）。
- 半影最小 1.5 个像素（接触处不出锯齿）、最大 24 个像素（搜的范围也到这里）；采样点用 Vogel 圆盘，按像素的交错梯度噪声转，噪声留给 TAA 和画面的模糊。大角度时 16 个采样有颗粒，以后可以按半影大小加采样数、开 TAA 时每帧换噪声。
- 只有方向光；点光、聚光要的 pcss 按 pcf7x7（透视投影的半影另算，以后做）。画质档位只有极高给 pcss，高档降成 5x5。采样不按级联在图集里的块裁剪，靠近块边时可能读到隔壁的块（PCF 也一样，范围小）。
- TPP 上太阳的 0.53° 半影比 PCF 5x5 还窄，看不太出差别；角直径 15° 时脚下硬、身体的影子很软。不透明通道多约 0.04 ms。

## 2026-11-20 屏幕空间次表面散射：Jimenez 的可分离核，只糊漫反射光

P4 画面功能的下一项（`rendering/SubsurfaceScattering.ts`，材质的 `subsurfaceScattering`，合成器的 `SubsurfaceScatteringBlurEffect` 开，`stride sss`；画质档位中以上允许）。

- **算法**：照 Stride 的 SubsurfaceScatteringBlur（Jimenez 2015 的可分离次表面散射）：不透明阶段之后、透明阶段之前，有散射材质的像素横竖各模糊一遍，步长按散射宽度和深度换成像素；核在 CPU 上按 Stride 的 SubsurfaceScatteringKernelGenerator 生成（几个高斯之和的皮肤轮廓，各通道的强度、衰减），每种材质一个槽位（最多 16 种，同 Stride），材质改了重新生成。
- **和 Stride 不同：只糊漫反射光**。Stride 把整个颜色一起糊，高光会糊成十字（散射宽度大时很明显）。着色器里直射光分成漫反射和镜面两份，散射材质的像素在第 3 张表面（屏幕空间反射也用的那张）的 rgb 里存颜色里不散射的部分（镜面反射、自发光），模糊时先减掉、糊完加回去。代价是这些像素不做屏幕空间反射（rgb 不再是环境镜面反射）；皮肤、蜡、玉这类材质粗糙，反射本来就弱。
- 邻居不是散射材质的不混进来，深度差得多的按 Stride 的 SSSS_FOLLOW_SURFACE 拉回中心。透光度（Translucency）同 Stride 既是模糊的强度，也定透射的强弱。
- **透射**（薄的地方背光透过来，Stride 的 MaterialSurfaceSubsurfaceScatteringShading）：有阴影的方向光按级联的阴影图算这个像素沿光的方向的厚度（往表面里缩 1.5 个像素的对角线，四个像素双线性读深度），按皮肤的透射轮廓加进直射光的漫反射，和它一起被模糊。和 Stride 不同：没有阴影图的光不算透射（Stride 当厚度是 0，被照到的地方都透亮）。点光、聚光的透射、透光度贴图、自定义的散射轮廓还没做（后两个导入时报警告）。
- TPP 上两遍模糊约 0.06 ms。

## 2026-11-20 屏幕空间全局光照：位掩码（SSILVB），按 sin 均分的位，光源是上一帧的画面

P4 画面功能的下一项（`rendering/ScreenSpaceGlobalIllumination.ts`，`stride ssgi`，默认关，画质档位高、极高才允许）。

- **算法**：照 three.js 的 SSGINode 用的 SSILVB（可见性位掩码），在 GTAO 的切片和步进上做：每个采样当作有厚度的东西挡住切片上的一段角度，32 位记哪些角度被挡。和 three.js 不同：位按 sin(和法线的夹角) 均分，每一位是同样多的余弦加权立体角，所以没挡的位数 / 32 就是可见比例，新挡住的位数 / 32 乘亮度就是那里来的间接光，不用 three.js 的经验强度 10；切片按投影法线的长度加权再归一化，平地上可见比例正好是 1。
- **光源**：着色之前算，这一帧还没画，取上一帧的 HDR 画面（半分辨率，压过亮的像素），按矩阵把采样投到上一帧的画面上；几帧以后自然是多次反弹。只取正面朝着这个像素的采样。考虑过用这一帧的直射光（要先画一遍不带间接光的）：多一遍着色，不做。
- **降噪**：每帧换噪声；按位置把上一帧的结果重投影过来累积（上一帧那里的深度对不上就不要），横竖各一遍按深度加权的模糊。
- **着色**：环境光乘它的可见比例（代替 GTAO：开着 SSGI 时不算 GTAO），再加漫反射颜色乘间接光。复用同一个绑定（binding 14），视图的 `locals.z` 说是哪一种。
- TPP 上开销约 0.2 ms（追踪 0.135 ms，半分辨率、2 个切片、两边各 8 步）。
- 调的时候踩到的：WGSL 里 `from` 是保留字（`FullscreenShader` 预热失败时现在会把编译信息的行号和原因一起报出来）；画面边上法线退化成 NaN，经过累积和模糊几秒铺满全屏（法线退化时退回朝着相机的方向）；视图的 uniform 在 `prepare` 里写，比深度预通道之后才定的东西早（`screenIndirect` 改在每帧开头定）。

## 2026-11-20 原生任务系统的默认线程数最多 8 个（native 0.30.0）

换到 18 核 36 线程（单核慢）的机器后量的（fork 的 `StrideNative/Tests/Bench/threads.mjs`，Node 里的正式版，机器空闲，每档 3 次取中位数；物理 4000 个箱子不让睡，"一大堆"是一个大岛、"100 小堆"是互不接触的物体群；导航网格的"第一次"含 V8 把 wasm 换成优化代码的热身，"热身后"是并行本身）：

| 工作线程 | 启动 | 一大堆 ms/步 | 100 小堆 ms/步 | 导航网格第一次 | 导航网格热身后 |
|---|---|---|---|---|---|
| 1 | 116 ms | 10.14 | 7.90 | 912 ms | 823 ms |
| 4 | 127 ms | 4.94 | 3.85 | 498 ms | 255 ms |
| 8 | 133 ms | 3.61 | 2.88 | 432 ms | **153 ms** |
| 12 | 139 ms | 3.23 | **2.52** | 438 ms | 165 ms |
| 16 | 151 ms | **3.15** | 2.67 | 503 ms | 198 ms |
| 35（原来的默认） | 226 ms | 3.35 | 2.75 | 765 ms | 201 ms |

- **决定**：默认是逻辑核数减一、最多 8 个（JS 的 `defaultWorkerThreads`、C 的 `sn_init(-1)` 同一个规则），要更多的游戏自己传 `workerThreads`。物理到 12～16 个就到顶（比 8 个快 10%～13%），并行任务 8 个最快，再多只是多占 CPU；浏览器里每个线程启动时还要把核心和侧模块各实例化一遍（调试版原生模块上 TPP 的原生启动 35 个线程 2489 ms、4 个 862 ms），第一次用到时的热身也随线程数变慢。空闲时工作线程都睡着（不占 CPU）。8 个以内的并行效率不差（导航网格 5.4 倍），剖析里没有锁上的空转。
- **试过、没采用**：换 mimalloc（`-sMALLOC=mimalloc`）：导航网格在 12～24 个线程时快 10%～15%，35 个时照样慢、物理反而变慢，核心模块大 15%（402 → 463 KB），没有 `mallinfo`、原生内存的统计要换接口。Node 里关掉 wasm 的动态分层编译（`--no-wasm-dynamic-tiering --no-wasm-lazy-compilation`）：第一次构建快一倍，但编译挪到了启动，整个进程的时间不变，导入器不加。
- **下一步能省的**：物理步进现在在主线程上等着做完（这台机器约 3 ms 一步）；放到工作线程上和渲染上一帧重叠，主线程就省下这段，记进路线图 P6 的"性能"。
- 回归另外固定 4 个工作线程（`?stride-workers=4`），原生内存的预算和机器无关（每个线程 1 MB 的栈算在里面）。

## 2026-11-20 预制体实例：实例就是预制体的根；导入时把 Stride 的实例转成引用

照用户定的格式（prefabs.md）做加载器和导入器。

- **实例就是预制体的根**（prefabs.md 原文"实例自己是预制体的根"）：第一版做成了容器（预制体的根挂在实例下面），转 Stride 的场景时会多出一层父实体，按层级找实体的脚本、实体数都会变，改回原意。实例实体的 id、名字、变换、父实体是自己的，组件是预制体根的加上覆盖；根下面的成员 id 是 `<实例>/<预制体里的 id>`，指向根的引用换成实例的 id。预制体有几个根时（Stride 允许，ParticlesSample 的 PrefabRainbow 有 7 个），一个实例放其中一个（`prefab.root`），同 Stride 把每个根各自放进场景。
- **导入器**：Stride 场景里每个成员带 `Base`（预制体、预制体里的实体、实例）。按实例分组，每个根成一个实例实体（id 照 Stride 的），场景里的值全部当覆盖、和展开的预制体逐项比，相同的去掉（不看 Stride 不可靠的 `*` 标记）；预制体里有、场景里没有的成员记成 `removed`；场景里引用成员的地方跟着换 id。嵌套的预制体先转（连同它成员改了的名）。
- **转完自己核对**：用加载器再展开一遍，和原来展开着的场景逐个实体比，对不上就整个场景照旧展开着存、记进导入警告。所以导入的画面和行为不会变：TPP 的 134 个实例全部转成引用（8 个带覆盖），场景文件 194 → 101 KB，编辑状态的截图和转之前逐像素相同。
- Stride 场景里成员的 `Base` 指着预制体里已经删掉的实体时（CSharpIntermediate 的 DefaultScenery、FPS 的 Stairs1x1x2：预制体后来改过，场景里还留着），这个成员当普通实体，实例照常转：资源编译器照样把它放进游戏，所以画面不变。全部样例重新导入后，没有照旧展开的场景。
- **编辑器里改实例**：界面和视口看到、改的是展开以后的场景（同游戏里的），修改在 `EditorSession.apply` 经 `toDocumentEdit` 换成文档上的——实例自己的名字、变换照常改，成员的值和根的组件成一条覆盖，改回和预制体一样时去掉，所以文件里只留真的差异。考虑过属性面板直接编辑 `prefab.set` 的列表：用的人得知道路径怎么写，不如照常改值。展开时没变的成员、变换、组件沿用上次的对象，拖成员时游戏里只动这个成员的变换。
- **覆盖里的资源路径**：覆盖的值按它的路径放进一个只有这一处的探测实体，照实体的引用规则找（`content/references.ts` 的 visitOverrideReferences），所以资源数据库的引用关系、移动资源时的改写都认得换材质、换模型、脚本属性引用的资源；不用另照字段描述认路径。

## 2026-11-20 GTAO：半分辨率，只乘环境光

P4 屏幕空间效果的第一项（`rendering/AmbientOcclusion.ts`，`stride ao`）。

- **做法**：Jimenez 2016 的 GTAO，参照 XeGTAO：每个像素 2 个切片、每边 6 步找地平线，按投影到切片上的法线积分；法线从深度重建（不要法线缓冲）；噪声开着 TAA 时每帧换；两遍按深度加权的模糊。深度预通道之后、着色之前算，结果放进视图绑定组（第 14 个绑定，没有时是白图），着色器只拿它乘环境光（天空盒的漫反射、镜面和环境光），直射光不乘。只有主画面不透明的阶段用它。
- **和 Stride 不同**：Stride 的 AmbientOcclusion 在后处理里把整个画面乘上遮蔽（`ApplyAmbientOcclusionShader`），太阳照着的地方也变暗。开不开、半径照合成器（`Enabled`、`ParamRadius`），导入器带过来；Stride 的默认是开着的，样例里只有 BepuSample 开着（别的都写了 `Enabled: false`），它重新导入了。画质档位里低档关掉。
- **半分辨率**：全分辨率第一版在 TPP 上 3.4 ms（近处 1 米的半径在画面上有好几百个像素，采样散、缓存命中低）。改成先把深度缩成半分辨率的视图空间位置（2x2 里取最近的），GTAO、模糊都在半分辨率上做，着色时取对应的那一格，半径在画面上最多 96 个（半分辨率的）像素。同一次会话里量：GTAO 0.21 ms、模糊 0.06 ms、缩位置 0.03 ms，整帧 GPU 1.32 → 1.63 ms（这一次笔记本的 GPU 比前几次快得多，整帧只有 1.3 ms，和别的会话的数不能比）。边缘没有看得出的方块和光晕。
- 还没做：用法线缓冲（有了以后比从深度重建准）；弯曲法线、镜面遮蔽按 GTAO 的锥体算（现在镜面也只乘同一个数）；多次反弹的近似。

## 2026-11-20 TAA：先按深度重投影，邻域裁剪压拖影，混合完再锐化

P4 画面功能的第二项（`rendering/TemporalAntialiasing.ts`，`game.graphicsCompositor.temporalAntialiasing`，`stride taa`）。

- **做法**：主画面的投影每帧挪一个亚像素（Halton(2, 3) 的 8 个点，透视和正交都对）；解析的那一遍按深度还原到世界、用上一帧没挪过的视图投影投回去取历史（Catmull-Rom），历史裁进这一帧 3x3 邻域的方差包围盒（YCoCg），在压缩过的颜色空间里混合（历史的权重 0.9）；深度取 3x3 里最近的。历史存两张、轮着读写，存的是没锐化的；锐化（照 CAS 的做法）另一遍，结果交给后处理。画完以后投影放回去，之后画的调试线、场景里的 UI 不抖。
- **和 Stride 不同**：Stride 的 TemporalAntiAliasEffect 要速度缓冲；我们先只按深度重投影，所有内容都能开。Stride 的样例都用 FXAA，所以默认仍是 FXAA（照内容画，现有样例的截图逐像素不变）；开了 TAA，后处理里的 FXAA 就不做。合成器的抗锯齿关着、画质档位不给抗锯齿时 TAA 也不开。
- **量的**（TPP，1280x720，无头 Chrome，不限帧率，两轮一致）：解析 0.85 ms、锐化 0.30 ms，代替 FXAA 的 0.56 ms，整帧 GPU 5.12 → 5.84 ms；两张历史 14.7 MB。静止的画面里桌子、阴影的边比 FXAA 平滑得多。
- **运动向量**（同一天稍后）：第一版只按深度重投影，跑动的角色身上有拖影。加了运动向量的阶段（`RenderStage.velocity`）：不透明的画完以后，网格按深度相等再画一遍（位置和别的阶段同一段代码、`@invariant`），顶点着色器把世界矩阵、蒙皮、形变都按上一帧的再算一次位置，写上一帧的 UV 减这一帧的（rg16float）；没画到的像素（天空、精灵、粒子）清成一个比任何差都大的数，TAA 在那里仍按深度重投影。TAA 取 3x3 里最近的那个像素的运动向量。
  - **上一帧的数据不另建缓冲**：世界矩阵、蒙皮矩阵、形变权重和它们的两张表，各自的缓冲分成两半，每帧轮着写，另一半就是上一帧的；视图常量里给这一帧、上一帧各自的起点。顶点着色器能绑的存储缓冲只有 8 个（WebGPU 的默认上限），已经用了 7 个，另建 5 个放不下；轮着写也不用多传一遍。两张表改了以后两半各写一次。视图常量从 768 字节加到 1024。
  - 量的（TPP，同一次会话）：运动向量这一遍 0.16 ms；开 TAA 整帧 GPU 5.31 → 6.28 ms（解析 0.95、锐化 0.31、运动向量 0.16，省掉 FXAA 的 0.41）。跑动的角色不再拖影；关着 TAA 时截图和改之前逐像素相同。
  - 还没做：网格效果（随时间变的，SpaceEscape 的走廊）按这一帧算上一帧的位置；运动向量的管线没进预热（第一次开 TAA 时当场编）；粒子、精灵没有运动向量。半透明不写深度，按背后的深度重投影，靠邻域裁剪压住。
- 主画面的深度缓冲加了 TEXTURE_BINDING（TAA 读它；之后的 GTAO、SSR 也要）。

## 2026-11-20 阴影图集按用到的大小建

和 Stride 不同：Stride 的阴影图集一上来就是最大的（4096x4096 的 depth32float，64 MB），不管这一帧的阴影图加起来多大。统计量里它是好几个样例贴图的大头。

- 每块阴影图的大小、滤波的纹素数都没变（着色器按图集的实际边长算），所以画面不变：TPP、FirstPersonShooter（四个 xlarge 的级联，本来就把 4096x4096 用满）改前改后的截图逐像素相同。
- 省下的（1280x720）：BepuSample 的贴图总量 119.8 → 55.9 MB，CSharpBeginner 184.8 → 111.3 MB（图集 64 → 16 MB，加上后处理接渲染图省的）。
- 影响到的情况：图集变大的那一帧要重建贴图和绑定组（一次）；最大的图集也放不下时和原来一样，那盏光这一帧没有阴影。

## 2026-11-20 渲染图：通道声明读写，裁掉没用的，临时贴图轮着用；先接后处理

P4 底座的第三块（`rendering/graph/`）。

- **图只管三件事**：通道（`graph.pass(名字, 声明, 执行)`）声明读哪些贴图、整张重写哪些、在哪些上接着画；结果没人用的通道不跑（从后往前看，写的贴图后面没人读、自己又没有图外面看得见的效果的裁掉，它读的东西也就不算有人读）；临时贴图只在第一次用到最后一次用之间占一张真的贴图，描述相同、时间不重叠的共用一张，真的贴图跨帧留在池里（`GraphTexturePool`，闲 30 帧销毁）。
- **不重排**：通道按加进来的顺序跑，读到的是前面的通道写的内容。Frostbite 的做法是每次写都换一个版本号的句柄、按依赖排序；我们的通道本来就是照顺序写下来的，换句柄只会让调用方的代码绕，排序也排不出别的顺序。
- **用错了当场报**：读还没人写过的临时贴图（读到的会是池里上一个用户留下的画面）、在执行时用没声明的贴图，都抛异常，不会悄悄画错。
- **先接的是后处理**。原来的池是"一帧里借出去就不还"：每个中间结果整帧独占一张贴图。现在 `FullscreenShader.draw` 往图里加通道，读写了哪些临时目标从参数里看得出来，各个效果的代码只是把"借一张"换成"要一个这一帧的临时目标"、把贴图的类型放宽成"句柄或者真的贴图"。亮度的测量、最后的色调映射写的是图外面的贴图，算有副作用。
- **结果**（1280x720，编辑状态下等画面稳定后比）：TPP 和 FirstPersonShooter 改之前、改之后的截图逐像素相同（最大差 0）；后处理的中间贴图从 33.8 MB 降到 18 MB，贴图总量 118.9 → 103.1 MB、122.2 → 106.4 MB。4K 下这一项是 9 倍。
- **前向渲染器的一帧也在图上了**（同一天稍后）：阴影、画进渲染目标贴图的相机（深度预通道、着色、拷进贴图）、点选、主画面的深度预通道和着色、后处理，都是 `ForwardRenderer.draw` 里同一张图的通道；HDR 颜色缓冲和渲染目标贴图的相机用的缓冲成了图的临时贴图（原来按尺寸各留一套、不回收）。TPP 一帧 27 个通道，24 张临时贴图实际占 15 张；TPP、FirstPersonShooter、AnimatedModel（两个渲染目标贴图的相机）、SpaceEscape（没有后处理，直接画进后备缓冲）改前改后的截图逐像素相同。通道的名字和裁掉了哪些在 `stride perf` 的 `graph` 里，统计量 `render.passes`、`render.targets`。
- **图在 `draw` 返回之前就执行完**，不是整帧录完再执行。游戏可以重写 `Game.draw`、可以换自己的根渲染器，在场景画完以后接着直接往后备缓冲上画（三个样例这样做）；整帧延后执行的话，它们画的东西会排到场景前面。代价是场景之后画的那几样（场景里的 UI、调试线、画在 UI 上面的粒子、调试文字）不在图里：主画面的深度缓冲因此是一张单独留着的贴图，"后面还有没有人要深度"仍靠前向渲染器自己问（`keepDepth`）。等后面的效果（TAA、GTAO、SSR）要读深度和法线时，它们是场景和后处理之间的通道，在图里。
- **色调映射的亮度图不再跟着输入的贴图**：输入现在是池里的贴图，哪一帧拿到哪一张不保证（两张来回倒的话，按贴图认会每帧重建亮度图、亮度的适应也跟着重置）。亮度图按输入的尺寸建，读输入的那个绑定组按贴图另存。
- 后来补上的：后处理的管线一起预热（见"后处理的管线一起预热"）；绘制次数在设备上数（`DrawCounts`：每个编码器的 beginRenderPass 套一层），所有渲染通道都算，按通道分的用 `stride draws` 看，`render.drawCalls` 是总数（原来只数网格和精灵）。

## 2026-11-20 运动模糊：McGuire 的重建滤波，在 TAA 之后、泛光之前

`rendering/MotionBlur.ts`，`stride blur [on|off] [--shutter] [--maxPixels]`。

## 2026-11-20 屏幕空间反射：Hi-Z 分层步进，用反射换掉环境镜面反射

P4 屏幕空间效果的第二项（`rendering/ScreenSpaceReflections.ts`，`stride ssr`，`--debug hits|reflection` 看命中和反射）。

- **表面**：开着 SSR 时主画面的不透明阶段换成写表面的阶段（`RenderOutput.surfaceFormats`、`SURFACE_FORMATS`）：法线（八面体编码）和粗糙度、环境镜面反射的权重 w（镜面色乘 DFG）、着色时加进去的环境镜面反射 E。同一个渲染通道里的别的特性（背景）的管线也带上这几个目标、写掩码 0（`colorTargets`）；透明的、粒子、线框挪到接着的一遍里，不用都带。
- **合成**：颜色 += 把握 · (w · 反射 - E)。和 Stride 不同：Stride 的 SSLRCombinePass 把反射乘 EnvBRDF 直接加上去，天空盒的镜面反射已经在着色时加过，开了 SSR 的表面整体变亮。
- **追踪**：Hi-Z（最近深度的 mip 链，最粗一级约 8 像素见方）上分层步进（FidelityFX SSSR 的 HierarchicalRaymarch，深度不反转），GGX 可见法线分布随机取方向（Heitz 2018），每帧换；解析时取命中处这一帧的 HDR 颜色，和上一帧的结果按运动向量（TAA 开着时）或深度重投影累积、按 3x3 邻域夹住。Stride 默认是半分辨率定步长 60 步加 4 个解析采样；我们全分辨率、最多 64 步（分层的一步能跨过一大片）。
- **画质档位**：高、极高开，低、中关。
- **空间上复用邻居的光线**（第一版没有，TPP 上一看满是黑点）：随机方向在粗糙表面上命中得稀疏，3x3 邻域经常全没命中，上一帧的结果被夹成 0、累积不起来。改成先做空间解析（同一块表面上周围 8 个像素的光线，半径按粗糙度 1 到 8 像素，按法线、深度挑），再拿它的邻域夹上一帧的结果。简化了 Stachowiak 的 ratio estimator：不按 BRDF/pdf 加权，邻居的命中一样算。
- 画面：BepuSample 的地面粗糙度超过 0.45，默认不做；在 TPP 上把最大粗糙度临时调到 0.6 看，地面靠墙处映出墙（比天空暗）、角色脚下有倒影，开关的差平均每通道约 1/255，差异图平滑。
- 还没做：粗糙表面按锥角取颜色的 mip（现在取命中处的一个像素，靠空间和时间平均）。

## 2026-11-20 管线的预热：模型的管线和资源一起在后台编，建实体之前等它

P4 底座的第二块。管线第一次用到时才建（`createRenderPipeline`），着色器的编译堵在那一帧：TPP 启动后第 4 帧停了 1.02 到 1.07 秒（开发服务器、无头 Chrome，三次）。

- **做法**：加载场景、预制体时，资源预加载完以后（`SceneBuilder.preload` 的最后）把它们的模型要用的管线——每个网格配它的材质，在阴影投射、深度预通道、不透明、透明这些阶段里的——交给 `MeshRenderFeature.warm`，用 `createRenderPipelineAsync` 在后台编，和别的资源一样等它编好再建实体。同一条管线只编一次；编译期间如果已经画到它，照旧当场建一条（结果一样）。场景开不开后处理决定主画面直接画进后备缓冲还是先画进 HDR 缓冲（颜色格式不同、管线不同），预热时按要加载的场景自己的合成器设置选。
- **为什么在建实体之前**：第一版放在建实体之后等，等的那几帧里新旧两个场景的实体同时存在、脚本同时在跑——ParticlesSample 换场景时旧场景的脚本卸载，把新场景刚登记的调试命令注销了。等待只能放在"还没有任何东西进游戏"的阶段。
- **效果**（TPP，同上）：启动后的停顿从 1.02 到 1.07 秒降到 0.37 到 0.40 秒，加载内容的时间从 0.43 到 0.52 秒涨到 0.96 到 1.10 秒（编译挪到了这里，并行编，合计少了约 0.1 秒）。更要紧的是以后：游戏中途加载场景、生成预制体，模型的管线已经在了。
- **剩下的 0.4 秒**是别处当场建的 18 条：后处理 12 条（色调映射、FXAA、泛光、光芒、镜头光晕）、背景 1 条，和加载时一次性的计算（DFG 表、天空盒预滤波、mip 生成）。全屏效果的管线跟着"用到哪些格式、怎么混合"在画的时候才定，要预热得把每个效果画的流程再抄一份清单，容易和实际画的对不上；它们的集合是固定的、只在第一次开后处理时编一次，先不动。等渲染图把各通道的输入输出都声明出来，从图里就能列出所有要用的管线，那时一起预热。
- **看得见**：设备上给管线的创建套了一层计数（`graphicsDevice.pipelines`：当场建的、后台编的各几条，最近当场建的标签），进统计量 `gpu.pipelines.sync`、`gpu.pipelines.warmed`。当场建的条数进回归的基线，不留余量（只让 2 条）：多出来就是有新的管线没预热到。

## 2026-11-20 统计量和预算：game.metrics，显存自己记账，基线进回归

P4 底座的第一块（路线图的原则："每个系统有预算，超了就是 bug；预算和实测值进回归，变慢了要能自动发现"）。

- **`game.metrics`**（`debug/Metrics.ts`）：一个量是名字、单位（个数、字节、毫秒）和一个现读现算的函数，预算是它的上限。读的时候才算（`stride metrics`、回归），平时不花时间。引擎登记了实体数、渲染特性的绘制次数和实例数、显存、原生内存、JS 堆（Chrome 才有）、最近 60 帧的帧时间；游戏和以后的系统（流式加载的池、粒子、音频）接着登记自己的。
- **显存自己记账**（`graphics/GpuMemory.ts`）：浏览器不告诉页面占了多少显存。给设备的 `createBuffer`、`createTexture` 套一层，建的时候按大小加上（贴图算上各级 mip、层数、多重采样、压缩格式的块），`destroy` 的时候减掉，另按标签的第一个词分组（看是谁占的）。引擎里所有资源都经设备建，所以只在一处记。数的是要的大小，不是驱动实际分配的；没调 `destroy`、等垃圾回收的会一直算在里面——那正是该查出来的。
- **基线进回归**（`tools/budgets.json`、`tools/smoke.ts` 的 `finish()`）：每个样例冒烟跑完时的统计量记成基线，回归时不能高出太多（个数 1.5 倍加 16，字节 1.3 倍加 4 MB）。留得宽是因为冒烟跑完时的状态每次略有不同（随机的关卡、还没回收的子弹）；抓的是成倍的退步和泄漏，不是百分之几的波动。只记和机器快慢无关的量；帧时间仍由 `tools/measure.ps1` 和桌面 Stride 同时段比。有意的变化之后用 `STRIDE_UPDATE_BUDGETS=1` 重记。
- 绘制次数现在只数渲染特性（网格、精灵）的，UI、粒子、调试线各自提交的还没并进来；等渲染图把所有通道收到一处时统一数。
- 基线一记就看出两处大头（`graphicsDevice.memory.groups()` 按标签分）：后处理的中间贴图 33.8 MB（Platformer2D 只有几十个精灵，贴图却占 47 MB，就是它加主画面的 10.5 MB），已经用渲染图降到 18 MB；阴影图集原来固定 64 MB（4096x4096 的 depth32float），不管用了多少，已经改成按用到的大小建（见"阴影图集按用到的大小建"）。
- 没做：按画质档位的预算（档位本身还没有）；显存按组的预算；统计量的历史和曲线。

## 2026-11-20 网格的线框：叠在画好的场景上，每个网格一份边的索引

调试视图（`game.graphicsCompositor.wireframe`，`stride wireframe`）。

- **做法**：WebGPU 没有"把三角形画成线"的填充模式。给每个网格建一份边的索引（每个三角形三条边，两个三角形共用的只留一条；第一次画线框时才建），用同样的顶点缓冲和顶点着色器、`line-list` 的管线再画一遍，叠在画好的主画面上。所以蒙皮、形变、位移过的网格线框也是对的。
- **深度**：线和它所在的三角形深度几乎相同，直接比会一段有一段没有。WebGPU 不许给线的管线设深度偏移，所以在片元着色器里把写出去的深度往相机这边挪万分之五再比；线框的管线不写深度缓冲。
- 线是 1 个设备像素宽（WebGPU 的线没有宽度），固定的浅色。只有网格画线框；只叠在主画面上，画进渲染目标贴图的相机不画。
- 考虑过在片元着色器里按重心坐标画边（能控制线宽、抗锯齿）：要每个三角形的三个顶点各带一份重心坐标，带索引的网格得拆开顶点，显存翻几倍，调试视图不值得。
- 没做："只有线框"的视图（不画着色的面）；按物体上色。

## 2026-11-20 属性面板的字段描述：引擎的组件手写、照文件格式的类型核对，脚本的从 prop 来

属性面板要知道一个实体的每种组件有哪些字段、是什么、范围和单位（`editor/fields.ts`）。

- **一个形状，两个来源**。面板只认 `Field`（名字、类型、可不可以不写、默认值、标签）；类型有数、布尔、字符串、枚举、向量、旋转、颜色、资源、实体、列表、对象、按种类分的几种形状之一，和"还没描述、按原样的 JSON 改"。
  - 游戏的脚本：`scriptFields` 从脚本类的 `prop` 声明换过来（范围、步长、单位、标签、分组都带着；transient、sealed、hidden 的不出现）。这是当初设计 `prop` 时说的"一份声明，面板也读它"。
  - 引擎的组件（场景文件 `components` 的各个键）：手写的 `COMPONENT_FIELDS`。场景文件的格式是自己定的一套（不是运行时组件的列：光在文件里按种类分、颜色是 sRGB 的三个数、资源是路径），没法从运行时组件的 `prop` 推出来。
- **手写的不会和格式悄悄对不上**：每张表用 `fields<文件格式的类型>()` 写，类型里有的字段表里必须都有，多一个少一个都过不了类型检查；按种类分的（光、碰撞形状、背景）用 `satisfies Record<种类, …>` 保证种类齐全。另有 `checkFields`、`checkEntity` 照着描述检查一个值，单测拿它把 20 个样例导入的 99 个场景和预制体文件查了一遍，没有对不上的——所以描述和导入器实际写出来的东西是一致的。保存前、读别人写的文件时也用它。
- 考虑过用 `prop` 的 builder 来写文件格式的描述（只有一套声明的办法）：`prop.asset` 只认能加载成对象的那几种资源（文件里还引用天空盒、立方体贴图、贴图文件），颜色只有线性的 RGBA，对实体和资源的引用在脚本属性里是 `{ $entity }`、`{ $asset }`、在组件里是字符串。硬套要给 `prop` 加一堆只有编辑器用的东西，所以另用一个只描述、不参与运行的小类型，脚本那边换算过来。
- 每种组件带一个"添加组件"时放进文件的初始值，单测保证它合自己的描述。
- 没描述的：粒子系统的模块、约束的设置、精灵的贴图（文件或渲染目标两种形状）先按 JSON 改；`loadScene` 的 `scripts` 选项里明说的脚本对应，代理不知道（按类名找）。

## 2026-11-20 编辑器怎么带着游戏跑：游戏页面开在编辑状态，试玩是重新打开页面

前端还没做（等用户定框架），但"编辑器的界面和游戏是什么关系"和框架无关，先定下来、把引擎这一半做了。

- **编辑器的界面是外面的一个页面，把游戏的页面嵌在里面**（同源的 iframe）。游戏页面就是应用自己的 `index.html`，地址带 `?stride-edit`：`Game.run` 看到它（并且打开了 debug，也就是只在开发服务器上）就进编辑状态（`game.editing`）。
- **编辑状态下游戏照自己的入口启动**：建设备、登记脚本、`loadContent` 里加载它的默认场景——只是场景文件里的脚本不挂（`loadScene` 的 `attachScripts` 默认成 false）、仿真不走（`simulation.enabled = false`），然后建编辑器在页面里的代理 `game.editor`（`editor/EditAgent.ts`，动态导入，不进游戏的主包）。应用的代码一行不用为编辑器改：20 个样例各有各的 Game 子类和启动方式，编辑器不用知道。
- **代理做页面里才能做的事**：编辑相机（单独的实体、单独的相机槽位，从场景原来的主相机的位置看起）、让实体跟着场景文档（`open`、`sync`，就是 LiveScene）、点选（返回文档里的实体 id）、选中的框（每帧用 `debugDraw` 画模型的包围盒）、聚焦、操纵器。文档和撤销栈在外面的页面里：代理读文档现在的文件，改的时候调外面给的 `apply`、`commit`（`EditableScene`，`UndoStack` 本身就满足），同源的两个页面之间直接传对象。
- **操纵器（Gizmo）**和编辑相机一样分两层：`TransformGizmo`（`editor/TransformGizmo.ts`）只有几何——把手在哪、鼠标碰到了哪个、拖到这里相当于移了多少、转了多少、放大了几倍——单测直接测；代理的视口脚本每帧喂给它鼠标的射线，把结果换成对文档的修改（每帧一个 `set`，同一次拖用同一个 mergeKey，松手 `commit`，所以一次拖是撤销的一步），用 `debugDraw` 画出来。
  - 把手都是线（轴、面片的边框、圈），碰没碰到在画面上按像素算（离线 8 像素以内，面片是落在里面），所以操纵器在画面上多大、离多远手感都一样；大小按枢轴到相机的距离算，画面上固定是画面高度的 14%。
  - 拖了多少从按下时的枢轴量，不从现在的量：操纵器画在实体上、跟着实体走，从现在的枢轴量会和自己的移动抵消（实测是来回跳）。每个实体的新值从拖之前的样子算，不逐帧累加。
  - 世界里的位移和旋转换回实体的本地值（乘父实体世界矩阵的逆）；选中了父子时只改父实体。缩放总是按实体自己的轴。写进文件的数四舍五入到 1e-6，不留 float32 换算的尾巴。
  - W、E、R 切换移动、旋转、缩放，F 聚焦；左键点选（Ctrl 加选）。和相机的操作（右键、中键、Alt 加左键）不冲突。
  - 没做：吸附的开关（步长的属性有了，没接按键和界面）；旋转的圈侧对着相机时不好抓（没有换成按屏幕拖动的算法）；多选时缩放不绕共同的中心；自由旋转的球、贴着屏幕的平移。
- **试玩是把里面的页面不带 `?stride-edit` 重新打开**：一个干净的游戏，和玩家打开的一模一样；停止是再带着 `?stride-edit` 打开。考虑过在同一个页面里切换（把场景按文档重建一份带脚本的）：切得快，但脚本在试玩里改过的东西（时间缩放、后处理、UI、正在放的声音、不在场景里的实体、游戏子类自己的状态）要一样样复原，漏一样编辑状态就不对；Stride 的 Game Studio 也是另起一个进程跑游戏。重新打开的代价是启动时间（样例 0.3 到 1 秒）；没保存的修改要在试玩里生效，得先保存，或者以后让内容管理器接一层"用编辑器里的版本顶替文件"。
- 在 Chrome 里拿 TPP 验过（`?stride-edit`）：只有编辑器自己的脚本在跑、仿真停着；点角色的胸口选中它（它是 PlayerCharacter 的子实体）；拖 x 轴的把手，文档里的本地位置变了把手那么长的一段，撤销一步回到原值；按 E 拖水平的圈转八分之一圈，转了 46 度。
- 编辑相机接手场景原来的主相机的位置和投影（2D 游戏的相机是正交的）；接手时第一帧还没跑、世界矩阵还没算过，要先算（Platformer2D 进编辑状态时查出来的：相机落在原点，精灵全在近平面以内，画面是空的）。
- 没做：外面的页面（等框架）；多个场景同时打开；子场景（`loadScene` 的 parent）在编辑状态下只是照常加载，不跟文档。

## 2026-11-20 编辑器的后端：工程就是应用目录，内容目录是真相，后端是 Vite 插件

P3 第二步（`packages/editor`）。

- **工程就是应用的目录，清单可以没有**。`stride.project.json` 里只有名字、内容目录、生成的句柄文件三项，都有默认值（package.json 的 name、`public/content`、`src/assets.gen.ts`），所以现有的 20 个样例不加任何文件就是工程。启动场景、渲染设置已经在 GameSettings 资源里，不在清单里重复。
- **内容目录就是资源的真相，不另设一套源格式**。编辑器编辑的就是运行时加载的 JSON（场景、预制体、材质、UI、精灵表……），保存是把它写回去，格式同导入器写的（缩进 1 格；TPP 的场景改了再撤销保存，文件和原来逐字节相同）。这是"场景文件是真相"往下走一步：少一层"源资源编译成运行时资源"，改了马上能加载。考虑过学 Stride 另放一套源资源再编译：好处是源里可以放运行时不要的东西（编辑器的折叠状态、导入设置），代价是每次保存都要编译、两份东西要对齐。运行时不要的东西以后放在旁边的文件里（`.meta` 那样），不混进运行时的 JSON。
  - 代价：从 Stride 导入的样例重新导入会盖掉在编辑器里改的东西（样例的内容目录本来就不提交，只是编辑器的测试数据）；用编辑器做的工程要把内容目录提交进仓库。
  - 模型、贴图这些二进制是导入器的产物。源文件（glTF、PNG）放哪、导入设置记在哪，等做 glTF 导入器时定。
- **后端是开发服务器上的 Vite 插件，不是单独的进程**（`strideEditor()`，`strideApp` 已经带上）。开发服务器本来就在、本来就监视着整个工程目录：HTTP 接口挂在它的中间件上，文件变化用它的监视器，推送走它的 HMR 通道（`server.ws.send`，前端 `import.meta.hot.on`），不加依赖、不多占端口。public 下面的文件变了 Vite 不会刷新页面（它们不在模块图里），所以保存场景不会把编辑器自己刷掉。
- **资源数据库**（`AssetDatabase`）：资源按"种类加内容路径"认，种类看扩展名；字形块算字体的文件。引用关系从引擎的 `content/references.ts` 取——`SceneBuilder.preload`（运行时加载场景前去读哪些文件）也改成从它取，两边不会对不上。启动时全扫一遍（最大的样例 159 个文件、24 MB，连 Node 启动 0.27 秒），之后只重读大小或修改时间变了的文件；自己保存的文件监视器会再报一次，这时什么都不做。
  - 没做持久化的缓存：到内容有几万个文件、每次启动全读一遍太慢的时候，再按"路径、大小、修改时间"存一份（P10 的派生数据缓存是同一类东西）。
  - 资源现在按路径认，没有单独的 id：改名、移动要把引用它的文件一起改（数据库知道是哪些），这个接口还没做。docs/architecture.md 里设想的"句柄的值是资源 id、移动文件记重定向"等做改名时一起定。
- **接口的安全**：接口能写工程里的文件。只答应 Host 是回环地址的请求（挡 DNS 重绑定；Vite 自己的主机检查排在插件的中间件后面，指望不上），带 Origin 的必须和 Host 一致，并且每个请求要带 `x-stride-editor` 头（跨源页面带自定义头要先过预检，这里不回 CORS 头）。路径里不许有 `..`、盘符、反斜杠；只有主文件是 JSON 的种类能经接口读写。写文件是先写临时文件再改名。
- **资源句柄**（`src/assets.gen.ts`，不提交；开发服务器启动和资源增减时重写，内容没变不写）：`assets.<种类>.<目录>.<名字>` 是 `assetRef(种类, 路径)`，引擎加了 `AssetHandle`、`assetRef`、`content.load(handle)`（结果的类型跟着种类），场景的句柄可以直接给 `setRootScene`。句柄带着种类而不是只有一个字符串，是因为要靠它在运行时选加载方式、在类型上选结果。现在类型里只有种类；docs/architecture.md 设想的结构（预制体的组件和部件、模型的材质槽名、场景里导出的实体）等编辑器能编辑这些的时候生成进去。顺手补上了 `AssetTypes` 里漏掉的 `texture`（场景文件早就能引用它）。

## 2026-11-20 场景文档：文件是真相，实体跟着它；不从实体反推文件

路线图里这一项原来写的是"把运行时的实体写回创作格式"。没这么做，改成反过来：编辑器里**场景文件（SceneFile 的 JSON）是真相**，实体是照着它建出来的。

- **为什么不反推**：运行时的实体里资源已经换成了 id、默认值已经合并、脚本运行中改过状态，写回去要么丢信息（哪些值是文件里写的、哪些是默认的），要么把运行时的状态存进文件。Stride、Unity、Godot 的编辑器也都是编辑一份创作数据、运行时照着它建。
- **`SceneDocument`**（`editor/SceneDocument.ts`）：不可变的文件加三种修改——改一个实体里某条路径上的值（`set`）、加实体（`add`）、删实体（`remove`），`batch` 把几个并成一个。`apply` 返回撤回它的修改，`UndoStack` 记着这些逆操作；连着拖同一个值时给同一个 `mergeKey` 并成一步，松手 `commit`。预制体文件也是一列实体，用同一个类。保存是 `JSON.stringify(document.file, null, 1)`，和导入器写的一样（写文件是 Node 后端的事）。
  - 换父实体不是单独的修改：文件里父实体必须排在子实体前面，换父实体是"删了再加在别处"的一个 `batch`，运行时这边看到的是同一个 id 的实体父实体变了，实体不重建。
  - 列表（脚本、材质槽）只能在末尾加一项、去掉最后一项，别的改法把整个列表设成新的：去掉中间一项会让后面的下标都变，逆操作就不是"设回原来的值"了。
  - `add`、`remove` 一次可以带很多个实体（一棵子树、一次粘贴），不管带多少个都只扫一遍实体列表。量过十万个实体的文档（Node）：拖着改一个值每帧 0.7 ms（拷一遍列表的引用加比较），删、撤销一棵一万个实体的子树各 21 ms。最初的写法一次只删一个，每删一个扫一遍，是它的几百倍。
- **`LiveScene`**（`editor/LiveScene.ts`）加 `ContentManager.updateScene`：文档改了以后调 `sync`，比较两个版本的实体列表里对象的引用（`changedEntities`；不加不删时两边一一对应，扫一遍就完，不建表），只动变了的实体：名字、位置、父实体直接改；组件按种类（`components` 的键）比较引用，只重建变了的那几种——去掉旧的、按新的值加上。实体还是原来的实体，选中的东西、别的实体对它的引用都不用换。要用的新资源先加载好，再一口气改完，不会画出改了一半的场景。
  - 考虑过整个实体销毁重建：简单，但实体的 id 会变，引用它的实体（实例的主实体、挂到骨骼节点的目标、约束）要跟着重建，子实体还得先挪走。也考虑过每个实体的组件全部重建：改灯的强度会让同一个实体上的动画、粒子、物体从头来。
  - 为了按种类去掉，`SceneBuilder`（从 ContentManager 里拆出来的"实体文件建成实体"）里每种组件有一对"怎么加、怎么去掉"（`BUILDERS`）。物理组件去掉时连 `PhysicsBody` 一起去掉：仿真要到下一帧才清没主的物体，不去掉的话马上加回来的组件会接着用旧的形状。
- **编辑状态不挂场景文件里的脚本**（`LoadSceneOptions.attachScripts: false`，同 Stride Game Studio）；试玩时另按文档建一份带脚本的。`Game.loadScene`、`setRootScene` 可以直接给场景文件（不经内容路径）。编辑器自己的相机不放进场景：单独建一个实体，相机用别的槽位，`graphicsCompositor.cameraSlot` 指过去。
- 在 Chrome 里拿 TPP 的场景（278 个实体）验过：按文档打开 9 ms（资源已经在缓存里），拖一个实体每帧 0.02 到 0.06 ms，改方向光的颜色 0.2 ms，改模型的投影设置（模型、骨架、蒙皮重建）0.6 ms；删两面墙（各 17 个实体）、加一盏灯再全部撤销，画面和重新打开的逐像素比最大差 1 级（自动曝光的收敛）。
- 没做：场景自己的设置（偏移、仿真、导航、合成器）改了不会跟上，要重新打开；兄弟实体的顺序运行时不跟文档对齐（没有东西依赖它）；编辑状态下仿真不走，约束连着的物体重建以后约束不会重连（试玩是重新建的，不受影响）；重建物理组件时旧的 Collider 没有释放（和场景卸载一样，等内容的引用计数）。一个实体里的值按 JSON 整个替换，没有按 `prop` 的 schema 校验，属性面板做的时候在那边按 schema 生成修改。

## 2026-11-20 编辑相机：状态和输入分开，视角读相机组件

编辑器视口的相机（`editor/EditorCamera.ts`）。

- **两层**：`EditorCameraState` 只有注视点、偏航、俯仰、距离和它们的算术（环绕、转头、平移、飞、推拉、聚焦），不碰输入和实体，单测直接测、编辑器的"聚焦到选中的东西"和以后的过渡动画也直接驱动它；`EditorCameraController` 是挂在相机实体上的脚本，每帧读输入、改状态、写回 Transform。
- **操作**照 Stride Game Studio 和常见的 DCC 工具：右键拖转头（眼睛不动），这时 WASD 飞、Q/E 降升、Shift 加速；中键拖平移；Alt 加左键绕注视点转；滚轮推拉。平移是"画面跟着手走"：拖的像素按注视点那个深度换成世界单位；推拉每格把距离乘 0.85，离得越近走得越慢，到不了注视点上。
- **视角不重复存一份**：平移、聚焦要用的竖直视角从同一个实体的 `Camera` 组件读（没有时按 45 度），正交相机用 `orthographicSize`，滚轮和聚焦改的也是它。
- 没做：相机有父实体时写回的是本地位姿（编辑器的相机没有父实体）；飞行的速度不随场景大小自动调；视图方向的快捷键（前、顶、侧）等前端做的时候加。

## 2026-11-20 点选：在 GPU 上画编号，读回一个像素

编辑器的视口要"点一下选中物体"（`game.pick(x, y)`，`rendering/ScenePicker.ts`，调试 CLI 的 `stride pick`）。

- **做法**：把主相机看到的网格再画一遍，颜色写实例的变换槽位加一（r32uint），裁剪矩形只留被点的那一个像素，把那 4 个字节拷进缓冲读回，槽位再换回实体（`entityAtSlot`）。用的是这一帧已经剔除、上传好的实例，不重新收集。
- **为什么不在 CPU 上拿射线和三角形求交**：蒙皮、形变目标、位移贴图、网格效果里改的顶点位置、Alpha 裁剪都在着色器里，CPU 上要原样再实现一遍才能点得准；画编号则"画出来什么样，点到的就是什么样"。只画一个像素，开销就是一遍顶点着色加一次很小的读回。物理的射线（`simulation.rayCast`）只认有碰撞体的东西，编辑器里大部分物体没有。
- **代价**：结果是异步的（这一帧画、下一帧开头才能映射缓冲），`pick` 返回 Promise；编号缓冲和它的深度缓冲和画布一样大（各 4 字节每像素），第一次点选时才建。
- 透明的物体也点得到（编号的阶段透明、不透明的都画，按深度取最前面的）；Alpha 裁剪掉的像素点不到。模型多出来的网格在子实体上，`game.pick` 把它们算成模型所在的实体。
- 精灵也点得到（2026-11-20：精灵的特性多一条写编号的管线，贴图上差不多全透明的地方点不到、会点到后面的）。
- 还没做：粒子、放在场景里的 UI 点不到（特性里 `supportsPicking` 是 false）；框选（读一块矩形）；编辑器里要"点第二次选后面的那个"时得把最前面的排除掉再画一遍。

## 2026-11-20 调试渲染：game.debugDraw 画解析的抗锯齿线

P3 第一步里"运行时这边编辑器要用的"一项（从 P1 挪来的调试渲染）：`debug/DebugDraw.ts` 攒线，`debug/DebugDrawRenderer.ts` 画。

- **立即模式**：`game.debugDraw.line / polyline / bounds / box / circle / sphere / capsule / cylinder / arrow / axes / frustum / grid`，默认只画这一帧（下一次 update 开始时清掉，暂停时留着），给 `duration` 的留那么多秒。形状都拆成线段。选它是因为调用的一方（脚本、编辑器的 Gizmo、物理的显示）不用管理对象的生命期；代价是每帧重新提交，线很多（上万条）又不变的东西（大网格的线框）以后要另给"留着"的句柄。
- **怎么画**：每条线一个四边形，顶点着色器里在屏幕上沿线的法线撑开成固定的像素宽度（CSS 像素换成整数个设备像素），片元着色器按到线段的距离算覆盖率，两头是圆的，所以折线的拐角是接上的。不用 WebGPU 的 line-list（只有 1 像素宽、没有抗锯齿）。一头在近平面后面的线先裁到近平面上。
- **深度**：默认和场景比深度，读主画面的深度缓冲（只读；有这种线时前向渲染器把深度留着），`depthTest: false` 的画在最上面。线的深度按"往相机挪 0.2% 的距离"算（位置不动）：贴在表面上的线（地面的网格、包围盒的棱）不会和表面打架。
- **画在哪**：场景和后处理之后、UI 之前，直接画到后备缓冲——调试的线不该被色调映射、泛光改掉颜色。只画主相机的视图。
- **没变就不做**：线没变（`version` 没动）不重新上传；一条线都没有时不开这一遍。
- **物理形状**（`physics/debugShapes.ts`，`simulation.showColliders`）：盒子、球、胶囊、圆柱照形状画（不跟实体的缩放，同物理），网格画三角形的边（共用的边去重，按网格缓存）。凸包画的是给它出顶点的那些网格的边：凸包的面在原生那边，TS 这里没有；要看真正的外壳得从原生把面取回来，等用到再做。
- 颜色按 sRGB 给（同 UI），存的时候换成线性。

还没做的：线框模式的网格（要逐三角形的重心坐标或者几何着色的替代），虚线，按世界单位给的线宽，画进渲染目标贴图的相机。

## 2026-11-20 P2 验收时的帧时间：两处优化，和一个比错了的教训

**教训**：第一轮把当天测的 stride-ts 帧时间去比各 README 里以前记的桌面数字，得出"五个样例比桌面慢"（UIElementLink 2.15 倍）。查到一半才把桌面版也重跑：桌面当天是 4.42 ms，不是记录里的 1.24 ms。路线图的验收写的就是"同一台机器、同一时段"；以后测帧时间，两边在同一轮里都跑（`tools/measure.ps1` 之前先把各截图工程的 `--benchmark` 跑一遍），README 里的旧数字只当历史。

查的过程里找到两处真的浪费，都修了（画面不变，截图比对的数字和改之前一样）：

- **网格的着色器给每个像素算用不到的东西**。着色器是一份通吃的：没有贴图的槽绑白图照样采样（漫反射、法线、自发光、遮蔽、光泽度）、天空盒强度是 0 也算球谐和采样立方体贴图、不是玻璃也算薄玻璃的菲涅耳（三次 pow，分段截断量出来是最贵的一段）。功能一个个加上去，每个像素的开销跟着涨，SpaceEscape（只有漫反射贴图加一盏方向光）从 0.78 ms 涨到了 1.40 ms。现在按 uniform 里的标志跳过：条件只依赖 uniform，在 WGSL 里是一致的控制流，里面可以用 textureSample；不用为每种组合编一个着色器。SpaceEscape 回到 1.06 ms。
- **深度预通道之后的不透明阶段**只比较深度相等、不再写深度（`RenderStage.afterDepthPrepass`）：预通道和它画的是同一批物体、同一个顶点着色器（位置是 `@invariant` 的），被挡住的像素一个都不着色。
- **没有后处理时直接画进后备缓冲**（同 Stride：合成器的 PostEffects 是 null 时前向渲染器直接画到输出上），省掉 HDR 缓冲和把它拷过去的一遍；没有网格的画面（纯 2D）不开深度预通道。JumpyJet 0.74 → 0.50 ms。超过 1 的颜色现在在写进后备缓冲时截断（以前是混合完、拷贝时截断），透明物体盖在很亮的表面上时结果会差一点，和 Stride 一致。
- 定位的办法值得记：在着色函数里分几处插"条件恒真的提前返回"（条件写成读一个 uniform，编译器删不掉后面的代码），看 GPU 时间戳里这一遍的耗时在哪一段涨，比猜快得多。

最后的结果（表在 progress-log.md）：20 个样例是桌面的 0.52 到 1.12 倍。三个最轻的 2D 样例（SimpleAudio、SpriteFonts、CustomEffect）高 0.03 到 0.05 ms：它们一帧里我们自己的 JS 和 GPU 加起来不到 0.2 ms，剩下的是浏览器的帧循环（rAF、提交、呈现），在每秒 2000 帧这个量级上才看得出来。能再省的是"只有 UI 的帧把清屏和 UI 合成一遍画"，没做。

## 2026-11-20 渲染组和渲染掩码（模型、UI、相机）

Stride 的 RenderGroup（组件属于 32 个组里的一个）和 RenderGroupMask（相机渲染器的 RenderMask：这台相机画哪些组）。样例的合成器掩码都是 All，所以以前忽略、导入时报警告；编辑器要靠它把辅助图形和游戏的东西分开（P3），先把通路做出来：

- `Model.renderGroup`（0 到 31）进批次的键：同网格、同材质但组不同的实例分成不同的批，画的时候整批按视图的掩码跳过（`RenderView.cullingMask`、`inRenderMask`）。没有改原生的剔除：按批跳过不用逐个实例判断；被掩掉的批照样剔除了一遍，白做的这点功等掩码真的用起来再看。
- 合成器里相机渲染器的 `RenderMask` 导入成 `renderMask`（主画面和画进渲染目标贴图的相机各有各的），全部时不写。
- `UIComponent.renderGroup`：主画面的掩码里没有这一组时这个 UI 不画（全屏的和放在场景里的都是）。Stride 还能用 RenderStageSelector 把某个组的 UI 分到别的渲染阶段（AnimatedModel 把 Group1 的 UI 放到后处理之后画），我们的 UI 本来就都在后处理之后画，这一层不用做。
- 还没做：精灵、粒子、背景的渲染组（组件上有这个属性，样例里只有 UIParticles 的粒子用了 Group1，已经由"粒子画在 UI 上面"处理）；阴影视图用的是全部的组。

## 2026-11-20 字形块的文件：点是字体网格上的 16 位整数、存差分，带存成 16 位

P2 记下的遗留项"点存成 f16"。量了一下 SpriteFonts 导入出来的字形块：531 个文件 128.6 MB，点（f32）占一半、带的索引（u32）占 47%、字形记录 3%。改了文件格式（`GLYPHS_VERSION` 2）：原始大小 128.6 → 66.2 MB（GameMenu 的 115.4 → 59.2 MB），brotli 以后抽样的 40 块 0.90 → 0.69 MB（小 23%）。下载的是压缩以后的，所以按压缩后的大小选的编码：

- **第一版是"每个字形一个包围框，框里量化成 16 位"**：原始大小也减半，但 brotli 以后反而大了 12%。f32 的坐标是"整数个字体单位除以 em"，不同的字里相同的坐标是相同的字节，压缩器吃得到；换成各自框里的相对值，这层重复就没了。
- **现在是字体网格上的整数**：步长取字体网格的四分之一（1 / (4 · unitsPerEm)），TrueType 的点（整数单位）和隐含的中点（半个单位）正好在网格上，没有损失；三次曲线转出来的点对齐到网格，差不到 1/8 个字体单位。坐标大到 16 位放不下的字体，整个字体换粗一倍的网格（编码时放不下会报错，不悄悄截断）。
- **存差分，x 和 y 分开放**：每个点存和同一个字形里前一个点的差（轮廓上相邻的点离得近，差都是小数），抽样比不差分小 20%。差按 16 位回绕着存。
- **带的字存成 16 位**：带头和曲线表里的数都相对这个字形，不会超过 65535。
- **只改了文件，运行时不变**：读进来还原成 f32 的点和 u32 的带，着色器和显存里的格式照旧。
- **分带之前先对齐**：管线把曲线对齐到网格再分带（`snapGlyphPoints`）。对齐以后才变成水平或竖直的线，要按水平、竖直的处理（不进和它平行的带），否则着色器里和平行的射线求交会除以 0。
- **还能再小的**：压缩以后带占 43%（点 49%）。带可以不存、加载时从点重建（分带是确定的算法），下载量能再少四成；代价是每块加载时多十几毫秒的计算，要放进 wasm 或者分帧做才不卡。没做，等字体的下载量成问题（大段中日文）再定。
- 文件格式变了，旧的内容读不了（报版本不对），所有样例重新导入过。

## 2026-11-20 导入警告清查：材质层的遮蔽；渲染器属性里的渲染阶段

把所有样例重新导入、收集警告（路线图 15.5），真有内容用到的两处补上：

- **材质层的环境光遮蔽**（层的 Occlusion 特性）：层文件多一项 `occlusion`（AmbientOcclusionMap 的标量树、DirectLightingFactor），着色器里和别的属性一样 `mix(下面的, 这层的, 遮罩)`——Stride 的层就是把每个流按遮罩线性混。底下没有遮蔽时从"遮蔽 1、直射光不受影响"往上混。层的 cavity 没做：没有贴图、后备值是 1 的 cavity 本来不起作用（样例里都是这样），不报警告；别的情况照旧报。PhysicsSample 重新导入后和桌面比是 1.02、0.38、0.96，和以前持平：这几个材质的遮蔽只影响环境光（DirectLightingFactor 是 0），量很小。
- **游戏自己的渲染器引用渲染阶段**（JumpyJetRenderer 的 OpaqueRenderStage、TransparentRenderStage）：这些属性引用的是合成器的 RenderStages，不是实体。现在导出成阶段的名字（`'Opaque'`、`'Transparent'`），TS 的渲染器要用时按名字找。没有做成专门的引用类型：我们的阶段本来就按名字取，多一种引用类型只多一层解析。

没补的：UI 的渲染组等渲染掩码（P3）；没有样例触发的警告留着（清单在路线图 15.5），等有内容用到再做——凭空实现没法和桌面版对。

## 2026-11-20 法线用世界矩阵的逆转置变换

以前顶点着色器里法线直接乘世界矩阵（注释里写着"非均匀缩放要用逆转置，等材质系统一起做"，一直没做）。缩放不等比的物体上，斜着的法线会歪向缩放大的那个轴，光照就错了；样例里第一个碰到的是 CSharpIntermediate 的 SceneB（拱的缩放是 1.68、1、1.99），拱顶两肩比桌面亮 12/255，查了两轮才想到是它。

- 现在用余子式矩阵（世界矩阵左上 3×3 的三列两两叉乘）：它等于逆转置乘行列式，长度在片元着色器里本来就要归一，所以不用真的求逆；每个顶点多三次叉乘。行列式是负的（镜像）时方向反回来。
- 切线照旧乘世界矩阵（切线是表面上的方向，本来就该这样变换），副切线仍由法线叉切线得出。
- 蒙皮矩阵那一步还是直接乘（骨骼带不等比缩放的情况样例里没有，Stride 那边也是直接乘）。
- 教训：比对时某块差"只在斜面上有、轴向的面上没有"，先看物体的缩放。

## 2026-11-20 影子 DOM：全屏 UI 的文字和控件在页面上有透明的节点

路线图"画在 canvas 里的东西也要有 Web 原生的能力"的那一层（`ui/semantics.ts` 算语义树，`ui/SemanticsLayer.ts` 同步到 DOM，`game.ui.semantics`）。输入框早就有自己的影子输入框（`TextInputBridge`），这次补的是其余的：

- **节点**：每段文字一个节点（一行一个 span），按钮是真的 `<button>`，开关按钮是 `role=checkbox`（不确定是 `aria-checked=mixed`），滑条 `role=slider`（方向键、Home、End 调值），输入框 `role=textbox`（走到它上面就开始编辑，真的输入框接手），ModalElement `role=dialog`，滚动的文字 `role=marquee`（内容是整段，不是这一帧露出来的几个字）。名字取 `accessibleLabel`（新加的属性），没设时按钮用它里面的文字、别的用 `name`。
- **平的一列，不嵌套**：节点按树的顺序排（也就是阅读和 Tab 的顺序），各自按世界矩阵用 CSS 的 `matrix()` 摆。按钮里的文字节点 `aria-hidden`（按钮的名字里已经有了，不读两遍），查找和复制仍然找得到。嵌套的话每个节点要换算到父节点的坐标里，换来的只是"名字从内容里算"，不值。
- **模态的弹窗**：最上面那个模态弹窗以外的节点设 `inert`——读不到、Tab 走不到、不能操作，和指针点不到它们一样。不这样的话键盘能绕过弹窗去按后面的按钮。
- **Tab 的顺序**：就是节点在 DOM 里的顺序。正在编辑的输入框是 `TextInputBridge` 的 `<textarea>`，不在这一层里，浏览器自己的顺序接不上（实测会跳出界面、再按又回到输入框，永远到不了后面的按钮），所以输入框里按 Tab 由我们结束编辑、把焦点交给下一个节点（`SemanticsLayer.focusNext`）。
- **透明而不是 opacity 0**：颜色、背景透明，这样 Tab 走到控件上时浏览器画的焦点框看得见，位置就是画面上控件的位置。
- **默认不接指针**（`pointer-events: none`）：鼠标照常落到画布上，游戏和 UI 的输入不受影响。读屏软件的"点击"、键盘的 Enter 和空格是 DOM 的 click 事件，转成 `ButtonBase.performClick()`；这些键不再传给游戏（空格常是跳）。
- **选中文字**：全选、查找、读屏对所有文字都有效；用鼠标拖着选要给 TextBlock 开 `isSelectable`（开了以后鼠标落在这段文字上归浏览器，不再是游戏的输入，所以默认关，同 Flutter 的 SelectableText）。选区的底色由我们的渲染器照自己的排版画（`SemanticsLayer.selectionOf` 读页面的 Selection），浏览器自己的选区底色关掉——页面上没有游戏的字体，浏览器排出来的字和画面对不齐。
- **文字的宽度**：照 PDF.js 的文字层，每行按我们量出来的宽度横向拉伸（`scaleX`），行的起止和画面一致；行内每个字的位置只是近似。
- **没变就不动**：最多每 0.1 秒同步一次（`updateInterval`），每次把语义树和上一次的逐个比（`semanticsKey`），变了的节点才写 DOM。没有逐帧做是因为要把整棵 UI 走一遍——元素的属性大多是普通字段，没有"变了"的信号；等 UI 的分层缓存做了，改成只在脏的时候同步。
- **在 Chrome 里验过的**（GameMenu）：无障碍树里有全部文字、按钮（名字取自里面的文字）、输入框、对话框；弹窗开着时后面的按钮是 inert，关掉后恢复；只用键盘 Tab、Tab、Tab、Enter 能从输入框走到按钮并关掉弹窗，焦点框画在按钮的位置上；开了 `isSelectable` 的两行文字用鼠标拖选，页面的选区文字和我们画的高亮一致。
- **还没做的**：放在 3D 场景里的 UI 不进影子 DOM（路线图说默认不进、可以按元素打开，打开的那部分还没做，要把投影换成 CSS 的 `matrix3d`）；图片没有节点（`role=img`，要有 `accessibleLabel` 才有意义）；ScrollViewer 没有对应的滚动区域，读屏软件把焦点移到滚出去的控件上时不会自动滚过来。
- **用户的偏好**（`game.userPreferences`）：`reducedMotion`、`highContrast`、`colorScheme`，读的是媒体查询的当前值。引擎自己还没有哪里照着它们改行为，留给游戏用。浏览器的缩放本来就跟着（后备缓冲每帧按 `devicePixelRatio` 调，文字是矢量的）。

## 2026-11-20 文字的描边按到轮廓的距离画；键盘事件发给有焦点的元素

**描边**（TextBlock 的 `outlineColor`、`outlineThickness`，ScrollingText 也有）。Stride 把整段文字往八个方向各偏移 thickness 再画一遍，垫在字下面：九倍的字形、描边比笔画粗时八个影子分开露出来、角是方的。我们的字本来就是按轮廓逐像素算的（Slug），所以描边在同一个着色器里算"这个像素到字形轮廓的距离"，不到半径的涂上描边色，边上按距离过渡一个像素：

- 一个字多画一项（字形的矩形向外扩半径），粗细不限，角是圆的，放大缩小、放进 3D 里都一样清楚。
- 距离怎么找：字形的曲线本来按横带、竖带分好了（数穿越用的），找距离时看采样点上下 radius 以内的横带；横带里没有横的直线（和带平行的不参与数穿越），再到竖带里找它们。每条曲线上最近的点用牛顿法（从投到弦上的位置起步，四次）：闭式解要解三次方程，在接近直线的曲线上单精度不够用。
- 整段文字的描边先画完再画字，相邻的字的描边不会盖住前一个字。
- 没解决的：半透明的描边在相邻两个字的描边重叠的地方会深一些（各画各的、叠了两层）。Stride 的八遍叠得更厉害。要完全均匀得先把整段描边画到一层上再合成，等 UI 的分层缓存做了再说。
- 只有 `SpriteBatch.drawText`（UI 用的）有描边；`drawString`（照 Stride 的 SpriteBatch.DrawString）没加，Stride 那边也没有。

**键盘事件**（`UIElement.keyPressedEvent`、`keyDownEvent`、`keyReleasedEvent`、`textInputEvent`，冒泡）：照 Stride 发给 `game.ui.focusedElement`。焦点可以给任何元素（用方向键选菜单项这类），它占着键盘，脚本读不到按键，UI 读的是不管占用的原始状态（`input.rawKeys`、`input.rawTextInput`）。

- 和 Stride 不同：这一帧有文字输入时 Stride 不发 KeyPressed、KeyReleased（松开的事件会丢），我们照发。
- 和 Stride 不同：TextInput 只有键盘直接打出来的字（keydown 的 `key`），没有输入法拼字的过程。浏览器里要输入法就得有一个拿着焦点的 DOM 输入框，手机上它一拿焦点就弹出软键盘——给菜单项焦点不该弹键盘。要输入法的地方用 EditText（它后面有输入框）。
- 键名是 `KeyboardEvent.code`（同 InputManager），`args.isKeyDown('LeftShift')` 也认 Stride 的键名。

## 2026-11-20 UI 控件补齐：开关按钮、图片按钮、滚动文字

Stride 能写进 .sduipage 的元素类型我们都有了（`UIElementType` 和运行时的类型表是同一份清单，少一个就编不过）：这次补上 ToggleButton、ImageButton、ScrollingText、ContentPresenter，页面里单独放的 ScrollBar 也认。样例的页面没有用到它们，在 GameMenu 的页面上用代码加了一组、在 Chrome 里点过看过。

- **ToggleButton** 照 Stride：三个状态各一张图（可另给悬停时的图），点一下换状态并发 Checked、Indeterminate、Unchecked。状态的名字照 Stride 的枚举写成 `'checked' | 'unChecked' | 'indeterminate'`（导入器把枚举值的首字母改小写，页面文件里就是这三个）。
- **ImageButton**、**ContentPresenter** 在 Stride 里已经标了过时（分别建议用 Button 的三张图、ContentDecorator），为了老页面能照常导入才有；新写的不用。
- **ScrollingText** 和 Stride 不同的两处：
  - 滚出左边的字从要画的那串里去掉。Stride 去字的循环条件写反了，从不去字，重复滚动时那串字一直变长（每帧量一遍越来越长的字符串）、偏移一直变负。
  - 不重复的文字全滚出去以后，`appendText` 接上的字从右边进来。Stride 把它们接在早已滚出去的那串后面，要等新接的字比空出来的那段还长才看得见。
  - 没改的：文字改了会让布局失效一次（大小其实只看 `desiredCharacterNumber`）；滚动是每帧在 CPU 上挪偏移、重画这一个元素，UI 的缓存做了以后（路线图"没变就不做"）它应该只让自己那一层重画。

## 2026-11-20 透明实例逐个从远到近画

以前透明阶段按批排（看每批第一个实例到相机的距离），同一批里的实例不排、不同批的实例不能交错；重叠的半透明物体混合的先后会错。Stride 把透明的渲染节点逐个排。

- 实例按批存在实例缓冲里，所以分两步（`rendering/transparentOrder.ts`）：剔除之后、上传之前，透明的批在每个视图里把自己可见的实例按距离排好；画的时候把各批的实例按距离归并成一段一段，同一批里连着的几个一次画完（`firstInstance` 指到那一段），不同批的交错着画。
- 只有透明的批（和要在透明阶段叠清漆的批）做这件事；阴影视图不画透明的东西，跳过。排序在 CPU 上、每帧做，透明的实例通常很少；多了以后（成千上万）要换成按深度分桶，到时候再量。
- 距离取物体原点到相机的距离（Stride 取包围盒中心在视图空间的深度）。两种在大物体互相穿插时都会错，要彻底对得上只有顺序无关的透明（P4）。

## 2026-11-20 手势识别（Input.Gestures）

Stride 的 `Input.Gestures`、`Input.GestureEvents`：SpaceEscape 用拖动手势换道，我们移植时在脚本里用指针事件自己判。

- **照 Stride.Input 的 Gestures 移植**（`input/gestures.ts`）：点（可以多指、多次）、长按、拖动、轻扫、双指的组合（平移、旋转、缩放）五种，状态机、默认值、阈值都照各个 `GestureRecognizer`；位置归一化，量距离时按屏幕宽高比把短边换到长边的尺度。`game.input.gestures.add(Gestures.drag(…))` 加配置，每帧读 `game.input.gestureEvents`。
- 和 Stride 不同：配置是不可变的普通对象（`Gestures.tap({ requiredNumberOfTaps: 2 })`），不是 new 出来改属性、加进集合后冻结；事件是按 `type` 区分的联合类型，不用强转；时间用秒。
- 和 Stride 不同：被 UI 占用的指针不参与手势（Stride 的手势看所有指针事件，点按钮的同时也会触发游戏里的点手势）。
- SpaceEscape 的 CharacterScript 换回手势的写法；冒烟加了"往右划换道"。TouchInputs 样例（专门演示手势）还没移植，记在路线图里。

## 2026-11-20 用代码建的动画剪辑（属性曲线）

Stride 的 `AnimationClip.AddCurve` 可以给任意属性加曲线；ParticlesSample 的 RotationScript 用它让环转起来，我们以前只有骨骼动画，移植时改成了按时间算角度。

- **写法**：`AnimationClip.fromCurves(name, 秒, [propertyCurve(Transform, 'rotation', [[时刻, 值], …], 'linear')], repeatMode)`，由 `AnimationComponent` 照常播放、淡入淡出、混合。
  - 和 Stride 不同：目标写组件类型加属性名（编译期检查属性存在、值的形状对），不是 `"[TransformComponent.Key].Rotation"` 这样运行时才解析的字符串路径。
  - 和 Stride 不同：四元数的三次插值 Stride 没实现（抛 `NotImplementedException`），我们按分量做同样的 Catmull-Rom 再归一化。
- **插值**照 Stride：常量取前一个关键帧，线性（四元数走球面最短的弧），三次是过四个点的 Catmull-Rom（两头用端点补）。
- **混合**：属性曲线是混合栈的第三部分（骨架的姿势在原生侧，形变权重、属性曲线在 TS 侧），同样的压栈、混合、叠加；只有一边有的属性取那一边，没有曲线的属性不动。
- **谁能播**：没有模型的实体（灯、相机、空实体）也能播——播带曲线的剪辑时实体被打上 `PropertyAnimated` 的记号，动画系统按它找。带骨架的模型也能叠播没有骨架轨道的剪辑（以前报错）：它不往原生的栈里压姿势，合并时只有一边有姿势就留那一边。
- 现在只能驱动数据组件的数、向量、四元数、颜色属性；脚本的属性、材质参数以后有需要再加（Stride 的字符串路径能指到任何可序列化的成员）。

## 2026-11-20 点光、聚光的阴影

CSharpIntermediate 的 SceneB 有一盏投阴影的点光，以前导入时报警告、不投阴影。

- **照 Stride 的做法**：点光是立方体的六个面各一个透视视图（`LightPointShadowMapRendererCubeMap`：视场角比 90° 大 8 像素的边，近平面 0.1，远平面是半径的两倍，按近、远平面裁剪），着色时按到光源的方向里最长的轴选面、深度按沿这个轴的距离算；聚光是一个透视视图（`LightSpotShadowMapRenderer`：按光源的世界矩阵摆，视场角是外锥的全角，近平面 0.01，远平面是射程的两倍）。每块的大小按光源在画面上盖住多大定。和方向光的级联共用一张图集、同一套滤波。
- **图集按矩形分配**（`GuillotinePacker`，照 Stride 的同名类）：以前只会把级联排成格子。每帧清空重排。
- **不给盏数、视图数设上限**：每盏光的阴影数据放存储缓冲（按需变长），每个视图的常量缓冲按需变长（以前最多 8 个视图，一盏点光就要 6 个）。上限只有图集的面积。
- 和 Stride 不同：Stride 的点光还可以选抛物面的画法（`LightPointShadowMapType.DualParaboloid`，两张图），我们都按立方体画——抛物面只是省图集面积的近似，边上有变形，没有样例用。
- 和 Stride 一样、以后要改的：图集放不下的光这一帧没有阴影（Stride 也是；光多的场景要按重要程度缩小或者轮流更新，P4 做阴影缓存时一起）。
- 验证：SceneB 停住仿真和桌面比，平均每通道差 1.23；阴影的形状、两个球投在拱顶和柱子上的影子都对得上。剩下的差在拱顶内侧的两边（我们亮 12/255 左右），关掉这盏灯的阴影两边再比还在，是这个模型上点光的光照本身的差，和阴影无关；原因没查清（不是法线，见路线图第 15.5 项）。

## 2026-11-19 导入的派生数据缓存

贴图编成 KTX2 是导入里最慢的一步，同一张贴图每次导入、每个用到它的样例都重编一遍（CSharpIntermediate 一次三分钟，全部样例重导十几分钟）。加了 `DerivedDataCache`（`packages/pipeline/src/cache.ts`）：键是"做法的名字和版本、像素、尺寸、选项"的 SHA-256，值存在 `~/.stride-ts/cache/pipeline`，各样例、各工作树共用；命令行默认打开，`--no-cache` 关掉；库里默认不缓存（测试不往用户目录写）。

- 按内容寻址：不会用到过期的结果，目录只增不减，随时可以整个删掉。换编码器或参数的含义时改做法的版本号（`BASIS_RECIPE`）。
- 现在只缓存贴图编码。别的步骤都在秒以内；团队共享的缓存（路线图 P10）到时在这个接口后面加一层远端。

## 2026-11-19 CSharpIntermediate：声音的发射器和听者；只改朝向；相机教程里 Stride 的毛病

- **发射器和听者做成引擎自带的脚本组件**（`AudioEmitterComponent`、`AudioListenerComponent`），场景里的同名组件导入成它们的属性。空间化用 Web Audio 的 PannerNode：距离模型 inverse、参考距离 1，和 Stride 在 Windows 上用的 X3DAudio 默认曲线一样（1 米以内不衰减，以外 1/距离）。听者的朝向是实体的 -Z：Stride 传给 X3DAudio 的是 +Z，X3DAudio 是左手系，左右算出来和我们一致。和 Stride 不同的地方：
  - 没标 Spatialized 的声音也能挂在发射器上放（不做空间化）；Stride 直接不让。
  - `directionalFactor` 起作用（正面是实体的 +Z，背面的音量 1 - 这个值，中间按角度过渡，用 PannerNode 的锥形近似心形）。Stride 的 XAudio2 后端把指向类型写死成全向，这个值没有效果；别的后端不看它。
  - `environment` 的混响是合成的（指数衰减的白噪声做冲激响应，混响时间小、中、大各 0.4、0.8、1.6 秒，自己定的），所有浏览器都有；Stride 用 Windows 的 HRTF 自带的房间模型，只在 Windows 上、只在 UseHRTF 时有。我们也只在 `useHRTF` 时加混响，免得同一个场景默认的 `Small` 让所有发射器都带上混响。
  - 不做多普勒和按距离的低通。X3DAudio 默认两样都算，但 Stride 传的速度是每帧的位移（不是每秒），多普勒几乎听不出；低通是 X3DAudio 的默认曲线（1 米以外截到采样率的 1/8），Stride 没有调它的接口，更像是没关掉而不是要这个效果。Web Audio 也已经去掉了多普勒。
- **`body.setOrientation`**（原生 0.29.0 的 `sn_physics_body_set_rotation`）：只改物体的朝向，位置和它的插值不动。第一人称、第三人称相机每帧把鼠标的偏航写给角色（Stride 的 `character.SetTargetPose(Quaternion)`）；用 teleport 的话每帧都让插值从头开始，开着插值的角色走起来一顿一顿。
- **鼠标锁定**：Stride 的脚本一启动就锁、Esc 来回切换。浏览器里锁鼠标要先有用户操作，锁着时按 Esc 由浏览器解锁（页面收不到这次按键）。所以两个相机教程改成：点左键锁定，锁着时才转视角，没锁时屏幕上提示一句；Esc 解锁。
- **第三人称相机的避障射线只跳过角色自己**：Stride 的脚本用 `CollisionMask.Everything & ~character.CollisionLayer.ToMask()` 跳过角色所在的整个层，而教程场景里的墙和箱子都和角色同在 Layer0，射线只打得到地面，相机退到墙边时穿到墙后面。我们用穿透的射线取第一个不是角色自己的命中，墙能挡住相机。
- **`entity.findChild(name)`**（Stride 的 `Entity.FindChild`）：找整棵子树（教程里激光挂在武器模型下面，不是脚本所在实体的直接子实体）。和 Stride 不同：不会找到自己（Stride 从自己找起），同名的先找到靠前的子实体（Stride 用栈遍历，先找到靠后的）。

## 2026-11-19 材质：着色模型、停用的特性、化不成固定槽的属性（CSharpIntermediate 的桌面比对查出来的）

第一次和桌面版比，四张图平均每通道差 26 到 67/255：木地板在我们这边是映着天空的镜面，激光是白的、长度不对。原因都在材质的导入，以前的样例没碰到：

- **镜面的颜色和着色模型是两个特性**：Stride 的 `Specular`（金属度或镜面颜色）只给出镜面色，`SpecularModel`（微表面模型）才画镜面反射，材质里没写就是没有。SamplesAssetPackage 的木地板（board1B）只有前者，在 Stride 里是纯漫反射；我们以前只要有 `Specular` 就画反射。现在没有模型的材质导出 `specularShading: false`：不画镜面反射，但金属度、镜面颜色照常折进漫反射（金属没有漫反射、能量守恒时乘 1 - 镜面），同 Stride。
  - 样例里只有 board1B 这一个材质是这样，别的 104 个带 `Specular` 的都有模型，不受影响。
  - 模型不是微表面的（玻璃 `MaterialSpecularThinGlassModelFeature`）先当微表面画并警告，见下面。
- **停用的特性（`Enabled: false`）当没有**：Stride 生成着色器时跳过停用的特性。教程的 Red 材质留着一个停用的自发光（一张按钮贴图乘 5），我们照样导入了，激光成了发白光的。
- **化不成固定槽的属性整棵树导出**：材质文件里漫反射、金属度、镜面、光泽度是固定的形状（一个常量，或常量和一张贴图），运行时不用按材质编着色器。board1B 的光泽度是"贴图 × 0.3"、镜面带贴图，以前退成后备值（光泽度成了 0，反相后粗糙度 0）。现在这样的属性放进一个遮罩是常量 1 的材质层（`MaterialFile.layers` 的第一层），运行时和材质层走同一条路径，不用新加概念；法线贴图不是单独一张贴图时走已有的 `normalTree`。漫反射的树（两张贴图合成等）还没这样做，仍然警告。
  - 考虑过的别的做法：给基础材质的每个属性各加一个"树"的字段和对应的着色器分支。和材质层的那套完全重复，不值。
- **颜色树里的法线贴图翻转绿色通道**（`TextureRef.invertY`）：Stride 在编译贴图时按 `InvertY` 翻，我们的贴图照源文件，固定槽的法线贴图在着色器里翻；颜色树（材质层的法线、`normalTree`）以前没翻，带法线贴图的材质层的凹凸在 Y 方向是反的。
- **没给材质的程序模型也有一个材质槽**：Stride 的程序模型总有一个 `MaterialInstance`，里面的材质可以是空的，实体的 `Materials` 按槽覆盖。我们以前在模型没给材质时不建槽，覆盖就用不上（教程的激光是这样的圆柱，红色由实体给）。程序模型也能被脚本的属性引用了（以前报不支持）。
- **玻璃**（`MaterialSpecularThinGlassModelFeature`，教程里绿色的箱子）：照 Stride 分两遍画在透明阶段，先把透过去的比例乘到背景上（混合是 目标 × 源），再把反射加上去；两个比例按折射率、视角和玻璃的颜色算（`MaterialTransmittanceReflectanceStream`），镜面的菲涅耳项和环境光的镜面系数都换成反射的比例。材质文件里是 `glass: { refractiveIndex }`。
  - 和 Stride 不同：两面都画时我们先画背面再画正面（远的面的反射被近的面挡掉一部分）。Stride 的注释也是这么写的，代码却是先正面后背面。
  - 顺带补上的两条 Stride 规则：背面的法线翻过来朝着相机（所有两面画的材质，以前背面是按背对着光算的）；漫反射的颜色和着色模型缺一个就不算漫反射光照（`diffuseShading: false`：玻璃、只有自发光的激光）。
- **清漆**（`MaterialClearCoatFeature`，车漆，教程里蓝色的箱子）：照 Stride 画两遍。第一遍在不透明阶段，是金属碎片和底漆：漫反射色和光泽度按到相机的距离从碎片过渡到底漆（过渡量 = saturate(距离 × LODDistance)），法线用碎片的法线贴图，金属度是碎片的；第二遍在透明阶段、直接加到画面上（One/One）：材质自己的漫反射色配清漆的金属度、光泽度和橘皮法线。各个输入整棵树导出（`MaterialFile.clearCoat`），运行时编译；渲染那边把"一个材质画几遍"收成一张表（`MaterialPass`），玻璃和清漆共用。
  - 和 Stride 不同：`UseRandomTextureCoordinates`（碎片的贴图按格子随机翻转、旋转、平移）采样时用打乱之前的坐标的导数。打乱以后的坐标在格子边上是断的，照它自己的导数选 mip 会在每个格子的边上取到最小的一级，画出一圈模糊的线；受影响的只有这种贴图的格子边缘。
  - 还没做：清漆加透明（Stride 第一遍沿用材质的透明混合）报警告，第一遍按不透明画；没有切线的网格上碎片和橘皮的法线贴图不起作用（和别的法线贴图一样）。
- 还没做的材质特性（曲面细分）导入时报警告，不悄悄忽略。

## 2026-11-19 贴图的颜色键和 1 位 alpha；泛光的权重；比对时关掉亮度适应

查 CSharpBeginner 里箱子的发光标志为什么比 Stride 多一圈蓝光（带材质层的箱子第一次近距离比）：

- **颜色键**（贴图资源的 `ColorKeyEnabled`、`ColorKeyColor`，精灵表也有）：以前没导入。等于键的像素变成全透明的黑，在缩放之后做（同 Stride 的 TextureHelper）。箱子的遮罩图里 22% 的像素是不透明的纯黑，是用颜色键去掉的。
- **`Alpha: Mask` 照 1 位 alpha 做**：这种贴图在桌面上压成 BC1，alpha 不到一半的像素是全透明的黑，其余不透明（预乘时颜色先乘 alpha）。这是 BC1 格式的限制，不是我们非跟不可的；但材质是按硬边的遮罩做的（标志的自发光是遮罩乘 50），留着平滑的 alpha 时半透明的边缘会亮出一圈。所以导入时照做。
- **1 位 alpha 的贴图不做 alpha 渗色**：渗色（`bleedTransparentColors`）把透明像素的颜色换成最近的不透明颜色，是为了线性过滤和 UASTC 的块误差。但渗进去的白色会被压缩误差漏出来的一点 alpha 带出来，自发光乘 50 以后在黑底上成了一道道蓝色条纹，泛光再把它放大成光晕。硬遮罩透明的地方就该是黑的（同 BC1）。
  - 考虑过的别的做法：贴图标成"已经预乘"、着色器里不再乘 alpha（更准，但要改贴图、精灵、UI 整条约定，只为边缘一个纹素以内的差别不值）。
- **泛光的权重少算了一次颜色空间转换**：Stride 的 Bloom 用 `Scaler.Color = new Color4(Amount)` 把模糊后的图加回画面，ImageScaler 把这个颜色当 sRGB 换到线性空间（`Color.ToColorSpace`，rgb 换、alpha 不换），Additive 混合又乘一次 alpha，实际权重是 srgbToLinear(0.3) × 0.3 = 0.022；我们照着"颜色乘 alpha"算成了 0.09，泛光强了 4 倍。之前的样例里亮的东西是大片的天空，差不明显；箱子的标志是 50 倍亮度的小光源，光晕一眼就看得出来。是逐个效果和桌面版比（两边只开泛光、只开光芒、只开镜头光晕）定位到的：光芒和镜头光晕各自对得上，只有泛光不对。
- **比对时两边都关掉色调映射的亮度适应**（`TemporalAdaptation`，时间常数 1 秒）：相机移到位以后曝光还在变，早截晚截墙面能差 4/255（桌面 Stride 自己两次截图就差这么多），之前"属性"那张差 5.98 有一半是它。截图入口和 `capture-ours.ps1` 都把它关掉。别的样例的截图工程是相机不动、等够了再截，不受影响；以后有相机移动的比对都照这个做。

## 2026-11-19 目标改成比 Stride 做得更好（用户决定）；CSharpBeginner：实体克隆、场景归属、调试文字

用户把目标从"对齐 Stride"改成"比 Stride 做得更好，同时整理文档和代码"（docs/roadmap.md 的"原则"）。之后每一项都要回头看两件事：Stride 的毛病不跟，我们比 Stride 差的限制补掉。CSharpBeginner 是按这个标准做的第一项：

- **实体克隆是实体层的通用能力**（`entity.clone()`，`engine/clone.ts`）：第一版放在内容管理里，按建实体的场景文件再实例化一次，只能克隆文件建出来的实体，运行时加的组件不跟着——比 Stride 差，职责也放错了层，所以重做。现在照抄数据组件和脚本属性现在的值，子树里的实体引用、组件引用换成克隆的；只有运行时状态的组件（字段全是 transient）不抄，由挂它的系统在 `entities.onClone` 里重新挂（动画系统给克隆的模型建自己的骨架实例和形变权重）；脚本属性以外的创作数据由脚本的 `cloneFrom` 抄（AnimationComponent 的剪辑、粒子系统、约束的设置）。
  - 和 Stride 不同：克隆出来的实体马上就在游戏里。Stride 的克隆要加进场景才看得见、才跑脚本，教程里的 clone0 就是演示"不加进场景就看不见"；我们没有"游离的实体"这个状态，演示改成克隆完就销毁，那行字跟着改。
  - 考虑过的别的做法：保留按文件再实例化（最省事，但限制去不掉）；给每个组件写克隆函数（数据组件有 schema，用不着）。
- **实体所在的场景**（`entity.scene`，Stride 的 Entity.Scene）：以前卸载场景只销毁场景文件建的实体，脚本克隆、实例化到场景根的实体留在游戏里（换一圈教程实体数从 143 涨到 175）。现在运行时建的根实体可以放进一个场景（`clone.scene = this.entity.scene`，或者 `create({ scene })`），卸载时一起销毁；没放进去的跟着父实体。多网格模型多出来的网格子实体改用 `ModelPart` 标记认（以前内容管理按实体记一张表，克隆的实体不在表里）。
- **调试文字按 CSS 像素、按设计分辨率摆**：Stride 按后备缓冲的真实像素摆，高分屏上字只有一半大，画布和设计的窗口不一样大时字和画面对不上（教程把字摆在 3D 物体旁边）。现在位置的单位是 CSS 像素，字按像素比放大整数倍（往下取整，挨着的两段字不会叠）；`debugText.virtualResolution` 设了以后位置按那么大的画面给，按高度缩放、水平居中换到画布上，`loadGameSettings` 把它设成游戏设置的后备缓冲大小，所以样例照搬 Stride 的位置就行。画布和设计的窗口一样大、像素比是 1 时和以前逐像素一样（已有的截图比对不受影响）。
  - `input.absoluteMousePosition` 跟着改成 CSS 像素（Stride 是后备缓冲的像素），`debugText.fromCanvas` 换成 print 用的位置。
- **调试文字默认只在开发版画**（`debugText.visible`）：同 Stride 的 `DebugTextSystem.Visible = Platform.IsRunningDebugAssembly`，调试用的字不该出现在正式版里；拿它当内容的样例（CSharpBeginner 的教程说明、BepuSample 的操作提示）自己设成 true。不画的时候文字照样记在 `lines` 里，调试 CLI 读得到。
- **相机插值封顶**：TutorialUI 的 `Vector3.Lerp(起点, 终点, 计时 / 2 秒)` 不封顶，最后一帧的系数大于 1，相机冲过头一点，冲多少看那一帧多长（帧率相关）。我们到 1 为止，相机正好停在教程的 Camera 上。
- **教程里的笔误不跟**：InstantiatingPrefabsDemo 写的是 `Quaternion.RotationY(135)`（弧度，转出来约 175 度），按 135 度转。
- **照 Stride 的**：`Content.Load` 是同步的，我们的 `loadModel`、`loadPrefab` 是异步的（网页上读文件只能异步），加载完之前算没加载。

## 2026-11-19 SimpleAudio：声音

- **用 Web Audio，源文件原样用**：浏览器自己解 mp3、ogg、wav（D9 的 (c)），不转码、不带解码器。不流式的声音整个解码成 AudioBuffer（音效：开始得快，能同时放很多个）；流式的（StreamFromDisk，音乐）每个实例一个 `<audio>` 元素边下边放，经过 MediaElementAudioSourceNode 接到同一个主音量。没选 AudioWorklet 加 wasm 解码：浏览器已经会解这些格式。
- **浏览器要用户先操作才出声**：Chrome、Safari 的自动播放策略让 AudioContext 在用户点击、按键之前挂起。和 Stride 不同（桌面一启动就有声音）：之前开始放的声音状态是 Playing，恢复出声后从头接着放（AudioContext 挂起时时间不走）。Game 在窗口上监听第一次点击、按键，恢复出声。
- **SoundInstance 的语义照 Stride**：Play 在放时什么也不做、Pause 只在放时有效、Stop 回到开头、没循环的放完 PlayState 自己变回 Stopped；Pitch 是播放速度，音高跟着变（`<audio>` 关掉 preservesPitch）。空间化的声音没有 AudioEmitter 时按 2D 放（同 Stride）；AudioEmitter、AudioListener 等用到的样例再做。

## 2026-11-19 UIParticles：粒子系统

- **粒子在 CPU 上模拟，照 Stride 的算法**：Stride 的粒子系统是 CPU 上的（每个发射器一个粒子池，生成器、初始化器、更新器），样例的粒子数在几百到几千，用 JS 的类型化数组按字段分列存足够快，以后数量大的效果再考虑放进原生侧或 GPU 计算。随机数、每帧的顺序、生成器的状态机都照 Stride，固定种子（RandomSeedMethod: Fixed）时结果和桌面一样（RandomSeed 和 .NET 算的逐位对上）；默认的按时间取种子两边本来就对不上。
- **场景按 Stride 的对象树原样导入**：粒子系统由几十种模块组成，导入成 `ParticleModuleFile`（类型名、属性名首字母小写，没写的属性运行时取 Stride 的默认值），运行时按 `$type` 建模块；导入器只留下运行时认识的类型，其余警告后去掉。加新模块只要在两边各加一项。
- **力场的衰减改掉 Stride 的毛病**：Stride 的 FieldFalloff 在 FalloffStart 到 FalloffEnd 之间除以 FalloffEnd / FalloffStart（应该是两者的差），过渡区里力几乎不变、到 FalloffEnd 时突然跳到 StrengthOutside。我们线性过渡。影响：UIParticles 的彩纸在力场的边缘附近受力和 Stride 不一样（Stride 的更强）。
- **组件的 Control 不导入运行时**：ParticleSystemComponent 的 Control（ResetSeconds、Play/Pause/Stop）在 Stride 里只在编辑器和预览里起作用（ParticleSystemSimulationProcessor 的 applyEditorControl），游戏运行时粒子系统一直在播。我们照运行时的行为。
- **统一缩放取世界矩阵 X 轴的长度**：Stride 把实体和所有父实体本地缩放的 X 乘起来（父实体转了角度时和世界矩阵不一样）；统一缩放时两者相同，我们直接从世界矩阵取。

## 2026-11-19 UIElementLink：放在 3D 里的 UI；跟着 UI 元素走

- **放在 3D 里的 UI 也画在后处理之后**（和桌面比对时量到的代价见 `tools/stride-capture/ui-element-link`：这个样例的场景很暗，Stride 的自动曝光把 UI 提亮很多，量平均亮度时也算上了 UI；我们的 UI 是原色，场景的曝光只看场景）：Stride 在透明阶段里画，会被色调映射、泛光、FXAA 处理；我们和全屏 UI 一样画在后处理之后（UI 的颜色照原样），另外和场景的深度缓冲比较，被更近的物体挡住。为此前向渲染器在场景里有 UI 时把主画面的深度缓冲留下来（`depthStoreOp: 'store'`，平时 `discard`，分块渲染的 GPU 上省带宽）。代价：斜着的 UI 的边没有 FXAA。没选在透明阶段里画：那样 UI 的颜色被色调映射改掉，和全屏 UI 不一致。
- **放在 3D 里的 UI 不把文字对齐到像素，布局按虚拟像素**：Stride 按投影估计 真实 / 虚拟 的比例（RealVirtualResolutionRatio），相机一动比例就变，文字每帧重新排版；只有面向相机且固定大小时才对齐像素。我们的字是矢量的，排版不随比例变，所以比例当 1、从不对齐（对齐在透视下也没有意义）；投影估计的比例只给文字的抗锯齿边留宽度（`SpriteBatch.pixelRatio`）。
- **UIElementLink 先布局再算**：Stride 的 UI 在画的时候才布局，UIElementTransformLink 用的是上一帧的元素位置，跟着走的实体晚一帧（按钮移动时骑士落后一点）。我们在 UIElementLink 系统里（变换更新之前）先布局这一帧的 UI（`game.ui.layout`，画的时候不再重复），跟着走的实体这一帧就对齐。没有 UIElementLink 的游戏仍在画之前布局，不受影响。面向相机的 UI 的朝向用上一帧画的时候的相机（相机的世界矩阵这时还没更新）。
- **面向相机的 UI 按实际画它的相机算朝向**：Stride 的 UIElementLinkComponent 要另外设 Camera，没设或设的不是画 UI 的相机时，跟着走的实体和 UI 的朝向对不上；我们用画 UI 的主相机，组件上的 Camera 导入但不用。
- **画布的大小在帧开头跟上窗口**：以前在画之前才调，启动的第一帧里脚本读到的是画布的默认大小 300x150（SplashScript 按它摆角上的按钮）；现在启动时和每帧开头调，这一帧的脚本和绘制看到的一样大（Stride 的后备缓冲在游戏开始前就建好了）。

## 2026-11-19 GameMenu：UI 只做两维的布局、画在最后；贴图按预乘 alpha 用

- **布局只做两维**：Stride 的 UI 布局是三维的（每个元素有 Depth、MinimumDepth、MaximumDepth、DepthAlignment，Margin 有 Front、Back，Grid 有层 LayerDefinitions），为了把 UI 放进 3D 场景时有厚度。实际用法里深度一直是默认值：GameMenu、UIElementLink、UIParticles 的页面没有一个元素设了深度（WelcomePopup 的 DepthAlignment: Stretch 在两维里没有意义）。3D 里的 UI 由 UIComponent 的世界矩阵和 Size 摆放，不靠深度布局。只做两维，每个元素的布局计算和存储少三分之一，代码更好读。导入时深度方向的属性和 Grid 的层直接不导入（不警告：它们在两维里没有对应）。代价：真要做有厚度的 3D UI（层叠的面板）时要补，目前没有样例用到。
- **UI 资源平铺成元素数组**（`UIFile`，`.ui.json`）：元素按 Hierarchy.Parts 的顺序放进数组，Children、Content 的 `ref!!` 引用换成下标；属性名首字母小写，值换成 JSON（颜色是 0 到 1 的 sRGB，Thickness 是四元数组，NaN 是 null，枚举是首字母小写的名字）。UI 库的实例（带 Base 的元素）在 Stride 的文件里已经是完整的属性，导入时不去合并 UI 库。页面和库同一种文件，库多一个 `templates`（名字 → 元素）。
- **贴图按预乘 alpha 用**：Stride 编译颜色贴图（包括精灵表）时预乘 alpha（ColorTextureType.PremultiplyAlpha 默认开；DirectXTex 对 sRGB 格式在线性空间乘，等于采样后的 rgb 乘 a），画精灵、UI、SpriteBatch 都按预乘混合。我们的贴图存直通 alpha，以前直接按预乘混合，半透明的边会发亮（Platformer2D 的精灵边、UI 的圆角框）。现在精灵、SpriteBatch（UI 用它画）的着色器采样后乘 alpha，结果和 Stride 一样（差 8 位量化；Stride 的 mip 在预乘之后生成，我们在之前，只影响有 mip 的半透明贴图）。设成 PremultiplyAlpha: false 的贴图画成精灵、UI 时也按预乘画（不支持）；网格的贴图不受影响。别的做法：导入时预乘——KTX2 可以在编码前乘，但原样复制的 PNG 只能在运行时让浏览器乘，两条路径；着色器里乘一次最简单。
- **UI 画在整个画面之后**：Stride 的 UI 在前向渲染器的透明阶段里画（会被泛光、色调映射处理，也会被 3D 物体的深度挡住），我们画在后处理之后、调试文字之前。全屏 UI 本来就清了深度，区别只在后处理：UI 的颜色照原样显示，这是想要的。（放在 3D 里的 UI 见上面 UIElementLink 一节。）
- **UI 的裁剪用剪裁矩形**：Stride 的 ClipToBounds 用模板缓冲，按元素本身的形状（可以转角度）裁；我们用元素在屏幕上的包围盒做剪裁矩形，不用模板缓冲、不打断合批。转了角度的元素裁到包围盒；样例里裁剪的都是 ScrollViewer，不转。
- **EditText 的文字区域按内边距放**：Stride 把文字区域（元素减去内边距）放在元素中心，左右或上下内边距不一样时文字偏了（GameMenu 的名字输入框上 30、下 40，文字高了 5 像素）；我们放在内边距里面。
- **UI 输入照 Stride master 的占用**：Stride 4.4.2 没有输入的占用（UI 和脚本都看到同样的输入），master 上加了（InputManager.MaskCapturedInput、InputCaptureMonitor 样例），我们照 master 做：GameMenu 的脚本本来就是 master 版的。按键的屏蔽照 ButtonCaptureTracker，脚本不会看到没有按下的松开、没有松开的按下。
- **EditText 用浏览器的输入框编辑**：Stride 桌面版自己解释按键（方向键、Home、End、退格），没有复制粘贴和撤销，输入法靠系统的 TextInput。我们在激活的 EditText 后面放一个看不见的 `<input>`（多行时 `<textarea>`），键盘、输入法、选中、复制粘贴、撤销都是浏览器的，行为和网页上的输入框一样；输入框摆在 EditText 的位置，输入法的候选窗在字旁边，读屏软件读得到。Enter、Esc 结束编辑同 Stride（多行时 Shift+Enter 换行，多做的）；编辑时点画布的别处不结束编辑（同 Stride 桌面版，挡掉画布的 mousedown 默认行为）。
- **滚轮滚动 ScrollViewer**（多做的）：Stride 桌面版的 UI 不处理鼠标滚轮，ScrollViewer 只能拖。鼠标在 ScrollViewer（或它里面的元素）上时滚轮滚动它，一格 50 个虚拟像素；鼠标被 UI 占着，脚本看不到这次滚轮。
- **OutsideClick 按弹窗的矩形判断**：Stride 拿相对弹窗中心的位置和 [0, 大小] 比，点在弹窗的左半边、上半边也算外面；我们按矩形判断。
- **每帧只提交一次命令**：场景（ForwardRenderer）、UI、调试文字以前各建一个命令编码器、各提交一次；现在都录进 `GraphicsDevice.frameEncoder`，Game 在帧末提交一次（GPU 计时的查询也在这里解析），后备缓冲的视图每帧只建一次。GameMenu 的启动页 0.57 → 0.43 ms（桌面 Stride 0.52 ms）。约束：`queue.writeBuffer` 在提交之前就写好，同一个缓冲一帧只能写一份，所以每个 UI 有自己的 SpriteBatch。游戏自己的根渲染器（SpriteFonts 的 FontRenderer）照旧可以自己提交。
- **调试文字按左上角摆**：Stride 的 FastTextRenderer 每个字以给的位置为中心，整段字向左上偏半个字（4、8 像素）；我们按给的位置当左上角。字体用 Stride 自带的 8x16 位图（嵌在引擎里，5.8 KB），颜色同 Stride（LightGreen 当线性颜色用）。
- **键名的缩写整个小写**：脚本属性和 UI 属性的键名以前只把第一个字母改小写，`UILibrary` 变成 `uILibrary`；现在开头的缩写整个小写（`uiLibrary`、`imeSelectionColor`），后面的单词不变。已有的样例里只有 GameMenu 有这样的键。

## 2026-11-19 SpriteFonts：文字按轮廓画（Slug）；排版改掉 Stride 的两处毛病；合成器的游戏渲染器

- **算法用 Slug**（Eric Lengyel，JCGT 2017）：每个像素对字形轮廓（二次贝塞尔）做横竖两条射线，按交点算覆盖率，带分块限制每个像素要看的曲线数。选它是因为数值上最稳（根的取舍按控制点的符号查表，没有浮点误差导致的漏点），2026-03-17 专利已捐给公有领域，参考着色器 MIT/Apache（要署名，见 README 的"许可证"）。考虑过 Dobbie 的网格法（精度问题多）、Loop-Blinn（要三角化轮廓）、MSDF（缩放到很大时角会圆，D16 定它只给世界空间的字）。字形在 CPU 上按真实像素外扩一个像素（SpriteBatch 只有平移、旋转、缩放，用不着参考顶点着色器那套按投影矩阵的动态外扩）。
- **运行时字体导入全部字形、按码位块下载**：Stride 的运行时字体带着整个字体文件，用到哪个字栅格化哪个；我们导入时把所有字形转成轮廓，按码位块（码位 >> 8）分文件，运行时用到哪块下载哪块。日文字体总共 118 MB，一屏文字只用到十几块。以后可以把点存成 f16 再减半。
- **系统字体**：照 Stride 在系统字体目录里按家族名（名字表的 1 号或 16 号）和粗斜体找，找不到依次试度量兼容的替代并警告。字形轮廓会进游戏的内容（同 Stride 把栅格化的字形放进内容），字体的授权由用游戏的人负责。
- **排版照 Stride 的度量，但改掉两处毛病**（用户 2026-11-19：Stride 有问题时不跟随，做得更好）：
  - 字距：Stride 的两种字体都没有填 KerningMap，字距不生效；就算填了，GlyphEnumerator 也只挪这一个字、不推后面的字。我们按 kern 表做（同 FreeType 取整到像素），推后面所有的字。
  - drawString 的原点：Stride 把它当字体像素用，而调用方（比如 SpriteFonts 的动画）给的是 measureString 量出来的虚拟坐标，窗口和虚拟分辨率不一样大时旋转中心就偏了。我们的原点就是虚拟坐标。
  - 留着照 Stride 的：度量公式（行距、基线、LineGapFactor；编译期字体的度量不随字号变，OfflineRasterizedSpriteFont 重写了那几个方法）、前进宽度按栅格化的 ppem 取整、字体要求时 ppem 取整（head 表 flags 第 3 位，Arial 有；FreeType 开 hinting 时照做，字号 33.33 的字按 33 排、按 33 画）、位置和字的原点取整到真实像素、颜色当 sRGB、预乘混合。
  - 更正：起初以为 Stride 的编译期字体"字形不随字号变、行距却缩放"是第三处毛病，和桌面截图比对时发现是我们第一版漏看了 OfflineRasterizedSpriteFont 的重写，Stride 本身是一致的。
  - 后果：和桌面 Stride 的截图在用到字距、动画的旋转原点的地方有差，比对时记成有意的偏差。
- **排版加缓存**：Stride 每次 MeasureString、DrawString 都重新排；SpriteFonts 每帧把同样的几段字量好几遍再画，CPU 占了一帧的大半。`layoutText` 按字体、字号、对齐、文字缓存（每个字体最近 256 条，字体下载完新块或开关字距时作废），SpriteBatch 每个字直接写缓冲。对齐那屏 2.1 ms 降到 0.39 ms。
- **合成器的游戏渲染器**：Stride 的合成器的根（Game）可以是游戏程序集里的渲染器（SpriteFonts 的 FontRenderer 没有场景）。导入游戏设置（`--asset <包>/GameSettings`）时写出它的类型名和属性（同场景脚本的属性规则，引用的字体、贴图一起导入），运行时 `Game.loadGameSettings(path, { renderers })` 按类型名用游戏给的工厂建它、换掉 `rootRenderer`。用显式的工厂表而不是登记表：现在只有这一个，等第三次出现再考虑和脚本的登记表合并。脚本和渲染器属性引用的贴图另写一个 `.texture.json`（编码、尺寸、sRGB），`content.loadTextureAsset` 读。

- **挪到后面的**：P1 的阶段表列了点光和聚光的阴影与分簇、SVG 精灵按矢量画、调试渲染、2D 物理，动画剪辑的非骨骼曲线（Updater）在第一节也标了 P1。P1 的七个游戏都没用到它们（点光、聚光本身做了，样例里不投阴影、灯也不多）。按"下一个游戏缺什么就做什么"：阴影和分簇、非骨骼曲线放到 P2（教程场景、粒子样例用到时做）；SVG 精灵按矢量画是 P2 矢量渲染底座的一部分，和字体一起做，免得先做一个只给精灵用的版本；调试渲染（线框、物理形状）放到 P3，和编辑器的解析线 Gizmo、网格用同一套画线；Bepu 的 2D 模式不做（Platformer2D 用 3D 物理，平台和角色都在 Z=0 上），有样例用到时用 Jolt 锁定轴；预先烘焙的导航网格（.sdnavmesh）等有样例用它再做（TopDownRPG 运行时建）。

## 2026-11-19 FirstPersonShooter：特效预制体照常生成，冒烟测试用真实点击拿指针锁定，穿透容差降到 1 mm

- **特效预制体照常生成**：枪口火焰、弹孔、受击拖尾都是 VFXPackage 的粒子预制体（P2），导入时粒子组件跳过，预制体只剩变换。EffectController 照 Stride 生成、定时移除，P2 有了粒子就直接能看，不用回头改脚本。
- **TriggerGroup 是脚本属性的嵌套对象**：Stride 里 TriggerGroup、TriggerEvent 是带 DataContract 的数据类；我们用 `prop.object` 和 `prop.list` 声明，场景导入的值照常对上，不为它们加新的资源或组件种类。
- **冒烟测试用真实点击**：浏览器只在用户操作里允许指针锁定，调试 CLI 的合成事件拿不到。`stride mouse left --trusted` 走 DevTools 协议的 Input.dispatchMouseEvent（stride open 启动的 Chrome），算用户操作；锁定后合成的 `mouse move` 照常进 mouseDelta。考虑过给 InputManager 加调试用的"假装锁定"，那样测不到真实的锁定路径，不选。
- **穿透容差降到 1 mm**：Jolt 默认允许物体陷进去 2 cm 才往外推（`mPenetrationSlop`），Bepu 的接触是软弹簧（样例里 30 Hz），静止时只压下去零点几毫米。结果是我们的角色和放在地上的物体都比 Stride 低 2 cm，FirstPersonShooter 的相机矮 2 cm，地面的网格线错开 4 像素。原生 0.21.1 对所有世界设成 1 mm（留一点免得堆叠的物体来回抖），所有样例的冒烟脚本回归通过。没有做成可配置：Stride 没有对应的设置。
- **共用的数学和输入**：Stride 模板各自带一份的 InputManagerExtensions（摇杆、扳机超过死区取平均）进了 `InputManager.thumbAny`、`triggerAny`；`Quaternion.betweenDirections`、`setYawPitchRoll` 同 Stride。TPP、TopDownRPG 改用它们。

## 2026-11-19 TopDownRPG：导航网格的输入取物理形状的三角化，路径给拐点

- **导航网格的输入**：Stride 的 RecastMeshSystem 把静态碰撞体按它自己的形状缓存（ShapeCacheSystem，球和胶囊有固定的细分）转成三角形。我们直接让 Jolt 把物理世界里的静态体三角化（`Shape::GetTriangles`，复合形状先收集叶子），各种形状都覆盖，和碰撞用的是同一份几何；球、胶囊的细分和 Stride 不完全一样，导航网格的边缘可能差一两个格子。
- **路径给拐点**：Stride 的 FindFollowPath 沿拐点按固定步长采样出一串平滑的点，我们给 Detour 的直线路径（拐点，含起点和终点）。TopDownRPG 的 PlayerController 自己按路径点走，拐点照样能用；点更少，转角处的减速逻辑按拐点算。
- **RecastNavigationComponent**：寻路（`tryFindPath`）之外，2026-11-20 补上了排队寻路（`setTarget`，导航系统每帧最多算 10 条）和沿路径走（`startFollowingPath`，按 `speed` 挪实体、转向前进的方向）。和 Stride 不同：一开始的状态是 pathIsInvalid（Stride 的枚举默认值是 QueuePathPlanning，每个组件一出生就排队找一条去原点的路）；排队的寻路没找到时状态是 pathIsInvalid（Stride 停在 PlanningPath）；已经站在路径点上时不转向（Stride 对零向量求朝向得到 NaN）。BepuNavigationBoundingBoxComponent 在 Stride 里本身没实现（源码里是 #warning），导入时忽略。
- **挂到骨骼节点用变换存储的链接**：ModelNodeLink 的实体世界矩阵 = 目标的世界 × 节点矩阵 × 本地，不看父节点（Stride 的 TransformLink）。做在原生的变换存储里（`setLink`），计算顺序按链接排，帧末一次算完；别的做法是在 TS 里每帧算好世界矩阵写回本地变换，但子实体和物理都要跟着处理，容易出错。
- **跟着实体走的刚体**：运动学刚体的世界变换被物理以外改过（脚本移动了它或它的父实体：JumpyJet 移动管子组的根，掉落金币的拾取触发器跟着金币落）、挂在骨骼节点上的刚体（出拳的碰撞体），每个物理步先瞬移到实体当前的世界位姿。Bepu 里刚体由仿真驱动变换，这些情况都停在原处（运动学的醒着时被写回、睡下后变换才跟父实体走，物理里仍在原处；出拳的碰撞体停在加进仿真时手的位置），样例的本意显然是跟着走。和 Stride 不同：运动学的在原生侧（stride-native 的 FollowMovedKinematics，按上次写回的位姿比较），骨骼节点的在 Simulation 的 followNodeLinks。
- **设计分辨率取默认后备缓冲**（2026-11-19）：Stride 的游戏在初始化时取后备缓冲大小当设计分辨率（JumpyJetRenderer 的虚拟分辨率、PipesScript 的场景宽度），桌面上窗口一开始就是 GameSettings 的 DefaultBackBufferWidth、Height（所有样例都是 AdaptBackBufferToScreen: false）。浏览器里画布跟着窗口和像素比走，第一次画时就可能比背景图大，背景露底。所以导入器带上默认后备缓冲大小（`game.settings.defaultBackBufferSize`），这类游戏按它算设计分辨率，窗口多大都拉伸铺满；竖屏的 JumpyJet 页面让画布保持 640:1136 居中（同桌面的窗口）。和 Stride 不同的只是取值的时机，桌面上两者相同。
- **脚本属性互相引用不要求顺序**：Stride 反序列化时引用总能解析；我们挂脚本时被引用的脚本还没挂上就推迟到下一轮（TopDownRPG 的 CrateScript 排在它引用的 Trigger 前面）。
- **节点名照 Stride 的 CleanNodeName**：FBX 的命名空间（`mannequinModel:CATRigHub001`）只留最后一段，去掉 `#`、`__` 之后的部分和空格；动画一个关节都对不上时导入警告（以前静默变成静止姿势）。
- **流式加载时停住物理**：Stride 的 SceneStreaming 用同步的 Content.Load，加载那一帧整个游戏停住；我们的场景加载是异步的（取文件、建实体），分块加载期间把物理仿真停住，角色不会在地面出现之前掉下去（DynamicScene 一开始就是这样：角色站在中央分块的触发器里，脚下还没有地面）。渲染和脚本照常跑。
- **正在接触只报最深的深度**：Stride 的 OnTouching 每步给全部接触点，原生侧按一对物体只报这一步最深的穿透深度（样例只用最深的）；物体要打开（设了带 onTouching 的处理器）才报，免得每步每对都产生事件。
- **场景的偏移在场景上**（2026-11-20 改，以前加在根实体的本地位置上）：每个场景在变换存储里占一个槽位当隐藏的根（`SceneRoot`，不是实体），场景里没有父实体的实体在存储里挂在它下面，子场景的根挂在父场景的根下面。所以同 Stride：实体的本地位置不带偏移，世界位置带（一层层累加）；`scene.offset` 可以运行时改；`Transform.parent` 对脚本仍然是 undefined。运行时放进场景的实体（`entity.scene = …`）跟着场景的偏移，移出来就不跟；克隆出来、还没放进场景的实体不带偏移（Stride 里也是加进场景才算数）。
- **去掉物理组件就移除物体**：以前只在实体销毁时移除；Stride 里从实体上移除 BodyComponent 就离开仿真，TopDownRPG 出拳时靠它开关碰撞体。

## 2026-11-19 Platformer2D：精灵表不重新打包，角色用 body() 控制

- **精灵表不打包成图集**：Stride 编译精灵表时把所有精灵重新打包进图集（Packing，默认开），我们每张源图导出成一张贴图，精灵记下它在源图上的区域。画出来一样；省掉打包，源图原样可查。代价是一个精灵表有几张源图就绑几张贴图（Platformer2D 的每个精灵表只有一张）。九宫格的边框（Borders）等 UI 用到时再做，导入时警告。
- **帧号放在 Sprite 组件上**：Stride 的 CurrentFrame 在 SpriteFromSheet（精灵提供者）上，脚本写 `SpriteSheet.CurrentFrame`；我们的 Sprite 是数据组件，`sheet`、`frame` 是它的两列，脚本写 `entity.require(Sprite).frame`。
- **角色也能用 `simulation.body()`**：Stride 的 CharacterComponent 继承 BodyComponent，Platformer2D 用 Orientation（瞬移）转身。我们的 BodyControl 接受带 Character 的实体，gravity 写回 Character 的列，Character 没有的 kinematic、sleepThreshold 记在控制对象里；原生侧的瞬移和读速度也接受角色（0.18.1），设速度、冲量仍只对动态和运动学物体（角色的速度由移动目标每步设）。
- **音效先不放**：CollectCoin 的 SoundEffect 是 P2 的音频，导入时警告并写 null，脚本里不声明这个属性。

## 2026-11-19 BepuSample 的比对：后处理按效果开关，缺法线补平面法线，工具脚本不移植

- **后处理按效果开关**：以前合成器只导入"有没有后处理"，效果一律按 Stride 的默认全开。BepuSample 和 Platformer2D 的合成器关掉了色调映射（ColorTransforms 里的 ToneMap），我们照样做 Hejl2 映射，整个画面比桌面版暗约 40/255。现在导入每个效果的 Enabled（`ScenePostEffects`：亮部提取、泛光、光芒、镜头光晕、色调映射、FXAA），色调映射关掉时 HDR 画面加上叠加层直接输出（超过 1 的截断，同 Stride）。我们还没有的效果（环境光遮蔽、屏幕空间反射、景深、雾、描边、胶片颗粒、暗角）不导入；BepuSample 开着环境光遮蔽和屏幕空间反射，P4 做。
- **缺法线的网格补平面法线**：Stride 导入模型时用 Assimp 的 aiProcess_GenNormals（逐面法线，OBJ 的平滑组 `s 1` 不管），glTF 规范对缺法线的网格也要求平面着色。我们以前 FBX、OBJ 让 ufbx 按平滑组生成平滑法线，glTF 留空（法线是 0）。BepuSample 的 bridge.obj 没有法线，桌面版是一块块平面，我们是平滑过渡。现在原生导入统一补平面法线（stride-native 0.17.2），被法线不同的三角形共用的顶点拆开。
- **没有材质的网格用 DefaultMaterial 槽位**：OBJ 没写 `usemtl` 时，Assimp 给网格一个叫 DefaultMaterial 的材质，Stride 的模型资源里就是这个槽位；我们的导入器照这个名字找槽位，找不到时和别的不认识的材质名一样用槽位 0。
- **压缩的贴图宽高补到 4 的倍数**：照 Stride（TextureHelper.FindBestTextureSize，`IsCompressed` 默认开）用 Lanczos3 缩放到 4 的倍数再编 KTX2（原生 0.18.0 的 `st_image_resize`，用 basisu 自带的重采样器）。要缩放的源文件在 `source`、`smallest` 策略下也不原样复制，否则运行时的尺寸和 Stride 不同，按点采样的图案会错开。这样的贴图也就能用上压缩格式（以前运行时只能退回不压缩的 rgba8）。BepuSample 因此要加载贴图转码模块。
- **没用到的工具脚本不移植**：BepuSample 的 Utils 里 CollisionComponent、RayCastComponent、OverlapTesterComponent、TriggerUsageComponent、TestComponent、ConstraintEditorComponent、ConstraintToggleComponent 在七个场景里都没挂，只是给用户抄的示例代码；它们演示的接触事件、射线、触发器、约束开关我们都有并有单测；重叠测试（Stride 的 BepuSimulation.Overlap）还没有，等游戏用到时做。GameProfilerComponent 打开 Stride 的性能叠加层，我们用 `stride perf` 代替。

## 2026-11-19 BepuSample：接触的软度不映射，调试文字先不画

- **接触的软度**：Bepu 按物体设接触的弹簧（SpringFrequency、SpringDampingRatio）和最大恢复速度（MaximumRecoveryVelocity），Material Properties 场景靠它们演示"软"和"陷进去"。Jolt 的接触是刚性的，全局用 Baumgarte 恢复，没有按物体的接触软度；只映射摩擦。和 Stride 不同：这几项的效果看不到。别的做法：在接触回调里改 Jolt 的接触约束（ContactSettings 没有软度参数），或者自己写软接触——代价大、收益只在这一个演示上。
- **调试文字**：BepuSample 的脚本大量用 Stride 的 DebugText.Print 当界面。文字渲染（字体、矢量）是 P2 的大件，P1 先做 `game.debugText`（记下每帧打印的文字，`stride call debug-text` 读），P2 做文字渲染时画出来。
- **伺服和马达**：Bepu 的伺服有最大速度、基础速度，马达有阻尼（MotorSettings.Damping，速度误差到力的软度）；Jolt 的马达只有弹簧（位置马达）和力的上限，所以这几项不映射，速度马达是"在力的上限内尽快达到目标速度"。重力枪、搅拌机的效果一致，只是起步更硬。
- **约束组件**：每种约束一个脚本类（BallSocketConstraintComponent 等，名字同 Stride），启动时加约束、移除时去掉，场景卸载时跟着去掉；同一个实体上可以挂几种不同的约束，但同一种只能挂一个（我们的实体按类存脚本）。样例里同种约束挂在同一实体上的只有 RopeSpawner 的代码，它直接调 `simulation.addConstraint`。ConstraintToggleComponent、ConstraintEditorComponent 在样例的场景里没用到，没有移植。
- **同类脚本**：Stride 的实体上可以挂几个同类的组件（Ropes 场景的一个实体上有 5 个 RopeSpawnerComponent），我们的实体按类存脚本，每类一个。加载场景时第二个起挂到自动建的子实体上（单位变换），脚本里的 `this.entity` 是那个子实体。别的做法：让实体按列表存脚本——`entity.get`、热重载、调试命令都要跟着改，等真有脚本需要在同一实体上多实例时再做。
- **模型实例化**：Stride 的 InstancingComponent 把实例的变换收集起来一次实例化绘制；我们的渲染器本来就把同网格同材质的物体合批，所以 `Instance` 只是"借用主实体的模型"，主实体自己不画。多网格的模型（拆成子实体）只借用主实体那一个网格。

## 2026-11-19 PhysicsSample 的材质和验收

- **材质分两批**：PhysicsSample 的材质用到透明（混合）、遮蔽贴图、镜面工作流（镜面颜色乘强度）、贴图乘颜色的自发光（`ComputeBinaryColor`），都能化成固定着色器里"一张贴图乘一个常量"的形状，P1 做了（没有贴图的槽绑白图，不加变体）。`LogoD` 有材质层（`MaskC` 按贴图的 alpha 混进来），材质层要按层生成着色器，按 D3 由 P2 的着色器系统做；在那之前导入器警告并只用底层材质，Logo 方块缺贴花图案。别的做法：在固定管线里为两层的材质加特例——P2 还要整个换掉，不划算。
- **验收**：Stride 仓库里 4.4.2 标签的 PhysicsSample 还是 Bullet 版（`Stride.Physics`），我们移植的是 master 上的 Bepu 版，没有能直接比的桌面截图。做法：材质做完后用 master 的 PhysicsSample 加 4.4.2 的 nuget 包（`stride.bepuphysics` 4.4.2 在本机 nuget 缓存里）编桌面版截图比对；编不起来时以冒烟脚本（玩法）加目视为准，在进度里写明。

## 2026-11-19 AnimatedModel 分两次验收；多个方向光先只有一个投阴影

- **AnimatedModel 分两次验收**：这个样例除了动画，还用了 UI 页面（Idle、Run 两个按钮）和"第二个相机渲染到纹理、两个精灵显示这张纹理"。UI 系统是 P2 的大件（矢量渲染、.sduipage、字体），只为两个按钮提前做不划算。P1 先做动画、2D 背景、多个方向光、相机槽位、指针输入，按钮暂时用调试命令（`stride call idle`、`run`）代替；渲染到纹理和精灵属于 P1 的"合成器的最小数据化"和"精灵"，接着做；UI 按钮在 P2 做 UI 时补上并重新验收。别的做法：用 HTML 按钮临时顶替（D4 已定 UI 照 Stride 自己做，临时的 HTML 以后还要拆）。
- **多个方向光**：一个视图最多 4 个方向光（`MAX_DIRECTIONAL_LIGHTS`），只有第一个打开阴影的投阴影，其余不投。Stride 每个投阴影的方向光各有一组级联。AnimatedModel 只有一个方向光开了阴影，结果和 Stride 一样；多个投阴影的方向光等有场景用到时再做（阴影图集按光源分块）。
