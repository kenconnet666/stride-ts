## 三、阶段和验收

每个阶段都以"复刻一批游戏"收尾。验收全部由 agent 用调试 CLI 自动完成，不靠人看：

- **画面**：同一场景、同一相机位置，和桌面 Stride 的截图逐像素比较（`tools/stride-capture` 推广到每个样例）。阈值：每通道平均差 ≤ 1/255，差超过 10 的像素 ≤ 0.5%，有意的偏差写进文档。
- **玩法**：每个游戏一个脚本化的通关或冒烟流程（`stride key`、`mouse`、`step`，加上 `inspect`、`eval` 的断言），放进仓库，回归时重跑。
- **性能**：同一台机器、同一时段，帧时间不比桌面 Stride 慢（用相对值，不受笔记本电源模式影响），另记绝对值和电源模式。
- **工程质量**：类型检查、单元测试、原生测试全过；每个游戏的导入、构建、启动时间和下载体积记入文档。
- **超出 Stride 的画面功能**（没有桌面 Stride 可比）：
  - 光照的近似算法（DDGI、SSGI、光追阴影和反射、AO）：和我们自己的参考路径追踪器收敛后的结果比较，记误差；
  - 每个功能各有一个固定机位的截图回归；
  - 各画质档位有帧时间预算，同时记录电源模式；
  - 矢量渲染：放大 1×、2×、4× 截图检查边缘清晰（边缘过渡宽度不超过 1 个像素），并和 Vello/浏览器自己画的 SVG 比覆盖率。
  - 影子 DOM：用 CDP 的 Accessibility 域读无障碍树，检查角色、名字和画面一致；脚本化地选中、复制文字，用输入法事件输入中文，检查结果。

**两条线怎么交错**：P3（编辑器）的验收做完以后，先做 S1（离成片最近、两边都用得上：时间轴是游戏过场，景深和运动模糊是 P4 剩下的效果），再做 S2（创作工具让后面每个阶段的内容都能在编辑器里做），然后游戏线的 P5（光追和全局光照也是成片画质的上限）、S3、P7 的动画部分和 S4 一起做（角色和动画两边共用）、P6、P8、P9、S5 和 P10 一起做。2026-11-21 用户把"从零创建大型世界和真实世界模拟"定为核心能力：P6 的大部分和 P8 提前成"进度"里的 W 组，接在 G2 之后、别的之前。实际的先后见"进度"开头的总览表。

P1 和 P2 内部不分先后，按"下一个游戏缺什么就做什么"推进，游戏顺序就是上表的顺序。P4 到 P10 的顺序可以按需要调整，但 P5 依赖 P4 的降噪和时间复用基础，P6 的可见性缓冲要等着色器系统稳定，P8 的城市要用 P6 的流式加载和程序化工具、P7 的动画和载具，P9 的头发和衣物要用 P7 的模拟。P4 开头的底座（渲染图、预算、管线预热）不能往后挪：后面每个效果、每种内容都靠它才不卡、才量得出快慢。

## 四、取舍（2026-11-19 用户决定：全部按推荐）

- ~~**D1 范围**~~：已定（用户 2026-11-19），见上面的"原则"。
- **D2 编辑器的时机**：放在 P3（运行时先跟着游戏走），还是从 P1 就和运行时并行？推荐 P3。理由是游戏复刻走 Stride 工程导入器，不依赖编辑器；运行时的组件和资源格式稳定后再做编辑器，返工最少。代价是编辑器晚几个阶段才有。
- **D3 着色器系统**：自定义着色器（.sdsl）怎么办？
  - (a) 我们自己的 WGSL 组合系统（Node 端预编译），样例里的 SDSL 由 agent 手工移植成 WGSL。推荐这个。
  - (b) 在资源管线里跑 Stride 自己的着色器编译器（这个仓库里有新的 SPIR-V 编译器，可以出 WGSL），能直接导入 SDSL，但管线要依赖 .NET。
- **D4 UI 系统**：
  - (a) 照 Stride UI 自己做：布局规则照 Stride，能导入 .sduipage，用矢量渲染器在 WebGPU 上画，屏幕和世界空间都清晰。推荐这个。
  - (b) 用 HTML/CSS 覆盖层，省事，浏览器本身也是矢量渲染，但做不了世界空间 UI 和逐像素比对。
- **D5 脚本**：游戏脚本只用 TypeScript；C# 脚本由 agent 逐个翻译（不做 C# 到 TS 的自动转译器）；编辑器不内置代码编辑器。推荐都选"是"。
- **D6 C# 网页移植版**：停止，只当参考实现。推荐停止。
- **D7 VR**：推迟（WebXR 以后再说），VRSandbox 不在验收清单里。推荐推迟。
- **D8 验证用的游戏来源**：
  - Stride 自带的样例：MIT，能和桌面 Stride 逐像素比，覆盖面全，必做。
  - Starbreach：Stride 官方的大型演示；代码 MIT，美术是 CC BY-NC 4.0，只能本机导入、不能提交进公开仓库。
  - 社区的开源 Stride 游戏，比如 StrideAsteroids。
  - 别的引擎的开源游戏（比如 Godot 的演示项目），要先有编辑器、要手工搬场景，验证的是"用我们的引擎做游戏"而不是"对齐 Stride"。

  - 公开的图形测试场景：Sponza、Amazon Lumberyard Bistro（CC BY）、Khronos 的 glTF 样例。用来验证 P4 到 P6 的画面和性能。

  推荐：P1、P2 只用 Stride 样例；P4 到 P6 加 Starbreach、测试场景和一两个社区游戏；其他引擎的游戏放到编辑器之后（P7）。
- **D9 音频格式**：管线把 .sdsnd 的源文件转成 Opus（WebM 或 Ogg 容器）要用 ffmpeg。
  - (a) 要求本机装 ffmpeg；
  - (b) 用 ffmpeg 的 wasm 版，慢但零安装；
  - (c) 浏览器能解的格式（mp3、ogg、wav）原样复制。
  
  推荐 (c) 起步，(a) 作为可选的压缩。
- **D10 无人值守的边界**：哪些事可以自己定、哪些要停下来等你？推荐：
  - **自己定**：表里已定的事；同一阶段内的实现方式；和 Stride 不同但更好的做法（照记忆里的规矩：想清楚后果、在代码里标"和 Stride 不同"）；原生包发版；提交和推送。决定记进 `docs/decisions.md`，写明理由。
  - **停下来问**：改动这份路线图的范围；公共 API 的大改（比如组件写法）；引入新的重型依赖；要花钱或要账号的事；连续两次修不好的阻塞。
- **D11 编辑器和现代画面谁先**：推荐编辑器在前（P3 再 P4）。烘焙、打光、调大气和特效都要在编辑器里看着调；而且编辑器做出来以后，P4 起的效果都能直接接进编辑器的预览。另一个选择是先做画面，展示效果来得快，但没有编辑器，灯光和特效只能写在代码里调。
- **D12 渲染器的主路径**：GPU 驱动加可见性缓冲（P6）做成以后，是否取代现在的前向渲染做主路径？推荐分档：
  - 对齐 Stride 的模式和低档继续用前向（简单，和 Stride 逐像素对得上，弱显卡也快）；
  - 高档和极高档用可见性缓冲（几何量大时才划算）；
  - 两条路径共用材质和光照代码，由着色器系统生成。
- **D13 全局光照的默认方案**：推荐：
  - 默认用烘焙（光照贴图加光探针），在 Web 上最省，画面也最稳；
  - 高档开 DDGI，配合日夜循环、可破坏场景这类动态光照；
  - SSGI 作为各档都能叠加的细节；
  - Lumen 式和 VXGI 暂不做。
- **D14 上采样和动态分辨率**：照你之前的意思，默认按原生分辨率只做抗锯齿；时间性上采样和动态分辨率做成玩家可开的选项（画质菜单里），不默认打开。
- **D15 多人联网**：Stride 没有。推荐放进 P7：权威服务器用 Node，客户端预测加插值，WebSocket 起步，WebRTC 数据通道可选。另一个选择是不做，交给游戏自己。
- **D16 矢量渲染怎么实现**：推荐两步：
  - P2 先做 UI 和文字需要的部分：圆角矩形、边框、阴影、渐变用解析 SDF；文字按字形轮廓（二次贝塞尔）在片元着色器里算覆盖率，世界空间的字用 MSDF；
  - SVG 精灵和矢量贴图要用到任意路径时，再做 Vello 式的计算着色器路径渲染器（WGSL，参考 Vello 的算法自己写，不引入 Rust 依赖）。

- **D17 原生宿主**（2026-11-19，随"3A 开放世界的潜力"加的，我按推荐定，用户可以改）：Web 仍是首选平台和日常开发的环境；同时保证同一套 TS 和 wasm 代码能跑在自带 Dawn 的原生壳里（先用 Electron 这类现成的壳，不够再做 V8 加 Dawn 的专用宿主）。理由：浏览器的内存、存储配额装不下这类游戏的完整体量，bindless 和硬件光追在 WebGPU 里还没有，Dawn 的原生扩展会先有。代价：多一个要测的平台；渲染器不能用浏览器独有的东西兜底。不做的是另写一套原生渲染后端。
- **D18 大世界的坐标**（同上）：位置用双精度（变换存储的平移列改成 f64，Jolt 打开 `JPH_DOUBLE_PRECISION`），渲染时减去相机位置再转成单精度；旋转、缩放、顶点仍是单精度。另一个选择是保持单精度、定期把世界原点搬到玩家附近（虚幻 4 的做法）：省内存，但所有存着世界坐标的地方（脚本、物理、导航、粒子、存档）都要跟着搬，容易漏。**2026-11-21 用户定的方向：各种类型的值都尽量高精度，按需要做足、不做没必要的精度，双精度不够的场景另想办法**（不只是位置的浮点数，见"原则"的"精度"）。位置用双精度加渲染原点（测过 Jolt 开双精度几乎不慢），W1 第二步做了。

- **D19 成片在哪渲染、用什么编码**（2026-11-21，随"一站式创作工作台"加的，我按推荐定，用户可以改）：推荐在浏览器里渲染、用 WebCodecs 编码（H.264 兼容最好，AV1 小；封装成 MP4、WebM），离线模式逐帧渲染不受实时帧率限制，浏览器不支持的编码交给原生宿主（D17）或服务器上的无头浏览器。另一个选择是导出图像序列交给 FFmpeg，可靠但要装外部软件，作为备选的导出格式保留。
- **D20 建模做到多深**（同上）：推荐"拼搭（基本形状、预制体）加轻量的多边形编辑加程序化建模（节点图）"，精细模型靠导入和 AI 生成，雕刻放到最后。另一个选择是做完整的 DCC（Blender 那样），工作量是一个独立产品，和"引擎加编辑器"的主线抢资源。
- **D21 AI 生成**（同上）：推荐只做接口：工程里配生成服务（外部 API 或本地模型），结果当普通资源导入，记下来源、提示词和许可证；不自研模型。另一个选择是内置某家的服务，绑定供应商、有费用和许可证的风险。
- **D22 agent 的接口**（同上）：推荐编辑器的每个操作都落成"场景文档的修改"或"资源接口的调用"，人和 agent 走同一条路；对外给 MCP 服务（agent 直接用）和命令行（脚本、CI 用），字段描述导出成 JSON Schema。另一个选择是只给命令行，agent 也能用，但要它自己拼参数，出错多。
- **D23 线性内容的画面标准**（同上，用户 2026-11-21 定"3A 风格"：现在的 3A 大作已经有接近电影的效果）：成片和游戏用同一套渲染，画面以当代 3A 的电影感为标准（路径追踪模式、ReSTIR、体积、皮肤和头发这些都要做到）；离线模式在这之上加子帧累积（抗锯齿、真实的运动模糊、降噪更干净）和更高的采样数，P5 的路径追踪是成片的最高档。不另写一套独立的离线渲染器，画质的提升都落在同一个渲染器里，游戏和成片一起受益。

## 加载与缓存（路线图"大世界收尾"的第一部分，2026-11-23 规划）

用户 11-23 问："快速渲染和烘焙、尽快展示、缓存、流式加载素材、懒加载、实例化、热重载做好了吗？Web 游戏引擎肯定要做好。"盘点见 progress-log 第 111 条。做法：先量，再按收益排，每步都在 `tools/budgets.json` 留回归门槛。

**指标**：出画面（打开页面到第一帧骨架、到近处世界就绪、到全部就绪）；卡顿（固定路线飞一圈的最长帧、超 50 毫秒的帧数、期间新编译的着色器和管线数）；下载量（首次、再次打开时重新验证的请求数和字节）；内存（显存、原生内存、JS 堆，长时间飞行后是否稳定）；热重载延迟（按资源种类）。

**步骤**（依赖：0 → 1 → 2 → 3 → 4，4 与 5 可并行，6 依赖 0 的内存度量）：
0. 度量基线：`tools/dev/streaming-bench.ts` 在 Valley 里按固定路线飞，输出上面的指标，写进预算。
1. 先出骨架：页面外壳（内联占位和进度条，`strideApp` 做，首帧淡出）；格子状态（排队、读取中、编管线中、就绪）；用 `.world.json` 的索引先画格子底色和参数化的地形，格子摘要（包围盒、平均色）烘焙时写进索引。
2. 不卡顿：画的时候管线没好先不画、后台异步编译、好了叫醒按需出帧（离线出片和烘焙保持同步）；格子读完先预热管线再换上；其他同步卡顿源（贴图上传、大缓冲、KTX2 转码）按度量逐个改异步或分帧。
3. 排队和优先级：看视线方向和重要性、管线已好的先上；取消过期请求；并发数按带宽自适应；大文件按范围读。
4. 缓存三层：网络（内容文件按哈希命名加清单，`immutable`，可选 service worker 离线）；运行时烘的（远处卡片、节点图烘的贴图、地形高度页，Cache Storage 或 IndexedDB 按内容哈希加引擎版本）；编译（节点图参数放 uniform 已做；记录场景要的管线、加载时并行预热）。
5. 烘焙流程：结果按内容寻址缓存（切分支、干净检出不重烘）；Basis 编码多线程（2K 贴图现在约 6 分钟）；已有按哈希跳过没变的。
6. 流式内容的粒度：贴图 mip 流式、网格细节层次流式、显存预算加按使用时间卸载。
7. 专项检查：懒加载（脚本按关卡动态 import，原生侧模块按需已有）；实例化（10 万实例压力测试）；热重载（按资源种类量延迟，只重建改了的）。

**验收**：空工程里建 8 公里见方的世界，第 0 步的指标全部达标，进 `verify.ps1`，以后每次推送自动比对。

**结论（11-24 做完）**：0～4、7 做了（数字在 progress-log 第 111～124 条）；5 的 Basis 多线程做了，按内容哈希的烘焙缓存早就有（`bakes.json`）；6 量过不做（开放世界没有位图贴图），网格细节层次的流式、显存预算和按使用时间卸载连同 HLOD 留在"大世界的渲染（二）"；8 公里世界的验收并进"大世界收尾"的验收那一行，预算已经进了回归。

## 世界模拟的底座（路线图"八、世界模拟的底座"，2026-11-24 规划）

用户 11-24："为了更好地进行世界模拟，核心功能和材质扩充和相关可能的基础模块必须尽可能扩充和做完整，并预留第三方模块扩展性，这些要在做好加载与缓存后先做。"这一阶段把原来 P7（玩法系统扩展）里世界模拟要靠的部分和材质扩充提前，P8（世界模拟本身：交通、行人日程）仍是路线图的"让世界活起来"。

**盘点（11-24）**：有的——数据组件和系统、脚本、`game.addSystem`、自定义资源种类和编辑器扩展（`defineEditorExtension`）、调试命令、渲染特性、原生 wasm 插件（extending.md）；虚拟按钮的输入；骨骼动画的播放和混合（ozz）、形变；Jolt 的刚体、角色、约束、浮力；Recast 的导航网格和寻路，原生已有 DetourCrowd（`sn_crowd_*`，引擎还没接）；Web Audio 的声音和空间化；146 种材质的库、节点图、扫描材质导入。没有的——插件包和清单、版本兼容；输入映射和改键；存档；事件总线；统一的世界时钟；数据表；动画状态机、IK、重定向、布娃娃；载具、绳索、可破坏物体、布料软体；碰撞体随格子流式；状态树或行为树、感知、环境查询、智能物体、海量实体的模拟层；声音事件和发声管理；分层材质、材质实例、通用的状态层。

**步骤**（每步做完在编辑器和 MCP 里都能用，有字段描述、热重载、样例和测试）：
1. **第三方扩展**：插件包（npm 包，`package.json` 的 `stride` 字段或 `stride.plugin.json`）声明贡献点——引擎侧（组件和系统、脚本、资源种类和烘焙、渲染特性、调试命令）、编辑器侧（面板、视口工具、属性的字段描述、库的条目、MCP 工具）、原生侧（wasm 模块），兼容的引擎版本范围（照 Godot `.gdextension` 的最低和最高版本）、依赖和加载阶段（照虚幻 `.uplugin` 的模块加载阶段）；工程的 `stride.project.json` 列启用的插件，编辑器有插件列表；引擎和编辑器的公开接口出 API 报告、按语义化版本管、改了留弃用期。现有的扩展点改成走同一套登记，示范插件放 `apps/` 外的独立包。
2. **玩法的基础模块**：输入映射（11-24 做了：`.input.json`、`game.input.actions`，动作和轴、几张映射叠、改键和存下改的键、手柄；触摸的虚拟摇杆以后加）；事件总线（11-24 做了：`game.events`，有类型的命名事件，脚本、系统、时间轴、调试命令都能发和收）；世界时钟和日历（11-24 做了：`game.clock`，日夜循环跟着它，以后的行人日程、营业时间用它的定时；列车、天气的过渡仍按游戏时间）；有类型的数据表（`content/schema` 写的表格资源，编辑器里表格编辑）；存档和世界状态的持久化（组件按字段描述序列化，格子卸载时记下改动、读回来时套上）。
3. **物理和动画**：载具（Jolt 的轮式车约束：引擎、变速、悬挂、轮胎摩擦，接进 fork；车身的损伤）、布娃娃（骨骼对应碰撞体和约束，从动画过渡到物理再爬起来）、绳索和电线、可破坏的物体（烘焙时预切分，约束受力断开）、布料和软体（Jolt 的软体）、碰撞体跟着世界格子流式、远处物理的降级；动画状态机和混合树（资源加编辑器的节点图）、IK（两段骨、看向、脚贴地、全身）、重定向、动画按距离降频。
4. **AI 和导航**：导航网格按格子分块烘焙和流式加载、动态障碍；人群的局部避让（接上原生的 DetourCrowd）；状态树（照虚幻 StateTree，资源加编辑器的节点图，可选行为树）、感知（视觉、听觉）、环境查询（打分选点）、智能物体（"人可以用"的东西声明槽位和动作）；海量实体的模拟层（照虚幻 Mass：按处理器成批跑的数据组件，按距离降低模拟和表现的细节）。
5. **声音**：事件和参数的数据模型（脚本发"脚步"加地面和速度参数，资源里定随机、层、开关）、同时发声的个数和优先级、虚拟化、遮挡和传播（用光追场景的射线）、环境声区。
6. **材质扩充**：库补全世界模拟要的类别（路面和标线、车漆、汽车玻璃、轮胎橡胶、布料、皮革、植被、建材、塑料、金属），数值对照 Physically Based 数据库（真实材质的 PBR 值）和 EPFL RGL 的实测 BRDF；分层材质（清漆、多层车漆、水膜、灰尘按层叠，照虚幻 Substrate 的叠层，而不是参数混合）；材质实例（引用一个材质、只改参数，按种子变化，批不拆）；湿、脏、旧、雪的状态层对所有材质通用（现在只有一部分走 `surfaceWeather`）。
7. **验收**：见路线图那一行。

**参考**：虚幻 5 的 Mass、StateTree、Smart Objects（City Sample 的人群和车流，Epic 的 City Sample 文档）；Godot 的 GDExtension 清单；虚幻的插件描述；Bevy 的 Plugin 和 PluginGroup；Physically Based 数据库（physicallybased.info）；EPFL RGL 材质库；虚幻 Substrate。
