# 原则（用户 2026-11-19 定，之后陆续补充）

> 原路线图的"原则"一节（2026-11-22 从 docs/roadmap.md 挪出来，内容没改）。文中的"第一节""第二节"在 [scope.md](scope.md)，"第三节"到"第五节"在 [stages.md](stages.md)，"进度"是 [roadmap.md](roadmap.md) 的大表。

- **有意义的功能都尽量做**：判断意义不大的可以不做（写明理由）；Stride 没有的功能可以加，参考虚幻、Unity、Godot；WebGPU 没有的硬件功能用计算着色器模拟（比如软件光追）。
- **要有做 3A 开放世界的潜力**（用户 2026-11-19）：
  - 架构上的选择不能给规模设上限：世界的大小（几十公里见方）、同时存在的实体（上万个会动的、上百万个静止的）、内容的体量（装不进内存和显存，只能流式加载）、团队的规模（很多人同时改同一个世界）。现在做小样例时就按这个标准选数据结构和接口，不留"以后重写"的坑。
  - 这类游戏的引擎用到的技术按方面列在第二节，逐项写明我们已有什么、缺什么、在 Web 上怎么做、放在哪个阶段。
  - 引擎有潜力不等于能做出这样的游戏：它们是上千人、多年的内容。我们验收的是技术演示级的切片（一个城市街区、一片几公里见方的野外、一段过场），素材靠程序化生成和公开授权的资源。
- **帧率的目标：在这台机器上稳定运行 4K 30 Hz 和 1080p 30 Hz**（用户 2026-11-24："修改项目目标以稳定运行4k 30hz和1080p 30hz的画面为目标"）：
  - 这台机器是 Xeon 18 核（单核慢）加 RX 9070 GRE（同 2026-11-22 的"以这台机器为目标、弱设备不管"）。两个分辨率都是原生分辨率渲染，同下一条，上采样不算。
  - "稳定"按每帧算：CPU 和 GPU 每帧都在 33.3 毫秒以内，量的是 p99 和最慢的帧，不只看平均；流式加载、着色器编译、物理和 AI 的峰值也不能把一帧顶出 33.3 毫秒（不卡顿）。
  - 预算按这个分：33.3 毫秒是一帧的上限，各系统的预算从里面分，留出余量给峰值；画质的取舍（光追的射线数、降噪、阴影、体积效果）以 4K 下守住 33.3 毫秒为准，省下来的不必再压到 60 或 120 Hz。
  - 取代以前文档里按 165 Hz（每帧约 6 毫秒）、60 Hz 估的帧预算；高刷新率的屏上照样能跑得更快，但不再是验收的标准。
- **性能靠算法和数据，不靠降分辨率**（用户 2026-11-19）：
  - 性能优化指的是少做没用的功（剔除、LOD、缓存、只更新变了的部分、分帧摊开）、把同样的功做得更快（数据导向的内存布局、批处理、并行、SIMD、放到 GPU 上）、不卡顿（流式加载和着色器编译不占帧），不是把渲染分辨率降下来再放大。上采样和动态分辨率只是玩家可选的开关（D14），不计入"达到帧时间预算"。
  - 每个系统有预算（毫秒、内存、显存、绘制次数），超了就是 bug；预算和实测值进回归，变慢了要能自动发现。优化先测再改（`stride perf`、`stride cpu-profile`、GPU 时间戳），结论记数字。
  - 各方面具体用哪些办法见第二节"做 3A 开放世界还缺什么"里的"性能"一行。
- **精度：各种类型的值都按需要做到足够高**（用户 2026-11-21）：不只是位置的浮点数——时间、深度、整数、计数、标识、小数、日期、颜色、角度、纹理坐标都算；按场景要求的范围和分辨率定精度，确实没必要的不做（顶点、旋转、缩放、GPU 上的数据不为大世界升精度）；但为了统一、简单，某一类数据统一用一个比较高的精度、损失一些性能是可以接受的（比如位置、世界矩阵、时间一律双精度，不按场景挑）；某种场景下双精度也不够时另想办法（分层的坐标：整数的区块号加区块里的双精度；定点数；按周期取模）。每加一种值先问"范围多大、要分辨到多细、用多久"。审计和还要改的见 decisions.md 的"精度"。
- **核心能力：从零创建大型世界和真实世界模拟**（用户 2026-11-21）：编辑器要能从一个空工程开始，做出几十公里见方的世界（地形、水、道路和轨道、城市和建筑、植被）并让它像真实世界一样运转（日夜、天气、交通、行人），也能把真实地点的数据（地图、高程）导进来。这是系统的核心，排在别的新功能前面（"进度"的 W 组）；新功能先问"对从零造大世界、对模拟真实世界有没有用"。
- **矢量优先，清晰优先**：
  - **矢量资源优先，编辑器只为矢量的格式做创作工具**（用户 2026-11-21）：编辑器的创作和编辑工具围绕矢量的（程序化的、参数化的）资源做，现成的矢量格式不够用就自己定新格式（文本、有字段描述）；别的格式（位图、导入的网格、高斯泼溅、视频、配光曲线这类采样数据）能导入、能放进场景、能在运行时用，编辑器管导入设置和引用，但不为它们做创作或编辑的工具。
  - **各种资源尽量做成矢量的**（用户 2026-11-19 扩大了范围）。"矢量"按广义理解：资源里存的是"怎么生成"（曲线、节点图、规则加种子），运行时按屏幕需要的精度现算并缓存；位图、三角网格、PCM 是"采样的结果"，照样支持，但不是默认。现成的矢量格式不够用时自己设计。
  - **照片级写实要同等可达**：采样数据（扫描的贴图和几何、动作捕捉、人声）是一等公民，在每种格式里都是图的一种叶子节点，和程序化的节点混着用。
  - 每类资源的格式方案在 [vector-assets.md](vector-assets.md)（讨论稿，和用户逐项定）；几何用哪种表示先做实验（"进度"的第 16 项）。
  - 能用矢量表达的东西，默认按矢量在原生分辨率下渲染，任何缩放、任何 dpr 都清晰，其他格式照样支持：
    - 界面和文字：界面的形状、文字的字形轮廓直接在 GPU 上算覆盖率，3D 场景里的文字用 MSDF；
    - 2D 精灵：SVG 精灵按矢量画；
    - 贴图上的图案：SVG 贴图按屏幕上需要的分辨率栅格化，见下面的"矢量贴图"；
    - 编辑器：图标、Gizmo、网格线都用解析的抗锯齿线，粗细恒为整数像素。
  - 资源管线和编辑器优先接受 SVG（导入成贴图、精灵、界面图片），位图照样支持。
  - 画面默认不糊：
    - 按原生分辨率渲染（已定：不封顶分辨率）；
    - 界面在后处理之后、按原生分辨率画，不经过 FXAA 和 TAA；
    - 时间性抗锯齿要配锐化，并保留 MSAA 选项。
- **画在 canvas 里的东西也要有 Web 原生的能力**（用户 2026-11-19 提出）：界面和文字画在 WebGPU 的 canvas 里，浏览器看不到；要同步一层透明的影子 DOM，做法参考 Flutter Web 的 semantics 树、Google Docs 的 canvas 渲染、CodeMirror 和 Monaco 的隐藏输入框：
  - **选中和复制**：每段界面文字在影子 DOM 里有一个位置、大小、字号和画面一致的透明文本元素，浏览器原生的选中、复制、Ctrl+F 查找和翻译插件都能用；选区的高亮由我们自己的渲染器画（读 `Selection` 和 `Range`），和画面一致。
  - **无障碍**：界面控件对应 ARIA 角色（按钮、复选框、滑块、列表、对话框），读出名字、状态、值；焦点顺序和 Tab 键导航和界面的焦点系统同步；屏幕阅读器能读、能操作。
  - **输入**：文本框获得焦点时，把一个隐藏的 `<textarea>` 放到光标位置，拿到输入法（中文、日文）组合输入、手机软键盘、粘贴、撤销；组合中的文字由我们的渲染器画。
  - **系统设置**：跟随浏览器缩放（矢量渲染按新的 dpr 重画）、`prefers-reduced-motion`、`prefers-contrast`、深浅色。
  - 影子 DOM 由 UI 系统按需维护（只在界面变化时更新，布局计算复用），游戏可以关掉；3D 世界里的文字和世界空间的界面默认不进影子 DOM，可以按元素打开。
  - 编辑器本身的界面就是 DOM，天然具备这些能力；视口里的叠加层同上。
- **一站式创作工作台：游戏和线性内容同一套**（用户 2026-11-21）：同一个工程既能发布成游戏，也能导出成片（短视频、剧集）。所以引擎的每样东西要同时服务两边：时间轴既驱动游戏里的过场也是剪片的工具，镜头系统既是游戏相机也是摄影机，渲染既有实时的帧率预算也有逐帧确定、多采样的离线输出。取舍时优先做两边都用得上的。
- **方便 agent 工具创作**（用户 2026-11-21）：编辑器里人能做的每个操作，agent 都能不靠点界面做到（编辑器的接口、命令行、MCP 服务）；资源和场景都是有字段描述（可导出成 JSON Schema）、可以逐行比较的文本；agent 能在无头的浏览器里预览、截图、量性能、导出成片来检查自己的结果；同样的输入出同样的画面（确定的时间步、确定的随机数）。新做的创作功能，同时给人的界面和给 agent 的接口。
- **全流程在编辑器里完成，改了马上看得到**（用户 2026-11-21）：我们和 Stride 不同、要做得更好——编辑器不只是摆场景，资源也在里面创作和编辑（材质、基本形状、UI、声音、贴图，以后是材质图、粒子、动画曲线、地形），从新建工程到试玩不用离开编辑器、不靠手改文件；每一处编辑都热重载，视口里马上看到效果（资源文件改了，用到它的实体就地重建，不重新打开）。新做的功能先问"能不能在编辑器里做、改了能不能马上看到"。
- **目标是比 Stride 做得更好，对齐只是底线**（用户 2026-11-19）：
  - Stride 有的功能，画面要能逐像素对上（有意的偏差除外）；截图比对是用来找我们的错的，不是要把 Stride 的毛病也复刻出来。
  - 每做一项都问两个问题：Stride 在这里哪里做得不好（bug、怪癖、帧率相关、单位不一致、API 难用、慢），我们就改好；我们哪里比 Stride 差（"只支持某种情况"这类限制），就补到不差。留着"比 Stride 差"的限制不算完成。
  - 改之前把受影响的情况想全；有意的偏差在代码里注明"和 Stride 不同：……"，在 docs/decisions.md 记一条。
  - 超出 Stride 的功能用"质量档"开关，对齐模式下关掉。
- **边做边整理**（用户 2026-11-19）：文档和代码的整理是持续执行的一部分，不留到最后。文档只留结论（被取代的决定改写原条目，不留互相矛盾的两条；"进度"每项写结论，细节放 docs/architecture.md、docs/decisions.md 和各工具的 README）；代码按第五节的"代码质量"整理。
