# 矢量化的资源：格式讨论稿（2026-11-19；2026-11-20 用户把下面的问题都照推荐定了，见 decisions.md）

用户 2026-11-19 的方向：我们和别的引擎不同，各种资源尽量做成矢量的；现成的矢量格式效果不好或者没有合适的，可以自己设计；别的常见格式照样支持，但不是默认。讨论里已经定下的三点：

- **"矢量"按广义理解**：资源里存的是"怎么生成"，运行时按屏幕需要的精度现算、缓存。位图、三角网格、PCM 是"采样的结果"。
- **照片级写实要同等可达**：采样数据（扫描的贴图、扫描的几何、动作捕捉、人声）是一等公民，不是兼容用的后门。所以下面每种格式里，采样数据都是图里的一种叶子节点，和程序化的节点混着用。
- **几何先做实验再定**（见最后一节）。

这份稿子给每类资源写出：创作时用什么格式、我们加什么、编译成什么样的运行时格式、照片级写实怎么做到、代价、要用户定的事。

## 共同的约定

- **两层格式**。创作格式是文本（JSON，一个资源一个文件，能比较差异、能合并）；运行时格式由管线编译出来（WGSL 加参数表加二进制的表），按内容哈希缓存。创作格式的节点名字和含义尽量和开放标准一致，这样能和别的工具互相导入导出；运行时格式完全是我们自己的，随引擎改。
- **每个输出声明怎么求值**（对应"性能靠算法"的原则）：
  - `direct`：每帧在表面的着色器里直接算。只给便宜的图用。
  - `page`：按需生成进虚拟贴图的页，缓存着，页没被淘汰就不重算。贵的图默认用它。
  - `baked`：导入时烘成普通贴图（KTX2）。给算不动的设备和对齐 Stride 的模式用。
- **确定性**。影响玩法的结果（碰撞用的几何、地形高度）在 wasm 里生成，同样的输入在任何机器上逐位相同；只影响画面的可以在 GPU 上生成。
- **采样叶子的编码**：贴图是 KTX2（UASTC），网格是量化加 meshopt，和现在一样。

## 一、2D 矢量图：界面图片、精灵、标牌、贴花、表面上的图案

**创作格式：SVG 的一个子集**（路径、填充和描边、线性和径向渐变、裁剪、不透明度、分组和变换）。不认滤镜、脚本、CSS 动画；文字先转成轮廓。

**SVG 不够用的地方，我们补的**：

| SVG 的问题 | 我们的做法 |
|---|---|
| 只有颜色，没有材质。贴在 3D 表面上的标牌、路面标线要有粗糙度、金属度、自发光、凹凸 | 每个形状可以带材质通道：`data-roughness`、`data-metalness`、`data-emissive`、`data-height`（凸起或凹下去的量，自动得出斜边的法线）。标准的 SVG 查看器忽略这些属性，文件仍是合法的 SVG |
| 不能随机访问：着色器没法问"这个 uv 处是什么颜色" | 编译成下面的运行时格式 |
| 没有程序化的填充（噪声、磨损） | 填充可以引用材质图（第二节）的一个输出：`fill="url(#graph:rust)"` |
| 网格渐变没有浏览器实现 | 先不做；要平滑的色彩过渡时用渐变叠加，或者干脆用采样的图 |

**运行时格式（`.vimg`，自己设计）**：一棵"画法"树加一组轮廓，和 OpenType 的 COLRv1 彩色字体是同一个模型（每一层是一个轮廓加一种画法：纯色、线性、径向、扫掠渐变，层之间按顺序合成）。轮廓全部转成二次贝塞尔，按包围盒量化成 16 位，再按水平和竖直的条带建索引。这正是我们已经有的文字渲染的数据结构（`rendering/text/slug.ts`：字形轮廓按条带存，片元着色器里逐像素算覆盖率），所以一张矢量图在运行时就是"一个多层的彩色字形"：

```
.vimg
  header     版本、画布大小、层数、轮廓数、通道（color / color+pbr）
  layers[]   { 轮廓编号, 画法编号, 混合方式, 变换 3x2 }
  paints[]   纯色 | 线性渐变 | 径向渐变 | 扫掠渐变 | 材质图的输出 | 采样的图；带材质通道时多 4 个 float
  outlines[] { 包围盒, 条带表的偏移, 曲线数 }
  curves     二次贝塞尔的控制点，u16 × 6（相对包围盒）
  bands      每个轮廓的水平、竖直条带 → 曲线编号的表
```

- 在屏幕上（界面、精灵）：直接在片元着色器里算，任何缩放都清晰。
- 在 3D 表面上（标牌、贴花）：放大时直接算（用 uv 的导数定抗锯齿的宽度）；缩小到一个像素盖住很多条曲线时，改成生成进虚拟贴图的页（`page`），不然每个像素要遍历太多曲线。切换点由曲线密度和像素大小决定。
- 层数很多的图（上千条路径的插画）每个像素的开销随重叠的层数涨，这种图默认走 `page`。

**照片级**：一层的画法可以是采样的图（照片、扫描的贴纸），和矢量的层混着用。

**要用户定的**：
1. 运行时用"COLRv1 式的画法树加 Slug 条带"这个模型，SVG 只当创作格式，可以吗？另一个选择是运行时直接解释 SVG 的路径（实现简单，但做不到随机访问，贴不到 3D 表面上）。
2. 材质通道用 `data-*` 属性挂在 SVG 上，还是另放一个旁边的文件？我倾向前者：一个文件，设计软件里改完图属性还在。

## 二、材质和贴图

**创作格式：节点图，节点的名字和含义照 MaterialX 的标准库**（`image`、`tiledimage`、`noise2d`、`fractal3d`、`cellnoise2d`、`worleynoise2d`、`ramplr`、`mix`、`multiply`、`heighttonormal`、`triplanarprojection` 等），存成我们的 JSON。理由：

- MaterialX 是开放标准，USD、Blender、Houdini、Substance 都能导出，素材来源多；
- 它的 WGSL 生成器已经合进主干（随 1.39.4），节点的参考实现可以对着验证；
- glTF 的程序化贴图扩展（`KHR_texture_procedurals`，还是草案）也是把 MaterialX 的图写成 JSON，方向一致。

我们现在的颜色树是 Stride 的 `ComputeColor` 节点，只有十来种。改成 MaterialX 的词汇以后，Stride 的节点在导入时翻译过去（`ComputeTextureColor` → `image`，`ComputeBinaryColor` → `multiply`/`add` 等）。

**MaterialX 里没有、我们要加的节点和信息**（前缀 `st_`）：

| 加什么 | 干什么 | 依据 |
|---|---|---|
| `st_exemplar` | 从一小块采样的样本（比如 512² 的扫描）合成不重复的无限平铺：六边形随机平铺加保持直方图的混合 | Heitz 和 Neyret 2018；Burley 2019 把查找表简化成每通道一维；Mikkelsen 2022 的六边形平铺 |
| `st_vectorimage` | 在图里取一张 `.vimg`（标线、标志、涂鸦） | 第一节 |
| `st_state` | 读材质的状态参数：`wetness`、`dirt`、`wear`、`snow`、`age`，全局的和每个实例的 | 天气和使用痕迹 |
| 每个节点的频带信息 | 生成器知道每个节点输出里最高的空间频率；目标页的一个纹素比它的半个波长还大时，这一层细节淡出（噪声少算几层倍频） | 程序化纹理的带限做法；阈值、锐边这类运算带限不了，生成页时对它们超采样 |
| 输出的求值方式 | `direct` / `page` / `baked`，见"共同的约定" | |

**例子**（创作格式；一面旧砖墙：砖缝是程序化的，砖面是扫描的样本，下雨时变湿）：

```json
{
  "surface": "open_pbr",
  "nodes": {
    "bricks":   { "type": "st_brickpattern", "inputs": { "size": [0.25, 0.065], "mortar": 0.012, "jitter": 0.02 } },
    "scan":     { "type": "st_exemplar", "inputs": { "file": "Scans/brick_face_512", "scale": 0.3 } },
    "mortar":   { "type": "fractal3d", "inputs": { "octaves": 5, "lacunarity": 2.1 } },
    "albedo":   { "type": "mix", "inputs": { "bg": "mortar.color", "fg": "scan.color", "mix": "bricks.mask" } },
    "height":   { "type": "mix", "inputs": { "bg": 0.0, "fg": "scan.height", "mix": "bricks.mask" } },
    "wet":      { "type": "st_state", "inputs": { "name": "wetness" } },
    "rough":    { "type": "mix", "inputs": { "bg": "scan.roughness", "fg": 0.08, "mix": "wet.out" } }
  },
  "outputs": {
    "base_color": { "from": "albedo.out", "evaluate": "page" },
    "normal":     { "from": "height.out", "via": "heighttonormal", "evaluate": "page" },
    "roughness":  { "from": "rough.out", "evaluate": "direct" },
    "height":     { "from": "height.out", "evaluate": "page" }
  }
}
```

粗糙度标成 `direct`：它依赖随时在变的湿度，烘进页里就要每次重算；它本身便宜（一次混合）。别的输出不变，生成一次就一直缓存着。

**运行时格式**：管线在 Node 端把图编译成 WGSL（同现在颜色树的编译，D3），输出三样：

- 表面着色器里调用的函数（`direct` 的输出）；
- 生成页的入口（`page` 的输出：给定页在贴图空间里的矩形和 mip 级，写出反照率、法线、粗糙度金属度遮蔽、高度）；
- 参数表的布局和用到的采样叶子的清单。

**照片级**：三条路，都在同一张图里。
1. 扫描的整套贴图直接当叶子（`image`）：独一无二的东西（雕像、角色的皮肤）走这条，按虚拟贴图流式加载。
2. 会平铺的表面（地面、墙、树皮、布料）用 `st_exemplar`：样本只有原来的几十分之一大，而且不重复。
3. 扫描打底、程序化加变化（湿、脏、磨损、积雪）。

**代价**：生成页要花 GPU 时间，必须分帧、有预算；省的是下载和存储，显存不省。

**要用户定的**：
3. 节点词汇照 MaterialX（推荐），还是在现有的 Stride 颜色树上自己长？照 MaterialX 的话，现有的颜色树编译器要改名和扩充，放在 P4 的着色器系统里一起做。
4. 表面模型用 OpenPBR（MaterialX 现在主推的，层次清楚）加一个"Stride 兼容"的模型（对齐用），可以吗？

## 三、几何

三角网格是几何的"位图"。候选的矢量表示，从保守到激进：

| 表示 | 存什么 | 适合 | 问题 |
|---|---|---|---|
| A. 基础网格加位移 | 粗网格，加一个沿法线的位移函数：程序化的（材质图的高度输出），或者采样的"微图"（每个基础三角形一张按重心坐标排的小高度表，8 到 11 位，分级存，每一级就是一档 LOD） | 岩石、地面、墙、雕像、角色；扫描的模型能自动转成这种（简化出基础网格，再量位移） | WebGPU 没有曲面细分阶段，要在顶点着色器里按"基础三角形编号加重心坐标"现算位置；相邻三角形级别不同时要缝合 |
| B. 细分曲面加位移 | 控制网格（Catmull-Clark 或 Loop），其余同 A | 有机的、要光滑的形状；电影业的标准做法（USD 原生支持） | 细分的求值比 A 贵；不规则点附近要特殊处理 |
| C. 生成器 | 规则、参数和种子：沿样条扫掠（道路、管线、电缆、栏杆）、建筑的文法、植物的参数模型 | 城市、基础设施、植被 | 每种东西要写生成器；美术要学着用规则而不是手捏 |
| D. 隐式曲面（SDF、CSG） | 基本体和它们的光滑并、差 | 可破坏的东西、雕刻式的建模 | 渲染贵（球面步进或者现转网格），细节有限 |
| （对照）簇 LOD 的稠密网格 | 全部三角形加层级（Nanite 的做法，P6 已排） | 任意的扫描网格 | 数据量最大 |

我的判断：A 最值得先试。它和扫描数据天然兼容（照片级），位移函数和材质图是同一套东西，存储按公开的数字很小（NVIDIA 的位移微网格每个微三角形 1 到 8 位），而且微图自带 LOD。C 和 A 可以叠加（生成器输出基础网格，细节靠位移）。B 的收益要看 A 之后还差多少。D 先不做。

**实验**（用户 2026-11-19：做实验再定）。素材：本机 three.js 示例里的扫描模型（Lee Perry-Smith 的头、Lucy、龙，1.8 万到 13 万三角形），加上斯坦福公开的两个稠密扫描（龙 87 万、佛像 109 万三角形，下载在 `C:/code/testdata/stanford`）。

| 编号 | 问什么 | 怎么做 | 量什么 |
|---|---|---|---|
| E1 存储 | 同样的几何误差下，A 比稠密网格小多少 | 稠密网格用 meshopt 简化成几档基础网格；每个基础三角形细分 k 级，沿插值的法线向原网格打射线量位移（Jolt 的射线，Node 里就能跑），量化成 8 位。对照：现在管线的量化加 meshopt | 压缩后的字节数（brotli）；重建的网格到原网格的距离（均方根和最大值，按包围盒对角线归一） |
| E2 运行时 | 顶点着色器里现算位置，比直接画同样多的三角形慢多少；LOD 切换有没有裂缝 | `apps/bench` 里加一个用例：按重心坐标的网格图案实例化绘制，顶点着色器取基础三角形的三个顶点和微图；每个基础三角形按屏幕上的边长选级别，边上取相邻两边较低的一级 | 帧时间（GPU 时间戳）对比同样三角形数的静态网格；显存；逐级切换时截图找裂缝 |
| E3 程序化位移 | 位移用材质图的高度输出时，近看比法线贴图好多少、贵多少 | 一面砖墙：平面加第二节例子里的图，对比同一张图只出法线 | 掠射角下的轮廓（截图）；帧时间 |
| E4 生成器 | 现生成和下载哪个快 | wasm 里沿样条扫掠出一公里的路和护栏 | 生成时间；对比下载同样网格（按 10 Mbps 算）的时间 |

**判定**：E1 里 A 在相同误差下不到稠密网格的三分之一大，并且 E2 的帧时间不超过静态网格的 1.3 倍、没有裂缝，就把 A 定为有位移的表面的默认表示；否则它只当可选项，默认仍是簇 LOD 的网格。结果和数字写回这份文档。

### E1 的结果（2026-11-19）

工具：`node packages/pipeline/experiments/displacement-storage.ts <模型>`。普通网格和基础网格的位置都量化成 16 位、meshopt 编码再 brotli；位移 8 位，按层级预测存残差再 brotli。误差是两边互相取样本点量最近距离，除以包围盒的对角线，报均方根和平均两种（均方根被少数差得远的点主导，薄的部位、洞的边上两种表示都差；平均说的是表面大部分地方）。"同误差的普通网格"是把原网格用 meshopt 简化到误差相同时的大小（在相邻两档之间插值）。

**位移怎么量化**（试了三种，定下第三种，运行时的格式和它一致）：

1. 全模型一个范围、8 位：范围被个别很大的位移撑大，步长跟着变粗。稠密的扫描上误差降不到 0.026% 以下。
2. 每个基础顶点一个范围（三角形里按重心坐标插值，NVIDIA 的位移微网格也是这样）、范围收到最紧：步长比需要的细得多，存下来的是噪声，体积是第一种的三到四倍。
3. **步长是参数**（占对角线的 0.02% 到 0.2%），顶点的范围不到 255 步的放宽到 255 步、下界对齐到 32 步的格子：误差由步长定，个别大位移的地方步长自己变粗，顶点的范围存成两条整数流、几乎不占地方。

每个模型最好的配置（按均方根和按平均各取最好的一个）：

| 模型（三角形数） | 位移的配置 | 大小 | 均方根 / 平均误差 | 同误差的普通网格 | 比值 |
|---|---|---|---|---|---|
| Lucy（100,000） | 基础 1/16，细分 2 级，步长 0.05% | 34.2 KB | 0.0207% / 0.0146% | 66.1 KB（均方根） | 0.52 |
| | 基础 1/64，细分 3 级，步长 0.05% | 23.7 KB | 0.0334% / 0.0182% | 49.3 KB（平均） | 0.48 |
| 龙（134,995） | 基础 1/64，细分 3 级，步长 0.05% | 24.2 KB | 0.0258% / 0.0146% | 35.5 KB / 38.7 KB | 0.68 / 0.63 |
| Lee Perry-Smith 的头（17,684） | 基础 1/16，细分 2 级，步长 0.10% | 6.5 KB | 0.0533% / 0.0329% | 11.8 KB / 12.4 KB | 0.55 / 0.53 |
| 地牢场景（72,137，不是扫描，硬边多） | 基础 1/16，细分 2 级，步长 0.20% | 18.5 KB | 0.197% / 0.076% | 30.2 KB / 29.5 KB | 0.61 / 0.63 |
| 斯坦福的龙（871,306，稠密扫描） | 基础 1/64，细分 3 级，步长 0.05% | 108.8 KB | 0.0215% / 0.0112% | 100.0 KB（均方根） | 1.09 |
| | 基础 1/256，细分 4 级，步长 0.02% | 117.7 KB | 0.0291% / 0.0059% | 141.5 KB（平均） | 0.83 |
| 斯坦福的佛像（1,087,474，稠密扫描） | 基础 1/64，细分 3 级，步长 0.20% | 63.2 KB | 0.0391% / 0.0276% | 56.1 KB（均方根） | 1.13 |
| | 基础 1/256，细分 4 级，步长 0.02% | 146.0 KB | 0.0274% / 0.0065% | 142.9 KB（平均） | 1.02 |

对照：原网格不简化时是 20 到 25 位每三角形（Lucy 299.7 KB，斯坦福的龙 2167 KB）；位移本身是 1 到 3 位每个微三角形，和 NVIDIA 公布的范围一致。

**读法**：

- **没达到"三分之一"的线，哪个模型都没有**。十几万三角形以下的模型上是同误差普通网格的 0.5 到 0.7 倍；稠密的扫描上和普通网格持平（0.8 到 1.1 倍）。
- **稠密的扫描反而没有优势**（和原先的猜想相反）。这两个扫描的三角形比它们的细节多得多：meshopt 简化到 1/16（1.5 位每个原三角形）平均误差才 0.005%。自适应的简化把三角形留给有细节的地方，均匀细分的微图在平的地方白白采样，每个采样点再省也有一位上下的底。
- **基础网格太粗就失控**：1/256 以下，沿法线的位移够不到原表面（薄的部位、凹进去的地方，射线打空或打到别的面），均方根误差是普通网格的几倍；最大误差也普遍比同样均方根的普通网格大。
- **位数多了没用**：误差是采样和投影方向决定的；步长比 0.02% 再细，多出来的位只存噪声。

**这个比法没算进去的**：

1. **保留全部三角形时**（照片级的近景要的是表面细节的着色，不只是轮廓的几何误差；Nanite 这类做法就是全留）：斯坦福的龙全留是 2167 KB，位移（87 万个微三角形，平均误差 0.011%）是 108.8 KB，20 比 1。普通网格要做到这个大小得简化到 1/20 再配一张法线贴图；法线贴图多大没有量，按 1024 见方、压缩后几百 KB 估，比这份位移大。
2. **LOD**。普通网格还要存一整条 LOD 链或者簇层级（总量大约是最细那一级的 2 倍），微图的粗级别就是细级别的前缀，不用另存。
3. **显存和运行时**：见 E2。
4. **构造方法是最朴素的**：基础网格直接用 meshopt 简化，位移方向用顶点法线。NVIDIA 的 Micro-Mesh Construction 专门优化基础网格和每个顶点的位移方向，论文里的例子是 15 比 1（和上面第 1 条是同一种比法）。

### E2 的结果（2026-11-19，第一部分：统一的细分级别）

页面：`apps/bench` 的 `displacement.html`（`node tools/run-page.ts http://localhost:5182/displacement.html displacementResults --error displacementError`），数据用 E1 的工具加 `--export` 导出。Lucy，基础网格 1560 个三角形，细分 3 级（每个基础三角形 64 个微三角形），位移 8 位（每个基础顶点带自己的位移范围，三角形里插值）。两条路径画同样的三角形、同样的片元着色器：

- **位移**：一个基础三角形一个实例，顶点缓冲只有细分图案的格点 (i, j)；顶点着色器取三个基础顶点和法线、插值、按格点的编号取位移。
- **静态**：重建好的顶点和下标。

RTX 3050 笔记本，1280×720，GPU 时间用时间戳查询量（每档 40 帧取中位数）：

| 物体数 | 三角形 | 位移 | 静态 | 比值 |
|---|---|---|---|---|
| 1 | 99,840 | 0.209 ms | 0.210 ms | 1.00 |
| 4 | 399,360 | 0.799 ms | 0.784 ms | 1.02 |
| 16 | 1,597,440 | 3.342 ms | 3.368 ms | 0.99 |
| 64 | 6,389,760 | 11.561 ms | 11.723 ms | 0.99 |

- **帧时间没有可测的差别**（判定线是 1.3 倍）。顶点着色器里多出来的几次缓冲读取和插值，相对几百万个小三角形的光栅化可以忽略。
- **画面一致**：两条路径的画面 921,600 个像素里没有一个差超过 2/255，格点编号的算法（顶点、边、内部三种情况）是对的，相邻的基础三角形之间没有缝。
- **显存**：位移这条路径一共 122 KB（基础顶点和法线、每个三角形的编号表、位移、细分图案），静态网格只算位置就要 1754 KB，按引擎的顶点格式是 1949 KB：小 14 到 16 倍，而且位移的那份已经含了全部细分级别。

### E2 的结果（2026-11-19，第二部分：每个基础三角形各选一级）

代码在 `apps/bench/src/displacement-lod.ts`，同一个页面接着跑。64 个 Lucy 排成 8×8、透视相机从第一排前面看过去；每帧在 CPU 上给每个物体的每个基础三角形按屏幕上最长的边选级别（让微三角形的边长大约是"目标像素"），按级别排进实例缓冲，每一级一次实例化绘制（细分图案每级一份）。

**缝合**：边上的点属于边、不属于三角形（E1 的采样点编号就是这么排的），所以只要两侧选中同一批点，算出来的就是同一个位置。每条边的级别取两侧三角形里低的那个；顶点着色器把落在边上的格点吸附到这条边的级别有的点上（`snap`：沿边的格点编号按 2^(三角形的级别 − 边的级别) 取整）。每个实例多带 12 位（三条边各 4 位）。

**裂缝怎么查**：背面画成纯红。模型本身有少量背面露出来（烘焙出来的表面在手指、衣褶这些地方自己翻了面），全部用最细一级时是 2096 个红像素，当基准；有裂缝时能从缝里看见后面三角形的背面，红像素会变多。

| 目标像素 | 三角形 | GPU 时间 | 红像素：缝合 / 不缝合 | 和全细的画面的平均差（0..255） |
|---|---|---|---|---|
| （全部最细，静态网格） | 6,389,760 | 10.57 ms | 2096 | — |
| 1 | 6,179,697 | 10.41 ms | 2098 / 2101 | 0.008 |
| 2 | 5,210,253 | 8.21 ms | 2122 / 2222 | 0.176 |
| 4 | 3,519,993 | 4.79 ms | 2122 / 2709 | 1.256 |

- **缝合管用**：不缝合时红像素比基准多出最多 613 个，缝合以后和基准差 26 个以内。两侧用的是同一批采样点，没有 T 形接头，这一点是构造上保证的，像素数只是旁证；剩下的 26 个没有逐个追查（轮廓上级别变了、露出的背面会跟着变；也可能有下一条说的末位误差）。
- **正式做时要补的一点**：两侧算的是同一个点，但着色器里各按自己的顶点顺序插值，编译器把乘加并成一条指令以后结果可能差最后一位。要按顶点编号排好顺序再插值，让两侧逐位相同。
- **时间跟着三角形数走**：三角形减到 55%，GPU 时间减到 45%；按级别分批没有带来额外的开销。
- **选级别不能照这个写法上线**：JavaScript 里逐个三角形算，10 万个基础三角形要 15 到 30 毫秒。正式做时先按物体选（远处的物体整个用一级，不逐三角形），只有近处的物体逐三角形，放进 wasm 或者计算着色器，而且相机没怎么动时不重算（"没变就不做"）。

### E3 的结果（2026-11-19：程序化的位移）

页面：`apps/bench` 的 `procedural.html`（`node tools/run-page.ts http://localhost:5182/procedural.html proceduralResults --error proceduralError`）。一面 4 × 2 米的砖墙，高度是程序化的函数（砖、灰缝、每块砖高低不同、表面的噪声），灰缝到砖面 12 毫米。先把它求值成一页贴图（高度、砖的遮罩、法线，2048 × 1024，2 毫米一个纹素，带 mip）：这就是第二节说的"按页求值"，**求值一页 11 到 12 毫秒**。三条路径都采这一页，着色相同：

- **法线**：一个平面，法线取自这一页；
- **视差**：同一个平面，片元着色器里沿视线在高度场里步进找交点（视差遮蔽映射，16 步或 48 步，再二分 4 次）；
- **位移**：平面细分成均匀的格子，顶点着色器里采高度抬起来。

RTX 3050 笔记本，1280×720，GPU 时间（三轮取最小）；"差"是和最细的位移（2 毫米一格，400 万三角形）的画面比，平均每通道差多少（0..255）：

| 路径 | 三角形 | 正面 2.2 米 | 贴着墙面的掠射角 | 0.3 米斜着看 |
|---|---|---|---|---|
| 法线 | 2 | 0.17 ms，差 6.2 | 0.06 ms，差 6.7 | 0.09 ms，差 9.8 |
| 视差 16 步 | 2 | 1.02 ms，差 0.9 | 0.38 ms，差 1.1 | 0.56 ms，差 1.1 |
| 视差 48 步 | 2 | 2.18 ms，差 0.9 | 0.80 ms，差 1.0 | 1.18 ms，差 1.1 |
| 位移，16 毫米一格 | 62,500 | 0.42 ms，差 2.0 | 0.14 ms，差 2.8 | 0.17 ms，差 3.6 |
| 位移，8 毫米一格 | 250,000 | 0.59 ms，差 1.2 | 0.40 ms，差 1.8 | 0.30 ms，差 2.3 |
| 位移，4 毫米一格 | 1,000,000 | 1.61 ms，差 0.5 | 1.63 ms，差 0.8 | 1.05 ms，差 1.0 |
| 位移，2 毫米一格 | 4,000,000 | 7.59 ms | 6.11 ms | 4.31 ms |

- **只出法线差得明显**（6 到 10）：灰缝没有深度，斜着看砖不挡灰缝，越近越假。
- **同样的画面质量，位移和视差的开销在同一档**：差 1 上下时，视差是 0.4 到 1.0 毫秒，位移（4 到 8 毫米一格）是 0.3 到 1.6 毫秒；两者都是法线的几倍到十几倍。位移多给的是真的几何：轮廓、深度（和别的物体相交、阴影贴图都对），视差给不了。
- **均匀的格子是最笨的排法**：2 毫米一格的 400 万三角形绝大部分小于一个像素。配上 E2 第二部分的按屏幕大小选级别，三角形数跟着画面走（一个像素一个上下），开销就落在表里 4 毫米那一行附近，远处自然退回平面加法线。
- **不占存储**：高度本来就是材质图的一个输出，法线也要从它来；位移只是多采一次。
- 没量的：比一个像素还小的三角形对光栅化不友好（Nanite 用计算着色器里的软件光栅化解决，WebGPU 里代价大），所以级别要选在"一个像素一个三角形"以上；阴影里再画一遍的开销。

### E4 的结果（2026-11-19：生成器）

工具：`node packages/pipeline/experiments/sweep-generator.ts [--length 1000] [--spacing 0.5]`。一公里的路：中心线是过 21 个控制点的 Catmull-Rom 样条，路面（9 个点的横截面）和两侧的 W 形护栏（各 9 个点）沿它扫掠，护栏的立柱 4 米一根。对照是把生成出来的网格照管线的做法压缩（50 米一段，位置 16 位、法线 8 位、UV 16 位，meshopt 再 brotli）。

| 沿路的间隔 | 三角形 | 描述 | 生成 | 网格（压缩后） | 按 10 Mbps 下载网格 |
|---|---|---|---|---|---|
| 0.5 米 | 102,416 | 598 字节 | 11.3 ms | 198.2 KB | 162 ms |
| 2 米 | 28,576 | 601 字节 | 5.4 ms | 101.5 KB | 83 ms |

- **描述比网格小两个数量级以上**（339 倍、173 倍），而且和取多密无关：间隔是参数，近处密、远处疏只是换个数再生成一遍，不用另存 LOD。
- **生成比下载快一个数量级**（14 到 15 倍），这还是没优化的 JavaScript（逐个 push 进数组）；下载完的网格另外还要解码。放进 wasm、直接写进顶点缓冲会更快。
- 显存里两边一样大（1.6 MB）：生成器省的是下载量和磁盘，不是显存。
- 没量的：生成放在哪个线程、流式加载时一帧能生成多少（P6 做开放世界时按预算排）；道路和地形的贴合、路口这些真正难的规则不在这个实验里。

### 结论（2026-11-19，按事先定的判定线）

| 实验 | 判定线 | 结果 |
|---|---|---|
| E1 存储 | 同误差下不到稠密网格的三分之一 | **没过**：0.5 到 0.7 倍（十几万三角形以下），稠密扫描上持平 |
| E2 运行时 | 帧时间不超过静态网格的 1.3 倍、没有裂缝 | **过了**：1.0 倍；缝合以后红像素和基准持平；显存小 14 到 16 倍 |
| E3 程序化位移 | （没定线） | 同样画面质量下和视差遮蔽一个档次的开销，多出真的轮廓和深度，不占存储 |
| E4 生成器 | （没定线） | 描述比网格小两个数量级以上，生成比下载快一个数量级 |

按判定线，**"基础网格加采样的位移微图"不当任意几何的默认表示**：把扫描数据转成它，下载量省不到三分之一，稠密的扫描上不省。任意拓扑的稠密模型默认仍是簇 LOD 的网格（P6 已排）。

位移这条路留着，用在它确实占优的两处：

1. **位移由材质图给出的表面**（地面、岩石、墙、地形）：不占存储（E3），运行时没有额外开销、LOD 自带、显存小一个数量级（E2）。这是"矢量"意义上最干净的几何细节：基础网格加一张图。地形（第四节）本来就是这个形状。
2. **规则生成的几何**（道路、护栏、管线、建筑的构件）：默认存规则和参数，加载时生成（E4），不存网格。

采样的位移微图（扫描来的细节）作为可选项保留：要保留全部细节时它是 20 比 1，和"简化的网格加法线贴图"是同一个定位，等 P6 做簇 LOD 时再和它实测比一次（那时两边都有完整的运行时）。

**要用户定的**：上面这个"默认是簇 LOD 的网格，位移只用在材质图驱动的表面和地形，规则几何用生成器"的分工是否照此定下；以及第一、二节里那四个格式问题。

## 四、地形和摆放

- **地形 = 分层的描述**，按需求值成高度页：
  1. 程序化的底（噪声图加侵蚀的参数）；
  2. 矢量的地物：样条（山脊、河道、道路，各带横截面曲线）、多边形（湖、压平的地块）；
  3. 稀疏的采样残差：手工雕刻的改动，或者真实世界的高程数据（照片级和真实地点靠这一层）。
  高度在 wasm 里确定地求值（碰撞要用），贴图层在 GPU 上生成进虚拟贴图。
- **摆放 = 规则加种子**（密度图加筛选条件，在 GPU 上生成实例），只有手摆的东西才逐个存。

格式上这两样都是"图"，节点词汇是我们自己的（没有现成标准），放到 P6 做的时候再细化。

## 五、别的

- **动画**：本来就是曲线。动作捕捉是采样数据，导入时拟合成压缩的曲线。
- **声音**：撞击、脚步、引擎、风雨这类可以用合成图（模态合成、颗粒合成），随 P7 的音频做；人声和音乐是采样的。
- **光照**：能用探针和实时全局光照的地方不烘光照贴图。
- **天空**：物理天空（P4），不用 HDR 贴图当默认。
