# 预制体在场景文件里怎么表示（用户 2026-11-20 定：B，四个问题都照推荐）

**做到哪了**：加载器做了（`content/prefabInstances.ts`，ContentManager 加载场景、预制体、编辑器建场景和更新场景时展开；实例就是预制体的根，不多出容器实体，导入的场景层级和 Stride 的一样）；编辑器里的显示和编辑、导入器的转换还没做。覆盖的值里的资源路径，移动资源时还不跟着改写。

**定下来的**：场景里只存引用和差异（B）；实例成员的 id 由实例 id 和预制体里的实体 id 拼出来；列表项按情况分（固定位置的按下标、脚本按类型名、能增删的列表整个覆盖）；导入器把 Stride 的实例转成引用，场景文件里的值全部当覆盖、再去掉和预制体相同的。下面是当时的方案和考虑。

2026-11-20 写。路线图 P3 的"预制体"要先定文件格式：场景里的一个实例怎么记、预制体改了实例怎么跟、实例上改的东西存在哪。这里给两种做法、我的推荐和要用户定的几个问题。定了以后再做编辑器里的预制体编辑和导入器的转换。

## 现在是什么样

- 预制体文件（`<路径>.prefab.json`）和场景一样，是一张实体列表；脚本运行中用 `content.load(assets.prefabs.…)` 加载、`instantiate` 建出来。
- 场景文件里**没有**和预制体的联系：导入器把 Stride 场景里的实例展开成普通实体，照场景文件里存的值（见 decisions.md 2026-11-19 的"预制体的实例照文件里的值"）。所以现在改了预制体，场景里的实例不跟着变；编辑器里也看不出哪些实体是哪个预制体的实例。

## 两种做法

### A. 照 Stride：场景里存实例的全部值，加上"来自哪里"和"哪些改过"

每个实例成员存完整的实体（和现在一样），另记它对应预制体里的哪个实体、属于哪个实例，以及改过的字段（Stride 在 YAML 的键名后加 `*`）。预制体改了以后由编辑器把没改过的字段同步进每个场景文件。

- 好处：加载场景不用读预制体，加载器不变；文件自己就是完整的。
- 坏处：
  - 预制体一改，所有用到它的场景文件都要重写（开放世界里是成千上万个文件，版本库里一堆无关的改动，多人同时改必冲突）。
  - 同步靠编辑器，编辑器以外改了预制体（版本库合并、脚本生成）场景就悄悄过时。Stride 自己的样例就是这样：CSharpIntermediate 的一半实例对应的预制体部件已经不在了，TPP 的柱子改过的碰撞体高度没带标记——标记不可靠，同步时会把改过的值冲掉（那次我们试过照 Game Studio 合并，只能撤掉）。
  - 每个实例都存一份全量，场景文件大。

### B. 场景里只存引用和差异（推荐）

实例在场景里是一个实体，带着 `prefab`：引用哪个预制体、在预制体之上改了什么。成员不展开存，加载时由预制体合并出来。虚幻（属性按原型存差异）、Unity（PrefabInstance 加修改列表）、Godot（实例加改过的属性）都是这一种。

```json
{
 "id": "7c1e…",
 "name": "Enemy (3)",
 "parent": "a90b…",
 "position": [4, 0, -2], "rotation": [0, 0, 0, 1], "scale": [1, 1, 1],
 "components": {},
 "prefab": {
  "path": "Game/Prefabs/Enemy",
  "set": [
   { "entity": "f02d…", "path": ["components", "scripts", "Game.Health", "props", "max"], "value": 120 },
   { "entity": "91aa…", "path": ["components", "model", "materials", 0], "value": "Game/Materials/Red" }
  ],
  "removed": ["3b7e…"]
 }
}
```

- `prefab.path`：预制体的内容路径（资源之间按路径引用，用户 2026-11-20 定）。
- 实例自己（这个实体）是预制体的根；它的 `position`、`rotation`、`scale`、`name`、`parent` 是实例自己的，不算覆盖，组件是根的（加上覆盖，再加上实例自己写的组件）。
- 预制体有几个根时（Stride 的预制体可以有），一个实例只放其中一个，`prefab.root` 写是哪个（预制体里的 id）；同 Stride 把每个根各自放进场景，不多出一个容器实体（多出来的话，导入的场景层级和 Stride 不一样，按层级找实体的脚本会变）。
- `set`：在预制体某个实体（`entity` 是它在预制体文件里的 id）的某条路径上改成的值，和场景文档的 `set` 修改同一个形状，编辑器里改一个实例成员就是加一条。
- `removed`：这个实例不要预制体里的哪些实体（连后代）。
- 实例里加的实体：普通实体，`parent` 写成实例成员的 id（见下一条），不放进 `prefab` 里。
- **实例成员在场景里的 id 由两段拼出来**：`<实例的 id>/<预制体里实体的 id>`，不存。场景里别的东西（约束的另一个物体、脚本属性里的 `$entity`、`UIElementLink` 的目标）引用实例成员时就写这个 id；预制体改了、加了实体，id 不变。
- **嵌套**：预制体文件里也可以有实例（同样的写法），加载时一层层合并；成员 id 一层层拼（`实例/嵌套实例/实体`）。引用成环时报错。
- **加载**：同一个预制体合并一次、所有实例共用（只是建实体时套各自的 `set`），和 architecture.md 的"属性的分层、合并和转发"里说的一样。运行时读值是普通读取，不逐层查找。
- **好处**：预制体改了，所有实例自动跟着（没覆盖的字段），不用重写场景文件；场景文件小、改动只在真改了的实例上，版本库里好合并；编辑器里每个值的来源一目了然（预制体给的、实例改的），可以"重置成预制体的值"。
- **坏处**：加载场景要先读它用到的预制体（引用关系里本来就有，资源数据库和预加载已经按引用读）；预制体删了实体、改了结构以后，实例里指向它的 `set` 会落空——编辑器把这些列出来让人清理，加载时跳过并警告，不悄悄改值。

## 要用户定的

1. **用 A 还是 B**。推荐 B：A 的问题正是 Stride 样例里实际出过的毛病，而且和开放世界的规模（大量场景文件、多人协作）冲突。
2. **实例成员的 id 拼出来（推荐）还是存下来**。拼出来不用存、预制体改了也稳定；代价是 id 里带 `/`，别的地方不能假设 id 是 UUID。
3. **列表里的项怎么指**（`set` 的路径经过列表时）：模型的材质槽、向量这类固定位置的按下标；脚本组件的列表按脚本的类型名（同一个实体上每种脚本只有一个，这是我们现在的规则）；碰撞体的形状、约束这类可以增删的列表，推荐整个列表一起覆盖（改一项就存整个列表），不引入 Stride 那样的逐项 id。也可以给这类列表的每一项加 id，按 id 覆盖（architecture.md 当初设想的），文件格式要跟着改。
4. **导入器怎么转 Stride 场景里的实例**：推荐转成 B 的写法，但只记引用、**把场景文件里的值全部当覆盖**（照 Stride 的编译器，不信任覆盖标记），然后去掉和预制体相同的值。这样画面和现在逐像素一样，又保住了和预制体的联系。

定了以后的工作：引擎的加载器（合并、拼 id、嵌套）、场景文档的修改（实例成员的 `set` 落到 `prefab.set` 上）、编辑器（实例在场景树里的显示、"重置成预制体的值"、打开预制体编辑）、导入器的转换、各样例重新导入后截图逐像素比对。
