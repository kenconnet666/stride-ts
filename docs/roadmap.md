# 路线图（2026-11-19 定稿，2026-11-21 目标扩成一站式创作工作台、核心定为从零创建大型世界和真实世界模拟，无人值守执行中）

目的（用户 2026-11-21 扩充）：做一个**一站式的创作工作台**，同一套引擎和编辑器既能产出大型 3A 游戏（GTA 6、荒野大镖客 2、赛博朋克 2077 这一类，见第二节的"做 3A 开放世界还缺什么"），也能方便地做短视频、动画片、电视剧这类线性内容（3A 的画面风格：现在的 3A 大作已经有接近电影的效果，成片就照这个标准）；里面要用到的各种元素——世界、模型、材质、角色、动画、特效、镜头、声音、字幕、界面、逻辑——都能在编辑器里创作和编辑，从新建工程到导出游戏或成片不离开它（第二节的"一站式创作工作台还缺什么"）；人和 agent 工具都能方便地用它创作。底线仍是"比 Stride 做得更好"（用户 2026-11-19 把目标从"对齐 Stride"改成"比 Stride 做得更好"）。**核心能力**（用户 2026-11-21）：编辑器能从零创建大型世界、模拟真实世界；资源矢量优先（见"原则"）。范围一次定下来，之后无人值守地持续执行，用复刻开源游戏、技术演示级的切片和短片来验证。本文件列出 Stride 的全部内容、超出 Stride 要加的功能、每项做不做、按什么顺序做、怎样算完成；取舍见第四节，执行中的决定记在 docs/decisions.md。

盘点依据：
- Stride：`~\IdeaProjects\stride` 的 `sources/`（engine、plugins、editor、assets、shaders、tools）和 `samples/`。
- 别的引擎：虚幻 5.7、Unity 6、Godot 4.6 的公开文档。
- Web 上的现成做法：`C:\code\refs` 里 three.js（2026-11-18 的版本）、Babylon.js、Filament 的 WebGPU 实现，以及 WebGPU 规范的提案状态。

## 原则（用户 2026-11-19 定）

- **有意义的功能都尽量做**：判断意义不大的可以不做（写明理由）；Stride 没有的功能可以加，参考虚幻、Unity、Godot；WebGPU 没有的硬件功能用计算着色器模拟（比如软件光追）。
- **要有做 3A 开放世界的潜力**（用户 2026-11-19）：
  - 架构上的选择不能给规模设上限：世界的大小（几十公里见方）、同时存在的实体（上万个会动的、上百万个静止的）、内容的体量（装不进内存和显存，只能流式加载）、团队的规模（很多人同时改同一个世界）。现在做小样例时就按这个标准选数据结构和接口，不留"以后重写"的坑。
  - 这类游戏的引擎用到的技术按方面列在第二节，逐项写明我们已有什么、缺什么、在 Web 上怎么做、放在哪个阶段。
  - 引擎有潜力不等于能做出这样的游戏：它们是上千人、多年的内容。我们验收的是技术演示级的切片（一个城市街区、一片几公里见方的野外、一段过场），素材靠程序化生成和公开授权的资源。
- **性能靠算法和数据，不靠降分辨率**（用户 2026-11-19）：
  - 性能优化指的是少做没用的功（剔除、LOD、缓存、只更新变了的部分、分帧摊开）、把同样的功做得更快（数据导向的内存布局、批处理、并行、SIMD、放到 GPU 上）、不卡顿（流式加载和着色器编译不占帧），不是把渲染分辨率降下来再放大。上采样和动态分辨率只是玩家可选的开关（D14），不计入"达到帧时间预算"。
  - 每个系统有预算（毫秒、内存、显存、绘制次数），超了就是 bug；预算和实测值进回归，变慢了要能自动发现。优化先测再改（`stride perf`、`stride cpu-profile`、GPU 时间戳），结论记数字。
  - 各方面具体用哪些办法见第二节"做 3A 开放世界还缺什么"里的"性能"一行。
- **精度：各种类型的值都按需要做到足够高**（用户 2026-11-21）：不只是位置的浮点数——时间、深度、整数、计数、标识、小数、日期、颜色、角度、纹理坐标都算；按场景要求的范围和分辨率定精度，确实没必要的不做（顶点、旋转、缩放、GPU 上的数据不为大世界升精度）；但为了统一、简单，某一类数据统一用一个比较高的精度、损失一些性能是可以接受的（比如位置、世界矩阵、时间一律双精度，不按场景挑）；某种场景下双精度也不够时另想办法（分层的坐标：整数的区块号加区块里的双精度；定点数；按周期取模）。每加一种值先问"范围多大、要分辨到多细、用多久"。审计和还要改的见 decisions.md 的"精度"。
- **核心能力：从零创建大型世界和真实世界模拟**（用户 2026-11-21）：编辑器要能从一个空工程开始，做出几十公里见方的世界（地形、水、道路和轨道、城市和建筑、植被）并让它像真实世界一样运转（日夜、天气、交通、行人），也能把真实地点的数据（地图、高程）导进来。这是系统的核心，排在别的新功能前面（"进度"的 W 组）；新功能先问"对从零造大世界、对模拟真实世界有没有用"。
- **矢量优先，清晰优先**：
  - **矢量资源优先，编辑器只为矢量的格式做创作工具**（用户 2026-11-21）：编辑器的创作和编辑工具围绕矢量的（程序化的、参数化的）资源做，现成的矢量格式不够用就自己定新格式（文本、有字段描述）；别的格式（位图、导入的网格、高斯泼溅、视频、配光曲线这类采样数据）能导入、能放进场景、能在运行时用，编辑器管导入设置和引用，但不为它们做创作或编辑的工具。
  - **各种资源尽量做成矢量的**（用户 2026-11-19 扩大了范围）。"矢量"按广义理解：资源里存的是"怎么生成"（曲线、节点图、规则加种子），运行时按屏幕需要的精度现算并缓存；位图、三角网格、PCM 是"采样的结果"，照样支持，但不是默认。现成的矢量格式不够用时自己设计。
  - **照片级写实要同等可达**：采样数据（扫描的贴图和几何、动作捕捉、人声）是一等公民，在每种格式里都是图的一种叶子节点，和程序化的节点混着用。
  - 每类资源的格式方案在 [vector-assets.md](vector-assets.md)（讨论稿，和用户逐项定）；几何用哪种表示先做实验（"进度"的第 16 项）。
  - 能用矢量表达的东西，默认按矢量在原生分辨率下渲染，任何缩放、任何 dpr 都清晰，其他格式照样支持：
    - 界面和文字：界面的形状、文字的字形轮廓直接在 GPU 上算覆盖率，3D 场景里的文字用 MSDF；
    - 2D 精灵：SVG 精灵按矢量画；
    - 贴图上的图案：SVG 贴图按屏幕上需要的分辨率栅格化，见下面的"矢量贴图"；
    - 编辑器：图标、Gizmo、网格线都用解析的抗锯齿线，粗细恒为整数像素。
  - 资源管线和编辑器优先接受 SVG（导入成贴图、精灵、界面图片），位图照样支持。
  - 画面默认不糊：
    - 按原生分辨率渲染（已定：不封顶分辨率）；
    - 界面在后处理之后、按原生分辨率画，不经过 FXAA 和 TAA；
    - 时间性抗锯齿要配锐化，并保留 MSAA 选项。
- **画在 canvas 里的东西也要有 Web 原生的能力**（用户 2026-11-19 提出）：界面和文字画在 WebGPU 的 canvas 里，浏览器看不到；要同步一层透明的影子 DOM，做法参考 Flutter Web 的 semantics 树、Google Docs 的 canvas 渲染、CodeMirror 和 Monaco 的隐藏输入框：
  - **选中和复制**：每段界面文字在影子 DOM 里有一个位置、大小、字号和画面一致的透明文本元素，浏览器原生的选中、复制、Ctrl+F 查找和翻译插件都能用；选区的高亮由我们自己的渲染器画（读 `Selection` 和 `Range`），和画面一致。
  - **无障碍**：界面控件对应 ARIA 角色（按钮、复选框、滑块、列表、对话框），读出名字、状态、值；焦点顺序和 Tab 键导航和界面的焦点系统同步；屏幕阅读器能读、能操作。
  - **输入**：文本框获得焦点时，把一个隐藏的 `<textarea>` 放到光标位置，拿到输入法（中文、日文）组合输入、手机软键盘、粘贴、撤销；组合中的文字由我们的渲染器画。
  - **系统设置**：跟随浏览器缩放（矢量渲染按新的 dpr 重画）、`prefers-reduced-motion`、`prefers-contrast`、深浅色。
  - 影子 DOM 由 UI 系统按需维护（只在界面变化时更新，布局计算复用），游戏可以关掉；3D 世界里的文字和世界空间的界面默认不进影子 DOM，可以按元素打开。
  - 编辑器本身的界面就是 DOM，天然具备这些能力；视口里的叠加层同上。
- **一站式创作工作台：游戏和线性内容同一套**（用户 2026-11-21）：同一个工程既能发布成游戏，也能导出成片（短视频、剧集）。所以引擎的每样东西要同时服务两边：时间轴既驱动游戏里的过场也是剪片的工具，镜头系统既是游戏相机也是摄影机，渲染既有实时的帧率预算也有逐帧确定、多采样的离线输出。取舍时优先做两边都用得上的。
- **方便 agent 工具创作**（用户 2026-11-21）：编辑器里人能做的每个操作，agent 都能不靠点界面做到（编辑器的接口、命令行、MCP 服务）；资源和场景都是有字段描述（可导出成 JSON Schema）、可以逐行比较的文本；agent 能在无头的浏览器里预览、截图、量性能、导出成片来检查自己的结果；同样的输入出同样的画面（确定的时间步、确定的随机数）。新做的创作功能，同时给人的界面和给 agent 的接口。
- **全流程在编辑器里完成，改了马上看得到**（用户 2026-11-21）：我们和 Stride 不同、要做得更好——编辑器不只是摆场景，资源也在里面创作和编辑（材质、基本形状、UI、声音、贴图，以后是材质图、粒子、动画曲线、地形），从新建工程到试玩不用离开编辑器、不靠手改文件；每一处编辑都热重载，视口里马上看到效果（资源文件改了，用到它的实体就地重建，不重新打开）。新做的功能先问"能不能在编辑器里做、改了能不能马上看到"。
- **目标是比 Stride 做得更好，对齐只是底线**（用户 2026-11-19）：
  - Stride 有的功能，画面要能逐像素对上（有意的偏差除外）；截图比对是用来找我们的错的，不是要把 Stride 的毛病也复刻出来。
  - 每做一项都问两个问题：Stride 在这里哪里做得不好（bug、怪癖、帧率相关、单位不一致、API 难用、慢），我们就改好；我们哪里比 Stride 差（"只支持某种情况"这类限制），就补到不差。留着"比 Stride 差"的限制不算完成。
  - 改之前把受影响的情况想全；有意的偏差在代码里注明"和 Stride 不同：……"，在 docs/decisions.md 记一条。
  - 超出 Stride 的功能用"质量档"开关，对齐模式下关掉。
- **边做边整理**（用户 2026-11-19）：文档和代码的整理是持续执行的一部分，不留到最后。文档只留结论（被取代的决定改写原条目，不留互相矛盾的两条；"进度"每项写结论，细节放 docs/architecture.md、docs/decisions.md 和各工具的 README）；代码按第五节的"代码质量"整理。

## 二、超出 Stride 的功能

### WebGPU 现在能做什么、缺什么（2026-11）

- **有**：
  - 计算着色器、间接绘制（`drawIndirect`、`dispatchWorkgroupsIndirect`）、存储缓冲和存储纹理、时间戳；
  - 子组运算（`subgroups`、`subgroup-size-control`）、`shader-f16`；
  - 压缩贴图（BC、ASTC、ETC2）；
  - 32 位原子操作：把深度和编号塞进同一个 32 位值，靠它可以做软件光栅。
  - 2026-11-20 在 Chrome 157、RX 9070 GRE（D3D12）上实测，下面这些都已进正式规范、拿得到（可选特性，要在 `requestDevice` 里要）：
    - `atomic-vec2u-min-max`：`vec2u` 上的 64 位原子 min/max，可见性缓冲（深度在高 32 位、编号在低 32 位）的软件光栅直接能用，不用再挤进 32 位；
    - `primitive-index`：片元着色器里拿三角形编号，可见性缓冲的硬件光栅那一半不用另外传；
    - 立即数（WGSL 的 `immediate_address_space`，`maxImmediateSize` 64 字节）：相当于 push constants，每次绘制的编号不用再走动态偏移；
    - `indirect-first-instance`（间接绘制带 firstInstance，GPU 驱动的实例化要它）、`clip-distances`、`dual-source-blending`、`float32-filterable`、`float32-blendable`、`texture-formats-tier1/2`、`texture-component-swizzle`、`rg11b10ufloat-renderable`、`bgra8unorm-storage`。
  - 限制按适配器给，比规范的默认值大得多（这块卡：单个缓冲和单次绑定的存储缓冲 2 GB，默认 256 MB / 128 MB；2D 贴图 16384，默认 8192；贴图数组 2048 层，默认 256；每个着色器阶段 48 张采样贴图、16 个存储缓冲，默认 16、8；工作组共享内存 32 KB；每个绑定组 1000 个绑定）。`GraphicsDevice` 要的是适配器给的全部限制（2026-11-20 起；之前只拿到默认值，GPU 驱动的场景数据、虚拟贴图的页图集、代替 bindless 的贴图数组都会先撞上），渲染器按 `device.limits` 选路径（手机和集显的限制小，默认值是保底）。可选特性（`shader-f16`、`subgroups`、`atomic-vec2u-min-max`……）等用到它们的功能时再要。
- **没有，要绕开**：
  - 硬件光追（规范里还没有）：用计算着色器遍历 BVH；
  - bindless（还是提案）：贴图图集、贴图数组（上面的 2048 层、48 张），或按材质分批；
  - multi-draw-indirect（不在规范里，Chrome 要开实验标志）：顶点拉取（vertex pulling）加每种材质一次间接绘制；
  - 曲面细分、几何着色器：用计算着色器生成；
  - 稀疏纹理：页表加图集模拟虚拟贴图。
- **说明 Web 上已经做得到的参考（都是 MIT 或 Apache，可以读、可以照着做）**：
  - three.js 2026-11 的 WebGPU 版有：
    - 渲染管线：簇（meshlet）绘制管线、可见性缓冲管线（大三角形走硬件光栅，小三角形走软件光栅）；
    - 光照和全局光照：体素锥追踪全局光照（VXGI）、光探针网格烘焙、BVH 光追的辐射度光照贴图烘焙、路径追踪渲染器（three-gpu-pathtracer）；
    - 屏幕空间效果：SSGI、随机 SSR、TRAA、接触阴影；
    - 场景内容：体积云、海洋、焦散、Gaussian splatting。
  - Babylon.js 9：上千盏灯的分簇光照、节点粒子编辑器、IBL 阴影。
  - EA 的 Gigi 示例：把 tinybvh 的遍历移植到 WGSL，做"软件光追"。
  - meshoptimizer 1.0 的 `clusterlod.h`：类 Nanite 的簇层级 LOD 构建，meshoptimizer 已经在我们的 stride-tools 里。
  - Vello：MIT/Apache，用 WGSL 计算着色器画任意矢量路径。

### 一站式创作工作台还缺什么（用户 2026-11-21 要求补充）

**没变就不做：从浏览器的渲染管线学什么**（用户 2026-11-19 问：DOM 和 CSS 动画为什么几乎不占 CPU 和显卡，游戏里有没有类似的办法）

浏览器省资源靠的不是算得快，是大部分时候根本不算：页面不变就不出帧；变了也只重算脏的那一小块（样式、布局、绘制各有脏标记）；画过的内容按瓦片存成贴图，滚动和 transform、opacity 动画只是在合成线程上把存好的贴图换个矩阵再拼一次；动画是事先声明好的，引擎才能把它整个交给合成线程、不经过脚本和布局。3D 游戏的相机一动整个画面都变，不能照搬，但每一条都有对应的做法：

| 浏览器的做法 | 引擎里对应的做法 | 我们现在 | 阶段 |
|---|---|---|---|
| 没有变化就不出帧 | 按需渲染：场景、相机、动画、输入都没变时不画也不提交，把上一帧留在屏幕上；编辑器的视口、菜单、暂停、回合制的画面大部分时间是静止的。要各个子系统报"我变了"（变换、材质、动画、粒子、UI 各一个版本号） | 每帧都画，哪怕什么都没动 | P3（编辑器最需要），运行时做成 `Game` 的一个模式 |
| 脏标记，只重算变了的部分 | 更新阶段的变化检测：变换只传播动过的子树，系统按组件列的版本号跳过没变的，睡着的物理岛不算（Jolt 已有），看不见或很远的角色动画降频；上传到 GPU 的数据只传变了的那几段 | 世界矩阵每帧整段上传，实例数据每帧重建 | P4 的底座（GPU 上常驻的场景数据，增量更新），P6 之前必须有 |
| 画过的内容存成显示列表和瓦片 | 把不变的绘制命令录下来重放（WebGPU 的 render bundle）；UI 页面画进缓存的贴图，控件变了才重画那一块；静态物体的阴影缓存着，只有动的物体进出才更新；远处的东西换成 impostor；程序化材质的页生成一次就留着 | UI 每帧全部重画；阴影每帧全部重画 | UI 缓存放 P2 收尾（先量它占多少）；其余 P4、P6 |
| 合成线程上的动画不经过脚本和布局 | 能声明的动画就不要逐帧用脚本驱动：风、UV 滚动、序列帧放在着色器里按时间算（CPU 上每个物体零开销）；粒子在 GPU 上模拟；人群的骨骼动画烘成贴图；补间动画成批在原生侧算。渲染放进 Worker 以后，主线程卡住时画面还能按上一次的状态继续动 | 粒子在 CPU 上；脚本逐个对象更新 | P4（GPU 粒子、着色器动画）、P7 |
| 只合成有变化的区域；视频走硬件叠加层 | 固定机位或画面大部分静止时只重画变了的区域；UI 叠在不变的 3D 画面上时不重画 3D | 没有 | 随按需渲染一起做 |
| 看不见的不处理（后台标签页降频、屏幕外的内容跳过） | 剔除要一直做到模拟：屏幕外和远处的东西降低模拟频率或者冻结（P8 的模拟 LOD）；页面在后台或者失去焦点时降到很低的帧率；可以设帧率上限 | 视锥剔除只管渲染；页面隐藏时浏览器自己停 | P4（帧率上限、失焦降频）、P8 |

共同的前提是"保留"：引擎记得上一帧算过什么、哪些输入变了。这和"每帧从头算一遍"的写法相反，所以越早把变化的来源收拢成版本号越好（现在加组件和系统时就该带上）。

**Web 上的硬限制和对策**（2026-11 的状况）：

- **内存**：~~32 位的 wasm 最多 4 GB~~（2026-11-21 实测后换成 64 位：原生模块只出 Memory64 的一份，内存上限 16 GB，是 Chrome、Firefox 给 Memory64 的上限；Jolt 的性能测试单线程慢 7%～12%；正式版 Safari 还不支持，见 decisions.md）。16 GB 也是上限：流式预算照旧要有。
- **显存**：浏览器不告诉页面有多少显存。按画质档位定预算，流式池按预算淘汰。
- **bindless**：WebGPU 的提案还在设计的早中期。继续用图集、贴图数组和虚拟贴图，材质数据放在存储缓冲里按编号取。
- **64 位原子**：不再是障碍，`atomic-vec2u-min-max` 已进规范（见上面"WebGPU 现在能做什么"）。
- **硬件光追**：有 ray query 和加速结构的提案，没有发布。软件 BVH（P5）是基线，遍历的接口留好，硬件可用时换掉。
- **下载和存储**：这类游戏有上百 GB，浏览器的存储配额跟着磁盘走、可能被清掉。对策：内容按块寻址、按需下载（HTTP range）、存进 OPFS，没到的地方先用 HLOD 顶上；完整的体量装在本地要靠原生宿主。
- **原生宿主**（D17）：渲染器只用 WebGPU 的接口，所以同一套 TS 和 wasm 代码可以跑在自带 Dawn 的壳里，没有配额，也能用 Dawn 先于浏览器提供的扩展。

## 三、阶段和验收

每个阶段都以"复刻一批游戏"收尾。验收全部由 agent 用调试 CLI 自动完成，不靠人看：

- **画面**：同一场景、同一相机位置，和桌面 Stride 的截图逐像素比较（`tools/stride-capture` 推广到每个样例）。阈值：每通道平均差 ≤ 1/255，差超过 10 的像素 ≤ 0.5%，有意的偏差写进文档。
- **玩法**：每个游戏一个脚本化的通关或冒烟流程（`stride key`、`mouse`、`step`，加上 `inspect`、`eval` 的断言），放进仓库，回归时重跑。
- **性能**：同一台机器、同一时段，帧时间不比桌面 Stride 慢（用相对值，不受笔记本电源模式影响），另记绝对值和电源模式。
- **工程质量**：类型检查、单元测试、原生测试全过；每个游戏的导入、构建、启动时间和下载体积记入文档。
- **超出 Stride 的画面功能**（没有桌面 Stride 可比）：
  - 光照的近似算法（DDGI、SSGI、光追阴影和反射、AO）：和我们自己的参考路径追踪器收敛后的结果比较，记误差；
  - 每个功能各有一个固定机位的截图回归；
  - 各画质档位有帧时间预算，同时记录电源模式；
  - 矢量渲染：放大 1×、2×、4× 截图检查边缘清晰（边缘过渡宽度不超过 1 个像素），并和 Vello/浏览器自己画的 SVG 比覆盖率。
  - 影子 DOM：用 CDP 的 Accessibility 域读无障碍树，检查角色、名字和画面一致；脚本化地选中、复制文字，用输入法事件输入中文，检查结果。

**两条线怎么交错**：P3（编辑器）的验收做完以后，先做 S1（离成片最近、两边都用得上：时间轴是游戏过场，景深和运动模糊是 P4 剩下的效果），再做 S2（创作工具让后面每个阶段的内容都能在编辑器里做），然后游戏线的 P5（光追和全局光照也是成片画质的上限）、S3、P7 的动画部分和 S4 一起做（角色和动画两边共用）、P6、P8、P9、S5 和 P10 一起做。2026-11-21 用户把"从零创建大型世界和真实世界模拟"定为核心能力：P6 的大部分和 P8 提前成"进度"里的 W 组，接在 G2 之后、别的之前。实际的先后见"进度"开头的总览表。

P1 和 P2 内部不分先后，按"下一个游戏缺什么就做什么"推进，游戏顺序就是上表的顺序。P4 到 P10 的顺序可以按需要调整，但 P5 依赖 P4 的降噪和时间复用基础，P6 的可见性缓冲要等着色器系统稳定，P8 的城市要用 P6 的流式加载和程序化工具、P7 的动画和载具，P9 的头发和衣物要用 P7 的模拟。P4 开头的底座（渲染图、预算、管线预热）不能往后挪：后面每个效果、每种内容都靠它才不卡、才量得出快慢。

## 四、取舍（2026-11-19 用户决定：全部按推荐）

- ~~**D1 范围**~~：已定（用户 2026-11-19），见上面的"原则"。
- **D2 编辑器的时机**：放在 P3（运行时先跟着游戏走），还是从 P1 就和运行时并行？推荐 P3。理由是游戏复刻走 Stride 工程导入器，不依赖编辑器；运行时的组件和资源格式稳定后再做编辑器，返工最少。代价是编辑器晚几个阶段才有。
- **D3 着色器系统**：自定义着色器（.sdsl）怎么办？
  - (a) 我们自己的 WGSL 组合系统（Node 端预编译），样例里的 SDSL 由 agent 手工移植成 WGSL。推荐这个。
  - (b) 在资源管线里跑 Stride 自己的着色器编译器（这个仓库里有新的 SPIR-V 编译器，可以出 WGSL），能直接导入 SDSL，但管线要依赖 .NET。
- **D4 UI 系统**：
  - (a) 照 Stride UI 自己做：布局规则照 Stride，能导入 .sduipage，用矢量渲染器在 WebGPU 上画，屏幕和世界空间都清晰。推荐这个。
  - (b) 用 HTML/CSS 覆盖层，省事，浏览器本身也是矢量渲染，但做不了世界空间 UI 和逐像素比对。
- **D5 脚本**：游戏脚本只用 TypeScript；C# 脚本由 agent 逐个翻译（不做 C# 到 TS 的自动转译器）；编辑器不内置代码编辑器。推荐都选"是"。
- **D6 C# 网页移植版**：停止，只当参考实现。推荐停止。
- **D7 VR**：推迟（WebXR 以后再说），VRSandbox 不在验收清单里。推荐推迟。
- **D8 验证用的游戏来源**：
  - Stride 自带的样例：MIT，能和桌面 Stride 逐像素比，覆盖面全，必做。
  - Starbreach：Stride 官方的大型演示；代码 MIT，美术是 CC BY-NC 4.0，只能本机导入、不能提交进公开仓库。
  - 社区的开源 Stride 游戏，比如 StrideAsteroids。
  - 别的引擎的开源游戏（比如 Godot 的演示项目），要先有编辑器、要手工搬场景，验证的是"用我们的引擎做游戏"而不是"对齐 Stride"。

  - 公开的图形测试场景：Sponza、Amazon Lumberyard Bistro（CC BY）、Khronos 的 glTF 样例。用来验证 P4 到 P6 的画面和性能。

  推荐：P1、P2 只用 Stride 样例；P4 到 P6 加 Starbreach、测试场景和一两个社区游戏；其他引擎的游戏放到编辑器之后（P7）。
- **D9 音频格式**：管线把 .sdsnd 的源文件转成 Opus（WebM 或 Ogg 容器）要用 ffmpeg。
  - (a) 要求本机装 ffmpeg；
  - (b) 用 ffmpeg 的 wasm 版，慢但零安装；
  - (c) 浏览器能解的格式（mp3、ogg、wav）原样复制。
  
  推荐 (c) 起步，(a) 作为可选的压缩。
- **D10 无人值守的边界**：哪些事可以自己定、哪些要停下来等你？推荐：
  - **自己定**：表里已定的事；同一阶段内的实现方式；和 Stride 不同但更好的做法（照记忆里的规矩：想清楚后果、在代码里标"和 Stride 不同"）；原生包发版；提交和推送。决定记进 `docs/decisions.md`，写明理由。
  - **停下来问**：改动这份路线图的范围；公共 API 的大改（比如组件写法）；引入新的重型依赖；要花钱或要账号的事；连续两次修不好的阻塞。
- **D11 编辑器和现代画面谁先**：推荐编辑器在前（P3 再 P4）。烘焙、打光、调大气和特效都要在编辑器里看着调；而且编辑器做出来以后，P4 起的效果都能直接接进编辑器的预览。另一个选择是先做画面，展示效果来得快，但没有编辑器，灯光和特效只能写在代码里调。
- **D12 渲染器的主路径**：GPU 驱动加可见性缓冲（P6）做成以后，是否取代现在的前向渲染做主路径？推荐分档：
  - 对齐 Stride 的模式和低档继续用前向（简单，和 Stride 逐像素对得上，弱显卡也快）；
  - 高档和极高档用可见性缓冲（几何量大时才划算）；
  - 两条路径共用材质和光照代码，由着色器系统生成。
- **D13 全局光照的默认方案**：推荐：
  - 默认用烘焙（光照贴图加光探针），在 Web 上最省，画面也最稳；
  - 高档开 DDGI，配合日夜循环、可破坏场景这类动态光照；
  - SSGI 作为各档都能叠加的细节；
  - Lumen 式和 VXGI 暂不做。
- **D14 上采样和动态分辨率**：照你之前的意思，默认按原生分辨率只做抗锯齿；时间性上采样和动态分辨率做成玩家可开的选项（画质菜单里），不默认打开。
- **D15 多人联网**：Stride 没有。推荐放进 P7：权威服务器用 Node，客户端预测加插值，WebSocket 起步，WebRTC 数据通道可选。另一个选择是不做，交给游戏自己。
- **D16 矢量渲染怎么实现**：推荐两步：
  - P2 先做 UI 和文字需要的部分：圆角矩形、边框、阴影、渐变用解析 SDF；文字按字形轮廓（二次贝塞尔）在片元着色器里算覆盖率，世界空间的字用 MSDF；
  - SVG 精灵和矢量贴图要用到任意路径时，再做 Vello 式的计算着色器路径渲染器（WGSL，参考 Vello 的算法自己写，不引入 Rust 依赖）。

- **D17 原生宿主**（2026-11-19，随"3A 开放世界的潜力"加的，我按推荐定，用户可以改）：Web 仍是首选平台和日常开发的环境；同时保证同一套 TS 和 wasm 代码能跑在自带 Dawn 的原生壳里（先用 Electron 这类现成的壳，不够再做 V8 加 Dawn 的专用宿主）。理由：浏览器的内存、存储配额装不下这类游戏的完整体量，bindless 和硬件光追在 WebGPU 里还没有，Dawn 的原生扩展会先有。代价：多一个要测的平台；渲染器不能用浏览器独有的东西兜底。不做的是另写一套原生渲染后端。
- **D18 大世界的坐标**（同上）：位置用双精度（变换存储的平移列改成 f64，Jolt 打开 `JPH_DOUBLE_PRECISION`），渲染时减去相机位置再转成单精度；旋转、缩放、顶点仍是单精度。另一个选择是保持单精度、定期把世界原点搬到玩家附近（虚幻 4 的做法）：省内存，但所有存着世界坐标的地方（脚本、物理、导航、粒子、存档）都要跟着搬，容易漏。**2026-11-21 用户定的方向：各种类型的值都尽量高精度，按需要做足、不做没必要的精度，双精度不够的场景另想办法**（不只是位置的浮点数，见"原则"的"精度"）。位置用双精度加渲染原点（测过 Jolt 开双精度几乎不慢），W1 第二步做了。

- **D19 成片在哪渲染、用什么编码**（2026-11-21，随"一站式创作工作台"加的，我按推荐定，用户可以改）：推荐在浏览器里渲染、用 WebCodecs 编码（H.264 兼容最好，AV1 小；封装成 MP4、WebM），离线模式逐帧渲染不受实时帧率限制，浏览器不支持的编码交给原生宿主（D17）或服务器上的无头浏览器。另一个选择是导出图像序列交给 FFmpeg，可靠但要装外部软件，作为备选的导出格式保留。
- **D20 建模做到多深**（同上）：推荐"拼搭（基本形状、预制体）加轻量的多边形编辑加程序化建模（节点图）"，精细模型靠导入和 AI 生成，雕刻放到最后。另一个选择是做完整的 DCC（Blender 那样），工作量是一个独立产品，和"引擎加编辑器"的主线抢资源。
- **D21 AI 生成**（同上）：推荐只做接口：工程里配生成服务（外部 API 或本地模型），结果当普通资源导入，记下来源、提示词和许可证；不自研模型。另一个选择是内置某家的服务，绑定供应商、有费用和许可证的风险。
- **D22 agent 的接口**（同上）：推荐编辑器的每个操作都落成"场景文档的修改"或"资源接口的调用"，人和 agent 走同一条路；对外给 MCP 服务（agent 直接用）和命令行（脚本、CI 用），字段描述导出成 JSON Schema。另一个选择是只给命令行，agent 也能用，但要它自己拼参数，出错多。
- **D23 线性内容的画面标准**（同上，用户 2026-11-21 定"3A 风格"：现在的 3A 大作已经有接近电影的效果）：成片和游戏用同一套渲染，画面以当代 3A 的电影感为标准（路径追踪模式、ReSTIR、体积、皮肤和头发这些都要做到）；离线模式在这之上加子帧累积（抗锯齿、真实的运动模糊、降噪更干净）和更高的采样数，P5 的路径追踪是成片的最高档。不另写一套独立的离线渲染器，画质的提升都落在同一个渲染器里，游戏和成片一起受益。
