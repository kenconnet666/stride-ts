# 定位：和市面上的 Web 游戏引擎比

状态：预估，2026-11-17。我们的引擎还没有代码；性能部分是从架构推断的，必须由原型实测；其他引擎的情况来自它们公开的定位和设计。

一句话：在**每帧 CPU 开销、启动速度和缓存设计**上，有条件做到同类最好的一档；**画面**有别人没有的特色（和桌面 Stride 一致）；**功能丰富度**短期内明显落后于成熟引擎，长期目标是追平 Stride。

| | 我们（预估） | Babylon.js | PlayCanvas | three.js（+ R3F 等） | Cocos Creator | Unity WebGL | Godot（Web 导出） |
|---|---|---|---|---|---|---|---|
| 类型 | 游戏引擎，引擎层 TS，热循环在 C++ 编的 wasm 里 | 游戏引擎（TS） | 游戏引擎（JS）加云端编辑器 | 渲染库 | 游戏引擎（TS）加编辑器 | 原生引擎编成 wasm（IL2CPP） | 原生引擎编成 wasm |
| 每帧 CPU 开销 | 低：数据导向，wasm 里批量处理，物理和渲染共享内存 | 中 | 中偏低 | 中 | 中 | 低 | 中 |

编辑器思路接近的先例：PlayCanvas（浏览器里的编辑器）、Cocos Creator（Electron 桌面编辑器加 TS 引擎）。我们的区别在于：编辑器的 Node 后端在本地，工程是文本文件，可以用 git 管理；渲染器和桌面 Stride 画面一致；物理是共享内存的 Jolt。

## 特色

1. **编辑器和游戏是同一个渲染器**：编辑器视口就是运行时，所见即所得；脚本在编辑器里也能热重载。
2. **和桌面 Stride 画面一致**：复用 Stride 的着色器，可以截图逐项比对。
3. **从 Stride 迁移有路径**：工程导入器搬内容；API 和组件是 Stride 的形状，熟悉 Stride 的人容易上手。但游戏逻辑要按系统重新移植，不是逐个脚本翻译。
4. **为浏览器的瓶颈设计**：数据导向、共享内存、GPU 驱动的实例化，适合物体多的场景。
5. **TS 热重载**：几百毫秒生效，没有 AOT 编译等待。
6. **缓存友好**：引擎和 wasm 库长期缓存，游戏更新只下载几十 KB 的代码加上改动的内容。

## 短板

1. 功能从零开始：第一年大概只能做到"能跑 Stride 的几个样例"。
2. 只支持 WebGPU：不支持的浏览器和老设备跑不了。
3. 社区和生态要从零做起。
4. 编辑器要从零做：场景编辑、属性面板、资源浏览、撤销重做、预制体，是和引擎同样量级的工程。
5. 维护量大：自有渲染器、引擎层、四五个 fork 的原生库。

## 性能预估（2026-11-17，给原型定目标用，不是承诺）

依据：C# 移植版在同一台机器上的实测数字、我们架构下每帧要做的工作量、各个组件典型的开销量级。参考机器：12 线程 CPU、RTX 3050 Laptop，屏幕 2560×1600 165 Hz 和 4K 143 Hz。

### Third Person Platformer 规模（约 150 个静态物体、1 个角色、几盏灯、方向光阴影）

| 指标 | C# 移植版（实测） | 我们（预估） |
|---|---|---|
| 主线程每帧 CPU | 同类的 RPG 13–16 ms，满载 | 约 2–4 ms：JS 组织 1–2 ms，wasm 变换和剔除约 0.2 ms，Jolt 0.2–0.5 ms，WebGPU 命令编码 0.5–1.5 ms（100–300 次 draw） |
| 帧率上限 | CPU 卡在 60 fps 左右 | CPU 能支撑 250 fps 以上，实际由显卡和刷新率决定 |
| 2560×1600 | — | 165 Hz 有希望跑满，显卡约 40–70% |
| 4K | — | 60–100 fps 比较现实，显卡容易成为瓶颈 |
| CPU 占用 | 主线程一个核跑满 | 165 Hz 时主线程占一个核的 30–60%，按 12 线程算总体 3–5%；Worker 平时空闲 |

### 物理压力（大量物理驱动的箱子，实例化绘制）

| 动态物体数 | Jolt 步进（按单个核心估计，SIMD） | 渲染的 CPU 开销 | 预估帧率 |
|---|---|---|---|
| 1,000 | 约 1 ms | 几乎为零 | 165 Hz |
| 10,000 | 约 5–10 ms | 同上 | 单核 60–120 fps；我们只出多线程版，实际更高 |
| 50,000 以上 | 几十 ms | 同上 | 靠多线程分摊，或降低物理频率 |

### 其他

- **启动**：代码 gzip 后约 1.5 MB，wasm 编译不到 0.5 秒，主要时间花在下载内容上。
- **内存**：wasm 堆固定大小（例如 256 MB），JS 堆几十 MB；显存取决于纹理。
- **卡顿风险**：JS 的 GC（引擎路径上禁止每帧分配），以及首次用到某个材质时编译管线（加载时预热）。
- **最不确定的**：
  - 显卡占用：取决于渲染器的实现质量和画面设置。
  - Jolt 在 wasm 里的速度：通常比原生慢 1.5–3 倍。
  - 浏览器差异：以上按 Chrome 估算。
- **验证**：CPU 端用 `tools/` 里的帧时间、CPU 剖析、WebGPU 调用统计；GPU 端用 WebGPU 时间戳查询；和 C# 移植版、Babylon.js、PlayCanvas 跑同一个场景对比。

## 原型要实测的性能点

- 少量物体的简单场景：预计和 Babylon.js、PlayCanvas 差别不大，瓶颈在 GPU。
- 物体很多、物理很多的场景：架构上应明显更好，这是主要卖点，要专门做压力测试，和 Babylon.js、PlayCanvas 跑同一个场景对比。
- 画面：目标是和 Stride 一致，不是超过它。
